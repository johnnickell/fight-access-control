# Feature references and Permission removal (unreleased)

[TASK-00065](../planning/tasks/00065-TASK.md) extends the existing removal boundary. `PermissionRepository::remove($expected)` is the only supported Permission removal write exposed by this package; `ReconcileManagedPolicyHandler` calls it for omitted managed definitions. There is no separate Permission deletion command or API. A direct repository caller must use the same transactional Unit of Work and authorize its own entry point. Neither a planner preview nor `hasFeatureReference($id)` grants removal authority.

Every stored Feature binds a stable Permission ID, regardless of OFF, PREVIEW or ON status. An unpaginated, authoritative `hasFeatureReference(PermissionId)` read allows `ManagedPolicyPlanner` to reject an invalid removal in preview and reconciliation. Storage errors must propagate, not be treated as an empty inventory. `remove()` is the final guard: it compares the expected Permission to the current definition and rejects Role, Agent **or any Feature** reference under the shared permission-reference fence through the enclosing commit. The handler rolls back other reconciliation mutations on rejection and publishes no success fact. Failure dispatch uses the ordinary command-failure contract; success publication after commit is best effort, not a rollback trigger. A Feature reference does not confer a Permission, alter a tier, prohibit promotion or make a protected Permission assignable to an Agent.

## Consumer adapter and schema obligations

Compose Feature creation, Permission removal, Role/Agent reference writes and the transaction manager on the same persistence boundary. The absence decision and removal must remain fenced through commit; Feature insertion checks the actual Permission ID under that same fence through commit. A conflicting insertion and removal cannot both commit. If removal wins, a later Feature insertion rejects the missing ID with `FeatureReferenceException`, never resolves a different Permission by name. Roll back every insertion in a losing atomic provisioning pass. A future Feature rebinding must check the target ID and its expected-state revision under that same fence, including stale and validated no-op attempts; it may not silently accept a broken binding. TASK-00066 owns the actual rebinding implementation and proof.

Consumer schema and adapter updates must implement the new `hasFeatureReference` method and the final removal fence together, not merely add a paginated reference query. Existing consumer Feature mappings require a binding index/constraint or equivalent locked predicate whose coverage includes every status and uncommitted conflicting writer. Verify transaction isolation, lock ordering, concurrent inserts/removals and crash/rollback behavior on the **actual** database/connection before adopting. The package ships no adapter or migration and does not qualify real database concurrency. A direct database writer bypassing the shared protocol is outside the package guarantee. All caller entry points, including command-bus and direct repository use, remain consumer-authorized; a Feature's testing Permission is not that authority.

## Executable evidence and remaining work

`tests/Application/AccessControl/Feature/Conformance/PermissionFeatureReferenceConformance.php` defines consumer-bindable persisted-outcome scenarios for all statuses, a sole target binding after 25 unrelated bindings (to catch first-page-only scans), unreferenced deletion, both committed winner orders and missing-ID creation. Bind its environment to real adapters and add transaction overlap/rollback races under actual database isolation. The package binding and managed-policy/handler tests exercise controlled reference state, preview, late final-guard rejection, provisioning contention, rollback and event ordering; they do not prove real concurrent processes. TASK-00066 adds rebinding/management conflicts; TASK-00067 adds guarded Feature deletion and reintroduction. Do not deploy or release a partial Feature composition on this package proof alone.
