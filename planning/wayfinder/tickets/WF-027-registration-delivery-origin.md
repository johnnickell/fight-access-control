# Distinguish registration mail from private invitations

**Labels:** `wayfinder:grilling`
**Mode:** HITL
**Status:** Closed
**Gate:** —
**Map:** [Optional user self-registration for v1.0.0](../self-registration-v1-map.md)
**Depends on:** WF-026

## Question

How should an opt-in registration's password-setting email be distinguishable from a private invitation to the consumer mail provider throughout retries, resends and restart recovery, without putting templates in AccessControl?

## Must decide

- The existing activation credential/journey is reused. A durable, immutable registration-versus-private-invitation origin accompanies recoverable delivery and reaches the consumer-owned provider for template choice, including after restart.
- Registration resend is settled to retain registration origin; retries and restart also retain the recorded origin. Existing private-invitation correction must not silently correct a registration; distinct administrator registration recovery must cover wrong-address correction and a new activation after an expired registration at the same email. Administrator recovery retains the same pending User and its Role set for both cases, and reissues registration-origin activation rather than a second User. Administrator authorization details belong to downstream design. A deleted User restored to pending activation by an administrator begins a new private-invitation journey, not registration recovery.
- The provider invocation must expose durable origin for both existing private invitations and new registrations so the consumer selects its own templates; provider adapters need to handle the new contract. No package template or additional template-configuration service is required.

## Required evidence

- `ActivationGrant::purpose()` always returns `activation`; `DeliverUserInvitationHandler` passes only purpose, delivery ID, destination and credential to `CredentialDeliveryInvocation`. `FindDueCredentialDeliveriesHandler` merges secret-free due-work by purpose/ID and the subscriber dispatches `DeliverUserInvitation` from publication events; neither path supplies a template origin after restart. `ResendInvitationDeliveryHandler` issues a successor grant, while `CorrectPendingInvitationHandler` and pending `RestoreUserHandler` also issue activation successors without origin today. The chosen origin must survive persistence/claim/provider invocation and authorized replacement rather than depend on transient publication metadata.
- The project profile and `docs/credential-delivery.md` assign mail/templates to consumers. The package currently has only `CredentialDeliveryProvider::deliver(CredentialDeliveryInvocation)` with purpose `activation` for the current invitation journey; it has no registration-origin distinction and cannot prove how an actual consumer currently configures invitation copy. Consumer integration must verify its real invitation and registration templates and origin routing; package planning/verification can prove provider invocation metadata, not consumer deployment.

## Resolution boundary

Decide durable business origin and consumer-facing selection, not copy, HTML, framework mail adapter or production template implementation. Preserve one-time grant, recoverable delivery and existing invitation semantics. [WF-026](WF-026-registration-admission-and-default-authority.md) already settled admission/default authority; exact PHP shapes, provider-adapter upgrades and consumer qualification follow in EPIC/TICKET work.

## Resolution

**Settled by John:** Reuse the existing one-time activation journey for public registration. Persist a non-sensitive, immutable registration-versus-private-invitation origin with the recoverable activation delivery, and expose that distinction on the provider invocation so the consuming project can select its own registration or private-invitation template. Never derive the distinction solely from an event, HTTP route, or the existing `activation` purpose. A replacement delivery must retain the correct origin; restart and retry must not lose it. John explicitly confirmed that **a resend of a user registration must still be known as a user registration**, not relabeled as a private invitation. The detailed representation belongs to later design, not this planning interview. John agreed the existing administrator-only `CorrectPendingInvitation` path must stay specific to private invitations, **but explicitly wants administrator registration recovery** rather than leaving a stuck registration. Do not interpret agreement as ruling out authorized correction of a registration; its separate operation covers wrong-address correction and expired-same-email activation reissue for the existing pending User. The current correction handler already atomically replaces a pending User email and grant under its invitation-specific authorization port; this is a candidate reuse seam, not permission to route registration through that command. Administrator registration recovery also permits a **new activation after an expired registration for the same email**, not only wrong-address correction. Existing `ActivationGrant::isUsableAt()` rejects exact/post-expiry credentials while `isIssued()` may still be true; delivery expiry terminalizes delivery material but not the account identity or necessarily the grant. Recovery therefore cannot treat expired delivery as a retry of the old token. John confirmed that both administrator recovery cases retain the same pending User and assigned Role set: correcting a wrong address or issuing fresh activation after expiry at the same email must invalidate predecessor activation authority, issue fresh registration-origin grant/delivery and audit the change, not create a second User or expose anonymous takeover. Existing-role reconfiguration is not part of this recovery. Detailed authorization port/API and concurrency proof remain design obligations. John confirmed that an administrator restoring a separately deleted User to `PENDING_ACTIVATION` starts a **new private invitation** even if the User originally self-registered; this is not registration resend/recovery. Private invitations continue to route through consumer-owned templates; the new non-sensitive origin must be passed on the common provider invocation, with existing private invitation behavior retained and consumer adapters verified against the new contract. No package-owned template/configuration service is introduced. This closes WF-027, not the map's remaining public-request safety decision or consumer integration proof.
