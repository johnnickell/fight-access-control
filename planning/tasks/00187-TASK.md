# Record retryable delivery failures that end in expiry

## What to Build

When an admitted invitation, password-reset, or email-change delivery worker records a retryable attempt and the next retry would fall at or after delivery expiry, commit `expired` and one truthful delivery-failed audit entry together when audit is enabled. The audit must retain the actual bounded failure classification, not provider diagnostics. Normal priority; no known blockers. The existing shared audit and family composition owners ([TASK-00122](00122-TASK.md), [TASK-00124](00124-TASK.md), [TASK-00125](00125-TASK.md), [TASK-00126](00126-TASK.md)) are complete; this record owns the repair.

## Reproduction and cause

Observed on clean `develop` at `3d7caa712d278260a11b0f419f5a120c657ab253`, with the same source, test and dependency inputs as v0.10.0 (`ae1cd27340a97daf260bbe30ae95d2fc62826453`). PHP 8.5.12, project in-memory transaction and repositories, fixed UTC clock, stub provider returning `RETRYABLE_FAILURE`; no real mail or database. Issue an invitation at `2026-08-25T11:00:00Z`, expiring at `12:00:00Z`, and make its first attempt (60-second backoff):

| Attempt time (UTC) | Next retry would be | Expected with audit enabled | Observed with audit enabled |
| --- | --- | --- | --- |
| 11:58:59 | 11:59:59 | `retry_pending` and one audit entry | Both committed |
| 11:59:00 | 12:00:00 | `expired`, recoverable material cleared, and one audit entry | Exception; prior `claimed` revision 1 remained, no audit entry |
| 11:59:30 | 12:00:30 | Same terminal commit | Same rollback |

With audit disabled, the 11:59:30 case committed `expired` at revision 2 and cleared recoverable material. The rejected outcome transactions emitted the existing command-failed notification, not a delivery success event. A successfully recorded provider failure does not emit the command-failed notification. Each probe made one stub provider call. The invitation path was reproduced end to end with in-memory collaborators; password reset and email change were traced in source but not separately run.

[`CredentialDelivery::fail()`](../../src/Domain/AccessControl/CredentialDelivery/CredentialDelivery.php) correctly produces `EXPIRED` and retains the failure reason at the boundary. [`AuditGrantOutcome`](../../src/Domain/AccessControl/Audit/AuditGrantOutcome.php) rejects that pairing (`Audit failure classification must match the persisted delivery outcome.`). An isolated status-only admission probe also confirmed that [`AuditEvidence`](../../src/Domain/AccessControl/Audit/AuditEvidence.php) separately rejects `EXPIRED` for the delivery-failed action. The handlers stage the terminal replacement and construct the audit entry in the same outcome transaction. The rejection rolls back the outcome, not the earlier claim or any external invocation.

## Scope and effects

- Existing commands only: `DeliverUserInvitation`, `DeliverPasswordReset`, `DeliverEmailChange`. Keep worker permissions, authority, generation, claim/lease and compare-and-swap checks unchanged. No new query or event; don't publish a delivery-success event for a failed send.
- Admit the truthful failure/status combination in both audit checks and on readback; update the affected [audit contract guidance](../../docs/audit-evidence.md). Preserve existing failure, success and separate expiry action semantics. Keep audit optional and keep real audit write faults atomic with outcome writes.
- No retry policy change, credential reissue, authority or reservation change, schema change, backfill, Agent delivery changes, or consumer runtime work.

## Acceptance Criteria

- [x] With audit enabled, each family commits `expired` with no recoverable material or retry eligibility when the next retry is at or after expiry. Exactly one family delivery-failed audit entry round-trips with the actual status, bounded failure classification, grant/delivery identity, revision and command correlation. No success event or new grant.
- [x] A next retry strictly before expiry still commits `retry_pending`. Both retryable classifications (`RETRYABLE_PROVIDER` and `UNEXPECTED_PROVIDER`) round-trip with their actual outcomes. Permanent failure still requires `PERMANENT_FAILURE`; contradictory status, classification or action combinations still reject.
- [x] Audit-disabled behavior remains unchanged. Stale claim, authority or compare-and-swap rejection does not commit an outcome or audit entry. A genuine audit write fault rolls back the attempted outcome without undoing the prior claim.
