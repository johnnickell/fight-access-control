# Validate and publish consumer docs automatically

## What to Build

Reuse the consumer site's reproducible validation/build command in GitHub Actions. Validate docs on PRs and automatically publish the validated site to GitHub Pages only when changes land on `main`. PRs and `develop` do not deploy. Use the existing GitHub authorization boundary; only the deployment job needs Pages write permissions. No package Commands, Queries, Events, permissions or persistence change.

## Acceptance Criteria

- [ ] A successful `main` build feeds the Pages deployment, and invalid docs fail visibly before deployment. Failed builds or deployments leave the last successful site available. Verify failure and non-deploy behavior without deliberately breaking production.
- [ ] Confirm actual Pages access/settings with the authorized repository owner at delivery. After an authorized merge, verify the Pages URL and bind a successful deployment to the exact `main` revision; workflow configuration alone is not publication proof. Use the working repository docs entry point until the hosted URL is verified.
- [ ] Do not modify branch or release policy, merge, tag or obtain new administrative privileges as a side effect of this TASK. Separate pre-merge implementation evidence from post-merge hosted evidence. If settings, merge or proof are unavailable, record the precise hold and owner; do not claim live publication.

## Verification

Run the docs build/validation command, `./bin/documentation-check`, `./bin/planning-check`, `git diff --check` and the canonical build as required for build-input changes. Independently verify the trigger and failure cases; capture the authorized hosted deployment evidence separately. No bulk notes cleanup dependency: the initial site already excludes repository-only material. Select the worktree before implementation.
