# Separate cohesive synchronous authentication capabilities

## What to Build

Deliver the use-case-interface slice of [TICKET-00035](../tickets/00035-TICKET.md). Replace the broad 17-dependency
AuthenticationService graph with cohesive synchronous owners using TASK-00111's complete User transitions.
Normally one independently reviewable public PHP interface/composition refactor with its tests and docs.

### Actors, Messages and Effects

Existing callers activate/login, refresh/logout, change/reset a password or confirm email through the owning
synchronous capability. Existing safe token/conflict/void results and domain facts remain. No raw secret becomes
a serializable Command/Query/Event; business mutations, grant consumption/revocation, audit, session effects and
post-commit publication keep their required atomicity, authorization and failure behavior.

### Responsibility and Caller Design

- Keep activation/login and token issuance in a cohesive authentication capability; refresh/current-session logout
  belong with refresh-session lifecycle, password operations with User password behavior, and email confirmation
  with its grant/use-case owner. Place collaborators in meaningful aggregate/capability namespaces, not loose roots.
- A caller needing email confirmation no longer constructs dependencies for login, activation and refresh. Show
  before `$authenticationService->confirmEmail(...)` and after the direct confirmation capability call with the
  same sensitive input and outcome. Do the same for session/password consumers; names follow the settled design.
- Each new owner performs substantive coordination and has only actual dependencies. Do not retain the old broad
  service as a forwarding facade, create one class per private method, inject handlers, use service locators or
  replace explicit operations with mode flags/options. Share token/revocation knowledge only where truly cohesive.
- Update existing constructors/named calls, fixtures, actual public consumers represented here, registrations and
  current guides/CONTEXT/README/Unreleased notes. Remove retired AccessControl APIs directly under ADR 0011.
- Visibly reconcile the profile/ADR 0003 single-service exception if TASK-00107 has not already recorded it. The
  approved amendment changes placement/interface ownership, not synchronous execution or the supported JWT profile.

## Acceptance Criteria

- [ ] Every existing secret-bearing use case has a direct cohesive synchronous owner with explicit input/result/
  failure/effects, narrower relevant dependencies and fewer unrelated caller setup obligations than the old graph.
- [ ] User/grant/session state-based rules stay Domain-owned; actual repository-backed coordination stays Application.
  Normal non-sensitive message dispatch traverses buses; no alternate handler route or duplicated Common use case.
- [ ] Login dummy-hash/throttle/rehash, activation/grant single use, token/session lifetimes, refresh conflict/replay,
  logout, password/reset and email authority outcomes are preserved with complete atomic/audit/revocation behavior.
- [ ] Stale writers, competing sessions/grants, provider/storage failure, lost commit acknowledgment where applicable,
  rollback and post-commit publisher faults retain their existing distinct outcomes. Notification failure cannot
  replace a primary fault, imply rollback or broaden the scoped Agent issuance-warning exception.
- [ ] Raw secrets remain SensitiveParameter, non-serializable and absent from returned diagnostics/messages/facts;
  existing safe results/wire contracts and independent consumer entry-point authorization remain unchanged.
- [ ] Retired broad API/callers are replaced without aliases/legacy modes, and current docs/fixtures reflect the
  new composition. Existing meaningful failure/concurrency tests are retained or replaced without coverage loss.
- [ ] Focused direct-capability/journey/race tests, complete full gate/exact coverage/local receipt and independent
  Review/applicable behavioral QA verify the implemented interface redesign, not just delegation mocks.
