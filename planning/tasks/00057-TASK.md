# Preserve operation-key meaning across canonicalization upgrades

## What to Build

Deliver historical-version resolution and cross-upgrade compatibility through actual provision/rotation/status
paths, using TASK-00056's compatible creation-cohort contract. Stored and tombstoned keys retain their original
request meaning through normalization changes and restart. This is slice C approved on 2026-09-27 under
[TICKET-00014](../tickets/00014-TICKET.md), targeting `v0.5.0`.

Build on TASK-00046's versioned binding and same-key contract, not a second canonicalizer subsystem. Add required
historical-reader integration, upgrade fixtures, consumer-bindable cases and canonical-version migration guidance.
Concrete supported representations/version rules are design obligations before acceptance, not assumed production values.

## Use Case and Contract

- **Actor/trigger:** a currently authorized originating caller or explicitly delegated worker retries/reads a retained
  operation after a package/normalization upgrade or restart; a caller creates an unseen key in a compatible cohort.
- **Validation:** enforce trusted scope/current authority before lookup or existence disclosure. Resolve existing keys
  before choosing a canonicalizer, including tombstones, and use their recorded version plus sufficient safe canonical
  request. Only an unseen key uses the selected compatible creation version.
- **Effects:** equivalent historical retry resolves the original outcome without generation/mutation/audit; conflict
  or unknown version denies without disclosure, rebinding or fallback issuance. Status reads have no commit/events.
  A genuinely new request uses the normal owning service's atomic issuance/event contract, not a migration workflow.
- **Failure:** unavailable state stays unavailable/indeterminate; absent reader support is not evidence that the key
  is new. Never repair incompatibility by rewriting old bindings under today's normalizer or inventing another key.

## Acceptance Criteria

- [ ] Document supported historical-reader/creation-version responsibilities, retained lifetime and sufficient safe
      canonical representation. Required readers remain available for retained keys/tombstones; removal cannot silently
      reinterpret history. Keep public DTOs and exceptions within existing Domain/Application ownership.
- [ ] Seed persisted provision and rotation outcomes under an earlier canonical version, change normalization/version
      selection, restart composition and retry through actual public services. Equivalent original requests resolve
      original Agent/credential/delivery identities with no duplicate secret generation, mutation, audit or fact.
- [ ] Historical conflicts remain conflicts across normalized name, kind, rotation target/predecessor, destination
      identity/revision and outcome-affecting options. New normalization cannot turn an old conflict into equality or
      old equality into a conflict; original rotation retry does not reapply its now-stale predecessor mutation check.
- [ ] Retained, completed, retired and tombstoned keys use recorded semantics. Unknown/corrupt version or unavailable
      reader denies safely without selecting the current canonicalizer, disclosure, key reuse or fresh issuance.
      Cleanup cannot make a previously issued key unseen or substitute a successor's credential.
- [ ] TASK-00056's compatible cohort selects agreed new-key creation rules. Test incompatible/restarted creators and
      supported historical readers separately; retaining an old reader does not authorize an old creation cohort.
      Destination meaning and ownership/order fences cannot be reinterpreted during an upgrade.
- [ ] Wrong scope/caller, revoked authority and expired delegation deny historical retries/status without exposing
      another scope. Versions, bindings, status and failures remain secret-free; no raw/ciphertext secret, key path,
      provider exception detail or read capability leaks. Issuance remains distinct from delivery/activation/use.
- [ ] M3 focused behavior/conformance tests prove cross-version outcomes through services and TASK-00047 reads, not
      migration-file or normalizer source inspection. Preserve current-contract tests with TASK-00046/00048/00049;
      this TASK owns upgrade/restart semantics rather than taking over basic correlation tests.
- [ ] Publish historical-reader retention and safe upgrade guidance alongside implemented behavior. No actual consumer
      database conversion, contract-binding rewrite or rollout occurs. No extra routine approval/configuration is added.
