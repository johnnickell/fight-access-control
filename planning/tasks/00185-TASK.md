# Support atomic consumer participation in email-change transitions

## What to Build

Give consumers a supported public way to save required notification work in the same transaction as an
email-change request or confirmation. If any required write fails, save neither the transition nor its
notification work. Consumers own notification identity/storage, templates, delivery, scheduling and recovery;
AccessControl continues to own User/grant/session changes and its optional audit.

John approved this bounded integration-contract correction after the pre-v0.9.0 audit. At intake, only record
creation had started. This standalone chore adds no new email-change policy and does not reopen historical
feature/audit parents.

## Use Cases and Contracts

| Actor and trigger | Commands / Queries / Events | Outcome and expected side effects |
| --- | --- | --- |
| Admitted owner or administrator requests an email change | Existing `RequestEmailChange` and its registered handler; existing post-commit fact | Reservation, grant/delivery, enabled audit and configured consumer request-notification intent commit together. |
| Credential holder confirms the accepted change | Sensitive synchronous `confirmEmail()`; existing post-commit confirmation fact | Exact grant consumption, identity promotion, reset/session invalidation, enabled audit and configured completion-notification intent commit together. |
| Consumer participation or another required write fails | Existing operation failures; no new success fact | All staged participant/business/audit writes roll back; no external mail is sent inside the transaction. |
| Commit acknowledgement or later publication fails | Existing authoritative observations and failure behavior | Preserve indeterminate acknowledgement and committed-state semantics; never enqueue later by assuming rollback or repeat the business transition blindly. |

## Scope and Boundaries

- Design and implement a narrow typed public participation contract owned by email-change transitions. Keep the
  registered handler/synchronous capability as the transaction coordinator. Do not expose private handlers or
  duplicate package transition policy in the consumer.
- Supply facts from the actual accepted transition: target User, exact grant/request and reservation generation,
  stage, original canonical old-mailbox recipient, trusted transition time and available initiating/proof
  attribution. Keep requester, target and later confirmation proof distinct; do not claim an identified human
  from bearer-secret possession or attribute confirmation to the original administrator.
- Make facts sufficient to bind the completion notice to the original accepted change and old recipient, not a
  later User lookup, destination equality or time-only correlation. Account for successive changes and restarts;
  if retaining original transition facts is necessary, give them an explicit owning typed persisted contract.
- Participation must stage writes on the same actual connection and Unit of Work as package state and enabled
  audit. Configured participant failure is a required-write failure, never a swallowed notification warning.
  Define invocation/identity semantics for supported rejection, duplicate, competing-winner and retry paths.
- Retain a usable consumer-free composition with no required notification infrastructure. Document explicitly
  what omitted participation promises; do not silently skip a configured participant on a required transition.
- No provider invocation, notification worker, consumer persistence adapter, standalone public enqueue API,
  general outbox engine, repository/audit interception, transaction decorator trick, outer nested transaction,
  after-commit substitute or consumer source edit is included.
- Audit remains separately optional per its current contract. When enabled it joins the same transaction; these
  notification facts must not put addresses or secrets into existing safe audit payloads.
- Teams, templates and their Permission application belong to Agent OS in separate transactions. They are not
  part of this contract or a prerequisite. Exact-request cancellation is separately owned by TASK-00186.

## Validation, Permissions and Failures

Protect all request entries through current consumer authentication, operation/target admission and existing
package self/admin rules. Confirmation still requires its purpose-bound usable secret and exact reservation;
participation grants no authority and is not a new authentication layer. Raw credentials, hashes, ciphertext,
links and provider diagnostics never enter participant facts, serializable messages, safe Views or audit.
Keep necessary recipient personal data scoped to the consumer's protected notification intent.

Preserve rejection before mutation, same-address successor/ABA safety, expected-state comparisons, business
writer fences, confirmed-commit publication ordering and primary-fault preservation. Unknown participant/storage
faults remain internal faults, not credential refusals. Success Event delivery alone is not durable notification
intent, exactly-once sending, consumer readiness or authorization to expose the email-change journey.
