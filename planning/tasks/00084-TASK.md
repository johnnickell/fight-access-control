### Approved Binding Contract

The selected constructor extension is `AgentToolPermissionCatalog(McpToolRegistry $registry,
array $permissionBindings = [])`, with `array<string, non-empty-list<string>>` as the documented mapping shape.
This is the approved implementation target, not a currently available API. Extend the existing catalog rather
than introducing another registry, scanner, availability engine or public/unprotected mode flag.

| Attributes on `handle()` | Mapping for the Tool | Composition result |
| --- | --- | --- |
| Valid and nonempty | Absent | Use all attribute requirements |
| Absent | Valid and nonempty | Use all mapped requirements |
| Present | Present | Reject, including identical requirements; no union, override or fallback |
| Absent | Absent | Reject |

- Use explicit maps for Common-owned Tools and attributes for application/package-owned Tools. This is one
  requirement owner per Tool; malformed declarations cannot be rescued by another source.
- Resolve mapping keys as exact canonical names through Common's registry and require complete coverage of its
  definitions. Reject unknown targets, wrong key/value types, non-list/empty lists and malformed Permission strings
  anywhere in the input before returning a catalog. Do not trim, case-fold, alias or duplicate Common naming rules.
- Validate strings with `PermissionName::fromString()` and deduplicate equal canonical requirements within the
  selected source, preserving first-declaration order. All remaining requirements are conjunctive, never any-of.
- Configuration loaders/consumers must reject duplicate target keys before constructing or merging the PHP map;
  the catalog cannot recover keys already overwritten by PHP. Do not advertise detection of erased duplicates or
  last-wins configuration merging as supported behavior. No new configuration parser is required by this TASK.
- Retain the exact Common definition objects, not newly reflected/cloned metadata. Unknown or same-name foreign
  runtime definitions deny before principal resolution. Empty registry plus empty mappings authorizes nothing;
  an unknown mapping still rejects. Public/unprotected composition remains separate.

### Request Lifetime and Entry Obligations

One request shares the provider, signed request and correlation across transport, availability and request-bound
profile Tools. The availability remembers successful or failed lazy resolution; a transport authentication failure
is terminal for that request, not permission to retry the provider independently. Reuse no principal, decision or
filtered page across requests. Rebuild registry and catalog together when Tools capture request state; only static
metadata tied to the exact same registry and independently request-safe Tool instances may cross requests.

Discovery stays private/zero-TTL and filters before Common pagination. Each later page, invocation and interaction
retry has fresh request authority and nonce. Common may privately open opaque retry state to locate the candidate
before availability, but restoration/disclosure, response validation, confirmation consumption and resume remain
after admission. Short-request snapshots do not promise in-flight cancellation or revocation-through-commit locking;
background/live continuation has its separate owner and must not replay the original consumed nonce.

Attributes do not intercept `handle()`. Every exposed direct Tool, CLI, HTTP, broker or worker entry must establish
its actual caller, applicable operation Permission and target scope before configured dispatch. The raw in-process
bus remains trusted infrastructure, not another authenticated public API; do not add blanket duplicate Application
or bus authentication. Owning Query admissions still enforce genuine scoped business policy under TASK-00089/00090.
A Tool grant must not manufacture all-project, reference, metadata or body scope. Consumer examples must retain
metadata-only protected reads rather than require body Permission merely to expose `execution.messages`/`execution.detail`.

### Actors, Triggers and Side Effects

| Actor and trigger | Commands / Queries / Events | Outcome and side effects |
| --- | --- | --- |
| Integrator constructs the mixed protected registry/catalog | N/A; static composition | Validate complete nonempty requirements and identity before serving protected work; no Tool execution, principal resolution or grant. |
| Agent requests discovery or direct invocation | No new checking message; admitted Tools retain their existing use cases | Filter before paging and deny before selected validation/handling/buses/progress; admitted Tools retain their actual effects. |
| Agent retries a protected interaction in a later request | No new checking message; Common owns interaction/confirmation | Fresh request admission precedes protected restoration, input-response validation, confirmation consumption and resume. |
| Unknown/foreign definition, missing Permission or unresolved authority reaches admission | N/A | Deny without borrowing a same-name grant or disclosing protected work, metadata or diagnostics. |

Authentication retains its existing request-scoped nonce transaction and authority fences. Reuse the same trusted
provider within one request; the mapping/check itself adds no Command, Query, Event, business mutation or commit.
Profile Tool writes retain their existing handlers' effects. Execution Tool Query-bus fixtures prove coarse
Tool-to-Query admission, not application scope or protected-body authorization.
