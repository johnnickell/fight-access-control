# Protect mixed Common-owned and attributed MCP Tools

## What to Build

Deliver the complete [TICKET-00025](../tickets/00025-TICKET.md) outcome in one independently reviewable feature
TASK: explicit Permission mappings and attributes coexist in one protected Common Tool registry. Consumers can
protect all seven Common-owned execution Tools alongside existing attributed Agent profile Tools without copying
schemas, subclassing final Tools or weakening complete fail-closed requirements.

Extend the existing immutable `AgentToolPermissionCatalog` composition and reuse `AgentToolAvailability` and
`CurrentAgentPrincipalProvider`. Specify the current public mapping API and deterministic attribute/mapping
coexistence/conflict rules during implementation; no silent override or implicit public Tool is allowed. Retain
Common's complete canonical registry and exact immutable definition identity rather than adding a second Tool
list or naming algorithm. All declared canonical `PermissionName` requirements remain conjunctive direct Agent
checks. Requirements and grants remain consumer-configured; this TASK supplies no automatic grants or managed
execution Permission vocabulary.

Include `execution.summarize`, `execution.list`, `execution.get`, `execution.phases`, `execution.activity`,
`execution.messages` and `execution.detail`, plus existing profile Tools. Qualify their real Common discovery and
invocation paths together with explicitly mapped interactive Tool retries. Common owns schemas, mirrors,
validation, interaction state, confirmation and protocol output; AccessControl supplies only a neutral decision.

This is one complete integration path, not a catalog-only prefactor followed by a testing-only TASK. Tests,
dependency qualification and public composition documentation belong with the feature. Keep existing Application/
Domain ownership and [ADR 0011](../adr/0011-pre-v1-current-contract-only.md)'s current-contract policy; a retired API
needs neither an alias nor a compatibility mode.

### Actors, Triggers and Side Effects

| Actor and trigger | Commands / Queries / Events | Outcome and side effects |
| --- | --- | --- |
| Integrator constructs the mixed protected registry/catalog | N/A; static composition | Validate complete nonempty requirements and identity before serving protected work; no Tool execution, principal resolution or grant. |
| Agent requests discovery or direct invocation | No new checking message; admitted Tools retain their existing use cases | Filter before paging and deny before selected validation/handling/buses/progress; admitted Tools retain their actual effects. |
| Agent retries a protected interaction in a later request | No new checking message; Common owns interaction/confirmation | Fresh request admission precedes protected restoration, input-response validation, confirmation consumption and resume. |
| Unknown/foreign definition, missing Permission or unresolved authority reaches admission | N/A | Deny without borrowing a same-name grant or disclosing protected work, metadata or diagnostics. |

Authentication retains its existing request-scoped nonce transaction and authority fences. Reuse the same trusted
provider within one request; the mapping/check itself adds no Command, Query, Event, business mutation or commit.
Profile Tool writes retain their existing handlers' effects. Execution Tool Query-bus fixtures prove coarse
Tool-to-Query admission, not application scope or protected-body authorization.

## Acceptance Criteria

- [ ] **Complete mixed composition:** Real Common registry definitions for all seven execution Tools and existing
  attributed profile Tools compose with validated nonempty requirements. Define/document coexistence and conflict
  mechanics; explicit declarations cannot silently replace attributes, canonicalize a second identity or make an
  unmapped protected Tool public. Common final classes and schemas are neither changed nor copied into wrappers.
- [ ] **Invalid configuration fails closed:** Missing/empty requirements, malformed Permission values, unknown
  mapping targets and conflicting declarations reject the entire composition, including invalid entries after
  valid ones. Same-name foreign/cloned definitions and unknown runtime definitions deny without resolving authority.
  Deliberately unprotected/public composition remains separate.
- [ ] **Conjunctive admission before work:** Every missing-Permission permutation and unresolved/faulting authority
  denies through real Common discovery/invocation before selected validation, Tool handling, Query/Command bus work,
  progress or protected diagnostic output. Unknown and unavailable public outcomes remain equivalent. The neutral
  port exposes no Agent principal, Permission reasoning, credential or raw exception message.
- [ ] **Permitted real journeys:** Admitted calls use actual Common discovery/invoker/Tool paths and the real
  AccessControl provider with controlled authoritative port fixtures, not only a Boolean availability stub. Assert
  each execution Tool's owning Query dispatch and safe result behavior, along with preserved profile Tool effects.
  Separate consumer Query admission is not replaced by this coarse capability grant.
- [ ] **Request and paging freshness:** Discovery filters before Common ordering/pagination and stays private with
  zero TTL. One provider/availability resolves authentication at most once per request, including failure; foreign
  definitions perform no authentication. Fresh later pages/requests observe revoked Agent authority, credential
  replacement and Permission changes; already resolved short-request snapshots keep their documented semantics.
  No cross-request principal, allow/deny or filtered-catalog cache is added.
- [ ] **Explicit-mapping retries:** Exercise an explicitly mapped interactive Tool through the real Common
  interaction path. A permitted fresh request can complete it; revoked/rotated/Permission-denied requests reject
  before protected restoration/disclosure, response validation, confirmation consumption, resume, buses or progress.
  Common may privately open opaque state to identify the candidate before availability; this does not grant
  restoration/disclosure. Retry state, prior discovery and an old consumed nonce confer no authority.
- [ ] **Qualified dependency contract:** Establish actual accepted/qualified/tagged Common APIs and the first
  supported dependency minimum for every newly used declaration; record exact version/source/lock identity in
  ignored evidence. Make only the necessary deliberate manifest/dependency changes under the later implementation
  scope. Test the supported minimum, not only a newer local checkout. No guessed version, dev-snapshot-as-stable
  adoption, compatibility fallback or unsupported advertised integration satisfies this criterion.
- [ ] **Documentation and gates:** Update `docs/agent-mcp-authorization.md`, affected current composition examples
  and `CONTEXT.md` for the chosen API, conflicts, request lifetimes, minimum and remaining consumer obligations.
  Focused catalog/provider/profile/interaction and real Common composition tests cover failures and effects; exact
  owned statement coverage, planning/documentation/diff checks and the full canonical package gate pass with a
  complete log/exit/receipt. Record warnings and fixture/actual-consumer qualification limits.
- [ ] **Independent acceptance:** Required independent technical Review and behavioral QA accept the implemented
  subject and its nonvisual request/result, denial and effect evidence. Planning approval, the historical 7/7
  rejection probe or a green focused test alone is not implementation acceptance.
