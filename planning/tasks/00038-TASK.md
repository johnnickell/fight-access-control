# Orchestrate provider-neutral credential delivery outside transactions

## What to Build

Implement package handlers, direct registrations, due-work/status queries, provider-neutral sensitive invocation and
typed outcome capabilities for invitation, password reset, and email change. Refactor the present invitation and
email-change handlers and add the missing password-reset provider path so every provider invocation occurs after a
committed claim and before a separate expected-state outcome transaction.

## Acceptance Criteria

- [x] Originating handlers retain their one atomic commit and post-commit events; discovery supplies recovery when
      dispatch is lost.
- [x] Every external provider call observes no active Unit of Work transaction; claim and matching outcome each commit
      independently.
- [x] Provider invocation receives stable effect identity and short-lived sensitive material, returns a typed outcome,
      and cannot leak arbitrary provider errors into durable/public diagnostics.
- [x] Repeated invocation after provider acceptance/outcome-commit crash uses the same idempotency identity and proves
      only at-least-once semantics.
- [x] Existing invitation lifecycle variants, reset lifecycle, and email-change lifecycle retain aggregate policy,
      audit evidence, stale-generation fencing, and direct package handler registration.

exact leased claim before decrypting or invoking the shared provider-neutral capability, then commit one matching typed
outcome separately. Provider adapters receive the stable delivery-generation ID as their idempotency identity. Typed
retryable and permanent outcomes retain or destroy material through existing aggregate policy, while unexpected
provider throwables become secret-free retryable failures without publishing arbitrary diagnostics.
