# Replace CONTEXT with a domain glossary and apply bounded simplifications

## What to Build

Replace the oversized CONTEXT orientation document with a focused root GLOSSARY.md, preserve its useful
contracts and historical evidence under their proper owners, and apply the four other agreed simplifications
from the read-only assessment. This standalone chore owns one bounded PR, not a general repository cleanup.

John approved all five assessment findings, replaced the proposed CONTEXT navigation-only change with a
strict domain glossary, and requested this record. Saving the TASK does not start implementation or authorize
publication, merge, release, deployment or changes to another repository.

### 1. Use GLOSSARY.md for domain language only

Create one root GLOSSARY.md for the AccessControl context. Start from CONTEXT's existing vocabulary and check
accepted contracts and current source before retaining or tightening definitions. Define each project-specific
domain term in one or two sentences; use canonical names, natural groupings and useful `_Avoid_` aliases where
already resolved. Do not invent synonyms to avoid or silently resolve disagreements between source and approved
contracts. Surface any genuine unresolved meaning before changing it.

The glossary contains definitions only: no implementation details, specifications, operational procedures,
architecture decisions, implementation progress or acceptance checkpoints. Short links to an owning concept or
guide are allowed as navigation, not as an excuse to embed those explanations. Do not include general programming
terms merely because the package uses them. No glossary map or multiple-context structure is needed for this TASK.

### 2. Retire CONTEXT without losing requirements or evidence

Preserve the original CONTEXT content as an explicitly historical reference outside mandatory orientation,
for example under docs/history/. Preserve checkpoint wording, approvals, subject identities, warnings, corrections
and qualification limits; make only necessary relocation/link repairs. Do not infer current delivery outcomes from
old checkpoints or archive planning records.

Before retiring the root document, inspect its non-glossary content and account for unique still-current
requirements. Keep those accessible in existing owning composition guides, project profile, standards or ADRs;
move unique material where needed and link rather than duplicate. Do not create ADRs merely to house ordinary
instructions or create another catch-all current-status document. Retain existing ADR locations and identities.
A migration inventory in the TASK-owned ignored handoff must identify the destination for each substantive
section and distinguish retained history from current requirements.

Update active references and required-reading instructions in AGENTS.md, CONTRIBUTING.md, README.md,
planning/agents/project-profile.md and affected local standards, including Architecture, Naming and Governance.
Use the glossary for vocabulary, relevant guides for behavior/composition and applicable ADRs for decisions.
Record the explicit project-local convention in docs/engineering/STANDARDS.md without editing the shared
standards provider or weakening any non-vocabulary requirement. Find and repair affected links across the checkout;
historical records retain their meaning and approvals. Remove root CONTEXT.md only after replacement destinations
and local links are verified. Do not leave it as a second mandatory orientation document.

### 3. Give build preparation and cache behavior one documentation owner

Use docs/engineering/LOCAL_TOOLING.md as the detailed authority. Correct CONTRIBUTING.md's claim that every
normal build performs image refresh and README.md's unconditional preparation description. Summarize and link
the distinction: normal build validates planning freshly and either reuses qualifying application evidence or
prepares and executes the full gate; `--force` requests fresh application execution.

Preserve runtime security-floor and fail-closed admission requirements, preparation on a cache miss, receipt/input
equivalence, and honest reporting of retained versus fresh evidence. Do not imply focused wrappers bypass runtime
admission. Change documentation, not build/cache/runtime behavior.

### 4. Centralize authentication-refusal classification only

Add a narrowly named predicate, such as isAuthenticationRefusal(), to
src/Domain/AccessControl/Agent/AgentAuthenticationDiagnosticClassification.php. Replace only the repeated
membership expressions in RequestAuthority, AgentTaskAuthority and the Prompt/Resource/Skill availability owners.
The same two classifications remain refusals: AUTHENTICATION_REJECTED and AGENT_AUTHORITY_NOT_CURRENT.
PERMISSION_SNAPSHOT_INVALID and RESOLUTION_FAILED remain faults, not ordinary denials or successful empty catalogs.

Keep each caller's existing translation, null or false response, exception propagation, request-local failure
caching and catalog-before-authentication ordering. Preserve enum serialized values, public signatures and required
docblocks. Do not merge admission workflows or apply the change mechanically to Tool availability.

### 5. Simplify the two identified test setups without deleting scenarios

In tests/Application/AccessControl/Event/OperationFailureContractTest.php, construct only the authentication owner
selected by each case. Use an explicitly valid fixed test hash where construction needs one instead of repeatedly
computing hashes unrelated to the transaction-failure behavior. Keep all 14 authentication failure cases and their
independently specified expectations. Do not extend this optimization to tests that actually prove password
verification or rehashing.

Give AgentDetailReadAdmissionUnitTest and AgentExecutionReadAdmissionUnitTest a narrowly owned authenticated-Agent
fixture accepting explicit Permission names. Remove their dependency on issuance, operation recovery, audit and
profile-Tool setup through ProfileToolEnvironment. Preserve real Agent/Permission values, controlled ports,
in-memory repositories, nonce consumer and actual CurrentAgentPrincipalProvider. Do not substitute another
capability-specific fixture with unrelated responsibilities or rewrite the shared ProfileToolEnvironment for all
its consumers.

  callers keep their current behavior.

- Outcome: focused vocabulary, correct build guidance and less repeated knowledge/setup without changed contracts.
- Commands, Queries and Events: no new messages, routing, event payloads or business effects. Existing failure events
  retain primary-exception identity, allowlisted context, redaction and notification-failure behavior.
- Validation, permissions and rejection: unchanged. Keep scope concealment, conjunctive requirements, fault
  propagation, request isolation, nonce behavior and transaction/fence/recovery boundaries.
- Schema, durable data and migrations: N/A; no persisted representation or consumer-data change.
- Compatibility: public APIs, serialized values and consumer obligations remain unchanged. Documentation links
  receive explicit replacements; historical evidence is preserved rather than reinterpreted.
- Excluded: broader authorization or Permission-snapshot extraction, dependency changes, blanket test cleanup,
  deletion quotas, new quality tools, planning archival, supplier changes and publication/delivery operations.
