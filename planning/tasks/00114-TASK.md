# Establish credential-operation aggregate and narrow read repositories

## What to Build

Deliver the aggregate/interface slice of [TICKET-00036](../tickets/00036-TICKET.md). Give the independently
persisted AgentCredentialOperation a clear aggregate home inside AccessControl and separate secret-free reader
obligations from material-bearing writes. Normally one coherent Domain/Application/consumer-test/docs refactor,
not a new bounded context, persistence implementation or alternate transaction boundary.

### Actors, Messages and Effects

Provision/rotation callers resolve retained issuance; delivery/maintenance workers transition the original
operation; authorized status/scheduler readers receive safe views through existing Queries. Existing events,
issuance-warning policy and external staging/receipt behavior remain. Reader dependencies do not expose material,
claim mutation, commit or grant future authority. No new checking message, event or physical cleanup is added.

### Aggregate and Interface Design

- Move AgentCredentialOperation, its repository interface and genuinely owned identity/delivery/maintenance/query
  concepts to Domain/AccessControl/AgentCredentialOperation; align Application/query/test homes with ownership.
  Keep Agent's own lifecycle authority separate and shared concepts where actual knowledge warrants it.
- Use an aggregate-named write repository and a cohesive Domain read repository for current secret-free status,
  due-work/maintenance selection and key-reference inventory. Keep QueryHandlers on Domain repositories. Actual
  class names express the concept rather than a Store or generic persistence port.
- Before: a status/scheduler handler receives the entire AgentOperationRepository, including material/claims/writes.
  After: it receives the narrow read repository; issuers/workers receive their write capabilities plus the existing
  TransactionalUnitOfWork. Show concrete callers and methods with fewer unrelated obligations, not just folder moves.
- One consumer persistence implementation may implement both repository contracts. Do not require forwarding-only
  adapters, per-method interfaces, new generic setup sequences or a single Store implementing UoW under another name.
- Preserve real atomic repository capabilities, especially Agent retirement/cancellation, cohort/restoration and
  cross-aggregate fences. Do not replace coupled operations with generic get/mutate/save sequencing or eventual consistency.
- Review the placement of operational qualification versus Domain authority/generation evidence as part of the
  boundary: preserve mandatory all-writer enforcement, never move readiness into a caller Boolean or optional preflight.
  No speculative new qualification facade is required solely for this relocation.
- Move public read projection construction out of aggregate lifecycle knowledge where a cohesive existing query
  mapping can own it; preserve safe View/message/wire shapes. Classify every moved type by its actual Domain or
  Application responsibility, not by immutable syntax alone; do not add a miscellaneous technical Domain bucket.
- Update owned callers, constructor/named arguments, mirrored tests, schema references/registration and current
  operation/cohort/restoration/integration guides, CONTEXT/README/Unreleased notes. Remove old AccessControl paths
  directly without aliases/history readers; leave Common/consumer repositories untouched.
