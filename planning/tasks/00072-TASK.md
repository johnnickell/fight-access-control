## Concrete Design

- Query `FindExpiredCredentialDeliveries(DateTimeImmutable $at, int $limit)` validates 1–100 (no implicit default);
  the three repositories require `findExpired()` returning immutable `ExpiredCredentialDelivery` values. Filter latest
  issued eligibility before ordering/limiting; merge expiry instant, delivery ID, purpose. The safe canonical fields
  are purpose, delivery/User IDs, required nullable email grant ID, expiry, nonnegative observed revision and status.
- Dispatch `ExpireInvitationDelivery(actor, UserId, ActivationDeliveryId, occurredAt)`, existing reset delivery expiry
  or full `ExpireEmailChange(actor, UserId, EmailChangeGrantId, occurredAt)`. All expiry messages/facts preserve
  microseconds. Command handlers return void; no extra lookup, grant inference or reliable-publication result is added.
  Cleanup failure events retain the safe original command but use constant `Credential expiry failed.` rather than
  arbitrary storage diagnostics, under C9's secret-free message requirement; the original throwable always rethrows,
  even when failure notification also fails. This narrows failure text, not transactional/post-commit behavior or the
  distinct Agent issuance-warning flow.
- Persist a mandatory positive User reservation revision on each email grant, supplied as `issue()`'s seventh argument
  by the request handler and preserved across every revision/CAS. Full expiry matches this immutable binding as well
  as ownership/destination; same-email equality alone is insufficient. There is no compatibility default/backfill.
- No-progress/failure mechanics stay in the protected composition recipe: use a finite cycle/page budget, wait for
  synchronous cleanup, stop/report unchanged identity/revision pages or errors instead of spinning or claiming success.
  Async scheduling permits one bounded page per cycle; authoritative rereads resolve uncertain outcomes. No corruption
  repair or separate consumer expiry state machine. See [public composition](../../docs/credential-expiry.md).
