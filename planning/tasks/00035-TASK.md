# Authorize Agent-protected MCP Tools

## Outcome

Deliver one AccessControl-owned, request-scoped authorization integration for an Agent-protected Fight Common MCP
Tool composition. It builds an immutable catalog from Common-resolved canonical Tool metadata and repeatable direct
Agent-Permission declarations, then supplies Common only a neutral available/unavailable decision. An Agent can
discover, invoke, or resume a protected Tool only when its one current immutable principal snapshot contains every
declared Permission. Common retains MCP registration, naming, protocol behavior, and enforcement mechanics.

## Scope

- Add the accepted repeatable `RequiresAgentPermission` public metadata on each Tool's `handle()` method beside
  Common's method-level `McpToolInfo`. Use `Attribute::TARGET_METHOD | Attribute::IS_REPEATABLE`; retain the
  accepted AccessControl namespace and canonical Permission-name semantics.
- Build and validate one immutable canonical-Tool-name-to-required-Permissions catalog from the same registered Tools
  and resolved canonical names used by Common. Reflection is limited to catalog construction for an integration
  instance; repeated availability checks do not reflect again.
- Implement Common's compatible request-scoped neutral availability seam using one
  `CurrentAgentPrincipalProvider` snapshot per MCP request and conjunctive canonical `PermissionName` checks.
- Integrate that decision consistently with Common's discovery, direct invocation, and protected-interaction retry
  seams so denial precedes all protected Tool work.
- Add only additive public AccessControl API and focused behavior/conformance coverage within the existing
  Domain/Application boundary.

## Exclusions

- Fight Common Tool registration, canonical naming, `tools/list` ordering or pagination, `tools/call` selection,
  protocol errors, progress transport, interaction-state storage, and wire representation.
- Consumer routes, HTTP responses, authentication-path selection, OAuth claim or scope mapping, TLS, origins,
  limits, persistence adapters, framework composition, exposed-Tool selection, deployment, and logging backends.
- Self-service Agent profile reads or updates; their Permission identities, schemas, idempotency, events, and
  failure classifications require their own Wayfinder resolution.
- Agent Roles, implicit public Tools inside an Agent-protected composition, any-of Permission semantics,
  cross-request principal or filtered-result caching, and an AccessControl filesystem metadata cache.

## Use-Case, Message, and Effect Matrix

| Actor and trigger | Commands | Queries | Events | Expected effect and observable outcome |
| --- | --- | --- | --- | --- |
| Consumer composes an Agent-protected Tool registry | N/A | N/A | N/A | Construct the static requirement catalog from Common-resolved metadata; reject absent/malformed declarations or duplicate/drifting canonical identities before requests are served. |
| Authenticated Agent requests discovery | N/A | N/A | N/A | Resolve and reuse one current Agent principal for this MCP request; Common receives a neutral availability decision and filters unavailable Tools before its ordering and pagination. |
| Authenticated Agent invokes a selected Tool | N/A | N/A | N/A | Apply the identical availability decision before Tool validation, Tool handling, CQRS dispatch, progress, or protected diagnostic work. |
| Authenticated Agent retries a protected interaction in a later request | N/A | N/A | N/A | Resolve a fresh principal and deny an unavailable Tool before restored-state disclosure, response validation, resume, CQRS dispatch, or progress. |
| Agent lifecycle, credential revision, or Permission-assignment revision changes | N/A | N/A | N/A | A later request observes current authority. Work already authorized from the request-local snapshot is not cancelled retroactively. |

The authorization integration dispatches no Fight Command, Query, or Event. A permitted Tool may use Common's
published Tool contract to invoke its own existing use case; that Tool behavior is not owned by this TASK.

## Permission and Authorization Rules

- Every Tool in an Agent-protected composition declares at least one repeatable `RequiresAgentPermission`; every
  declared Permission is required. Any future any-of rule requires a separate accepted construct.
- Compare the immutable `AuthenticatedAgentPrincipal` direct-Permission snapshot with canonical `PermissionName`
  values. Do not add Agent Roles, OAuth-scope mapping, or a general policy engine.
- Resolve the principal once through a request-scoped `CurrentAgentPrincipalProvider`; reuse it only inside that
  request. New discovery, direct invocation, and interaction-retry requests re-resolve current authority.
- Only static requirement metadata may cross requests. Principals, availability decisions, and filtered discovery
  results remain request-local; authorization-sensitive discovery uses `ttlMs: 0` and `cacheScope: private`.
- AccessControl supplies Common no Agent, principal, Permission, diagnostic classification, policy object, raw
  arguments, credentials, headers, or separately derived Tool name: only Common's compatible neutral decision.

## Validation, Rejection, and Concealment

- Reject an Agent-protected composition when static metadata is missing, malformed, contradictory, or cannot be
  paired uniquely with Common's resolved canonical Tool identity. Public Tools use a separate unprotected
  composition; missing metadata is never an implicit public-Tool convention.
- If an unexpected absent/malformed mapping is reached at runtime, fail closed as unavailable.
- Once execution reaches this integration, unresolved authority, any missing required Permission, and an unavailable
  Tool produce the same neutral unavailable decision. Common owns the public unknown-or-unavailable outcome.
- Denial occurs before Tool-specific validation, Tool handling or resumption, protected command/query dispatch,
  progress publication, interaction-state disclosure, and protected diagnostics. Consumer transport authentication
  may still reject before MCP dispatch and is not made publicly equivalent by this TASK.
- Preserve the accepted snapshot boundary: a revocation after principal resolution does not cancel already-authorized
  same-request work, but a later request observes the change and denies before protected work.
