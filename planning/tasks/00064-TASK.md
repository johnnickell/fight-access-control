# Evaluate Feature availability with fresh, identity-safe checks

## What to Build

Deliver the complete framework-neutral evaluator for [TICKET-00016](../tickets/00016-TICKET.md), including its
Domain/Application behavior, fresh-read repository obligations, identity-safe preview checks, error distinctions,
consumer-bindable scenarios, and integration guidance. One TASK owns the full path and its tests; no authentication
prefactor or separate conformance TASK is required.

John approved this single-TASK plan and these interface choices:

- Accept a validated FeatureName plus an existing AuthenticatedUserPrincipal or AuthenticatedAgentPrincipal, or
  `null` for anonymous evaluation. Reuse the existing snapshots; do not construct an anonymous authenticated principal.
- Match the Feature's stored Permission ID against the snapshot's captured Permission IDs. Leave the shared
  AuthenticatedAuthority interface and existing name-based Permission helpers unchanged.
- Return a boolean for ordinary availability. Unknown Features and broken Permission bindings produce distinguishable
  errors; infrastructure failures remain distinct and never become an availability result or implied success.

## Use Case and Contract

- **Actor/trigger:** a consumer explicitly checks a declared/registered Feature at a protected entry point or within
  already-running work. The consumer supplies its existing authenticated snapshot or an explicit anonymous input.
- **Input validation:** use TASK-00061's FeatureName grammar unchanged. The evaluator accepts the two package-owned
  principal types or null, not an arbitrary name-only authority implementation, raw grant list, or authentication
  request. Consumers resolve authentication before evaluation when the underlying use case requires it.
- **Reads:** obtain current stored Feature status and Permission binding on every explicit call. Resolve the bound
  Permission by its stored ID so an existing name-based helper cannot silently substitute a recreated Permission.
  Do not cache the Feature row/result in the evaluator or accept a previously fetched Feature as the decision source.
- **Reference validity:** a known Feature whose Permission no longer exists is invalid at every status, including
  ON and OFF. Raise a distinguishable broken-binding error; do not short-circuit into a normal boolean that masks
  the invalid configuration, mutate status, recreate the Permission, or use DEFAULT_FEATURE_PERMISSION.
- **Unknown name:** a syntactically valid name with no stored Feature raises an unknown-Feature error. It is neither
  ON nor ordinary unavailability and never triggers provisioning. Invalid names fail the shared value validation.
- **OFF:** a valid OFF Feature returns false for all callers, including privileged Users and Agents.
- **PREVIEW:** a valid PREVIEW Feature requires the bound Permission identity in the existing principal snapshot.
  Users have Role-derived Permissions and Agents have direct Permissions under unchanged tier/assignment rules.
  Anonymous input returns false. No Role name, super-admin status, or package-defined Permission name bypasses this.
- **ON:** a valid ON Feature returns true, including for anonymous input, meaning only that the Feature restriction
  is removed. It does not authorize the underlying action, bypass required authentication, or grant management rights.
- **Failures:** ordinary unavailable is false; unknown Feature, broken binding, and operational repository failure
  remain distinguishable. Keep exceptions within the applicable aggregate boundary and use existing lookup conventions
  where appropriate. Concrete public names are implementation design, not an excuse to collapse these outcomes.
  Consumers may conceal broken-reference details with a 404 like OFF while retaining internal diagnostics; the package
  returns no HTTP response and does not reclassify outages as 404.
- **Side effects/messages:** evaluation is a read-only service/use case. No Command, domain event, aggregate mutation,
  transaction commit, grant, repair, provisioning, or implicit audit pipeline applies. Safe consumer diagnostics are
  separate from state-changing package behavior.

## Freshness and Authority Lifecycle

Each explicit check must observe current stored Feature settings through the authoritative read contract, including
a second check in the same request or a subsequent job in the same worker process. State changes are observed after
they become visible to that read; no atomic coordination with arbitrary later work is promised. Consumer adapters
must avoid stale ORM identity-map results, not merely expose a method that the evaluator calls repeatedly.

Keep the supplied principal snapshot unchanged. Both existing principal implementations expose PrincipalPermission
entries with stable IDs; compare those IDs, not their captured/current display names. No new authentication flow,
per-check grant refresh, or process-lifetime principal cache is added. Fresh Feature reads do not promise immediate
revocation/grant refresh inside the existing snapshot lifetime. Protected Permissions remain human-only under the
existing policy; this TASK changes neither assignment eligibility nor reclassification rules.

OFF affects subsequent explicit checks. It does not schedule more checks, stop a job already admitted, roll back
prior effects, or cancel work automatically. A job with no additional check can finish; if it checks again, that
check uses current Feature settings. No shared cache, invalidation system, locking protocol, or cancellation service.

      Feature/Permission repository failures never grant access. Assert the approved distinction between ordinary
      false, unknown-Feature error, broken-binding error, and operational failure; no default or on-demand provisioning.
- [x] Using the same evaluator and principal instance, change stored status between calls and observe the new decision.
      Also rebind a PREVIEW Feature to a different Permission and prove the next check uses the new binding against
      the unchanged captured Permission IDs. No request-local Feature snapshot/result is reused.
- [x] Consecutive simulated worker jobs do not retain Feature settings; repeated checks do not call authentication
      providers or refresh principal membership. Demonstrate the documented snapshot lifetime rather than promising
      immediate reflection of grant/revocation changes within it.
- [x] Controlled in-flight scenarios distinguish already-admitted work finishing without another check from a later
      explicit check denying after OFF. Tests do not claim real worker cancellation or atomic admission/execution.

- [x] Record the public evaluator/error contract, fresh-read repository requirements, and any compatibility/schema
