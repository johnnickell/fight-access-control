# Register a pending User atomically with default Roles

## What to Build

Deliver the complete consumer-admitted registration journey in [TICKET-00022](../tickets/00022-TICKET.md)
as one independently reviewable package slice. A distinct, serializable registration command and registered
Application handler create a canonical-email-unique pending User with the **entire** consumer-configured default
Role set, a one-time activation grant, encrypted registration-origin recoverable delivery and audit in a single
`TransactionalUnitOfWork`. Publish a safe registration success fact only after confirmed commit. The handler
receives a nonempty list of `RoleName` strings at construction, resolves current Role identities by name for each
registration, and never accepts Roles or authority from a public command. Keep existing private invitations and
activation behavior intact; reuse [TASK-00073](00073-TASK.md)'s durable origin and provider contract.

Creation-time Role assignments require authoritative reference validation/fencing shared with Role removal
through transaction completion; today's separate `replaceRoleAssignments()` path alone does not establish this
for `UserRepository::add()`. Reconcile the current Domain repository/aggregate contract and faithful test
persistence without a post-commit assignment step or production Adapter. Exact DTO names, audit category,
repository method shapes and any justified safe operational query are design choices inside this TASK, not an
invitation to add a public existence lookup or reopen the approved product boundaries.

## Execution Order

These are dependent assignments inside **one** TASK/PR; any SUBTASK coordination belongs in its ignored `.runs/`
space after separate implementation authorization.

1. Establish a typed, safe registration command/event and creation-time User/Role repository contract. Specify how
   configured names are validated, current Roles are resolved, and references are fenced against concurrent
   deletion or replacement within the same transaction as User insertion. Preserve atomic canonical-email claims.
2. Implement the end-to-end pending identity, complete Role set, grant/delivery and audit commit with a
   registration-origin activation. Dispatch success after commit and reuse recoverable provider scheduling rather
   than making email sending transactional; keep private invitation creation untouched.
3. Prove the actual registration → provider → one-time activation path and competing-write/failure outcomes with
   controlled package-port tests. Align current public schemas, consumer composition guidance and verification
   evidence. No consumer page, transport, installation setting or template is part of this TASK.

## Acceptance Criteria

All [TICKET-00022 use cases, security requirements and evidence](../tickets/00022-TICKET.md) and the settled
[admission](../wayfinder/tickets/WF-026-registration-admission-and-default-authority.md) and
[public boundary](../wayfinder/tickets/WF-028-public-registration-safety-boundary.md) apply. Check a criterion
only when its observable evidence is recorded.

- [ ] C1 — The new registered command/handler is separate from private invitation, carries only necessary
      identity/email and safe provenance, never caller-selected Roles or raw credentials/passwords. Validate
      immutable message round trips and missing/invalid fields; actor provenance must not falsely imply an
      authenticated User or itself authorize an anonymous request. Consumers choose if/where to expose it; no
      package enablement check, public response, challenge or throttle.
- [ ] C2 — Handler construction requires nonempty valid `RoleName` defaults; at registration, resolve every name
      against the authoritative Role repository. A missing/invalid name, `ROLE_SUPER_ADMIN`, conflicting stored
      identity or concurrent Role removal/replacement rejects the whole operation. No global `ROLE_USER`
      requirement or blanket prohibition on other consumer Roles. The pending User has **all** configured Role
      IDs, no partial set; changing consumer defaults later does not reconfigure previously registered Users.
- [ ] C3 — Under one transaction/fence, successful creation commits pending User, complete Role assignments,
      activation grant, encrypted registration-origin delivery and audit, or none. Extend/clarify the
      creation-time `UserRepository::add()` contract (or an equivalent Domain-owned creation contract) so all
      initial Role references stay authoritative through commit under the removal fence. Prove both winner orders
      for registration versus Role removal/replacement and atomic rejection on failed reference validation,
      persistence write or commit. Do not use a separate post-commit Role-assignment command or unsafe preflight.
- [ ] C4 — Preserve canonical-email/reservation uniqueness at the authoritative insert. Claimed pending, active,
      disabled and deleted emails, plus live reserved destinations, reject as they do for invitation; no new User,
      grant, delivery or successful-registration audit/fact, no duplicate activation email and **no** package
      generic success. Do not add an email-availability query or convert a duplicate into recovery of an existing
      User.
- [ ] C5 — Publish a safe registration-specific success fact only after complete commit; pre-commit failures
      dispatch safe `CommandFailedEvent` and rethrow the original exception under current package conventions.
      A post-commit publication/provider fault does not undo committed state or establish that mail arrived.
      Demonstrate rolled-back versus committed uncertain outcomes and response loss by authoritative reads;
      due-work discovery/restart still reaches the provider with registration origin and delivery ID.
- [ ] C6 — Show a registration-origin provider invocation, pending User with its default Roles, and existing
      one-time activation of that **same** User, without claiming delivery alone makes it active. Verify normal
      private invitation behavior remains private, other credential purposes unaffected, and existing protected
      `GetUserById`/delivery-status reads suffice unless a new protected, read-only query is demonstrably needed.
      No secret or public identity oracle in messages, results, failure evidence or audit.
- [ ] C7 — Update affected public commands/events and generated OpenAPI integration tests, README/CONTEXT,
      credential-delivery/registration composition guide, Unreleased changelog and repository/Role-fence
      obligations. Use current-contract-only [ADR 0011](../adr/0011-pre-v1-current-contract-only.md); document
      consumer-owned storage, mail adapter/templates, public security/response and real race qualification as
      unexecuted integration work, not package proof.
- [ ] C8 — Focused checks and complete `./bin/build` pass in the package runtime with exact owned statement
      coverage, planning/documentation checks and actual warning/skip reporting. Save TASK-owned logs/exit
      receipt and tested-content mapping for independent technical review and applicable nonvisual behavioral
      QA. Controlled package interleavings do not qualify an actual database or consumer runtime.
