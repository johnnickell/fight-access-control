# Register a pending User atomically with default Roles

## What to Build

Deliver the complete consumer-admitted registration journey in [TICKET-00022](../tickets/00022-TICKET.md)
as one independently reviewable package slice. A distinct, serializable registration command and registered
Application handler create a canonical-email-unique pending User with the **entire** consumer-configured default
Role set, a one-time activation grant, encrypted registration-origin recoverable delivery and audit in a single
`TransactionalUnitOfWork`. Publish a safe registration success fact only after confirmed commit. The handler
receives a nonempty list of `RoleName` strings at construction, resolves current Role identities by name for each
registration, and never accepts Roles or authority from a public command. Keep existing private invitations and
activation behavior intact; reuse [TASK-00073](00073-TASK.md)'s durable origin and provider contract.

Creation-time Role assignments require authoritative reference validation/fencing shared with Role removal
through transaction completion; today's separate `replaceRoleAssignments()` path alone does not establish this
for `UserRepository::add()`. Reconcile the current Domain repository/aggregate contract and faithful test
persistence without a post-commit assignment step or production Adapter. Exact DTO names, audit category,
repository method shapes and any justified safe operational query are design choices inside this TASK, not an
invitation to add a public existence lookup or reopen the approved product boundaries.

## Execution Order

These are dependent assignments inside **one** TASK/PR; any SUBTASK coordination belongs in its ignored `.runs/`
space after separate implementation authorization.

1. Establish a typed, safe registration command/event and creation-time User/Role repository contract. Specify how
   configured names are validated, current Roles are resolved, and references are fenced against concurrent
   deletion or replacement within the same transaction as User insertion. Preserve atomic canonical-email claims.
2. Implement the end-to-end pending identity, complete Role set, grant/delivery and audit commit with a
   registration-origin activation. Dispatch success after commit and reuse recoverable provider scheduling rather
   than making email sending transactional; keep private invitation creation untouched.
3. Prove the actual registration → provider → one-time activation path and competing-write/failure outcomes with
   controlled package-port tests. Align current public schemas, consumer composition guidance and verification
   evidence. No consumer page, transport, installation setting or template is part of this TASK.
