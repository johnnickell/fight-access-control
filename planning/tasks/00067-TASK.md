# Retire Features through current-reference guards

## What to Build

Deliver the guarded Feature-deletion path and complete the retained cross-TICKET lifecycle evidence for
[TICKET-00017](../tickets/00017-TICKET.md). An authorized consumer can delete a Feature only when current code and
explicit registrations no longer reference it and its expected revision is still current. Later reintroduction
uses ordinary provisioning to create a new OFF record, not restoration of deleted settings.

## Use Case and Contract

- **Actor/trigger:** an authorized operator retires a Feature after code-reference cleanup has been deployed. Retain
  the released ON record while current references remain; missing from one candidate inventory is not permission
  to delete it. Consumers authorize their management entry points.
- **Input/read:** target the stable Feature ID with its expected revision from the management read model. Resolve its
  immutable name and request complete discovery of current-code Attribute references and explicit registrations
  through TASK-00061's consumer boundary. A saved candidate-release inventory is not current-code evidence.
- **Guard:** reject if either reference source contains the name, regardless of Feature status. Failed/incomplete
  discovery, operational discovery errors, or inability to establish absence reject; do not convert them to an
  empty inventory. A complete successful empty inventory can establish absence within the supplied scope.
- **Mutation:** after successful absence checking, atomically require the target's current identity/revision and remove
  that record under the repository/Unit of Work contract. Stale deletion, including a status/Permission edit during
  discovery, leaves the newer record intact. Reject unknown targets; never retarget a reused name to a new identity.
- **Events/failure:** publish a removal fact only after commit. Discovery/validation/write rejection publishes no
  success; pre-commit failure rolls back the deletion. Post-commit publication failure cannot restore the record or
  imply rollback. Preserve existing package failure-event/rethrow behavior, not the credential-only exception.
- **Retry:** remove remaining references, deploy the cleanup, refresh state, and retry. Do not remove code or registry
  entries automatically or delete catalog records merely because one deployment omitted them.
- **Name reuse:** deletion reserves no historical name. Later registration and TASK-00062 provisioning allocate a new
  identity OFF, revision 1, with the current default Permission. Neither old status, binding, revision, nor identity
  is resurrected. An old delete/update request cannot affect the reintroduced record.
- **Reference aftermath:** removing the last Feature reference may permit later Permission removal, subject to all
  remaining Role/Agent/Feature guards. Feature deletion itself neither deletes a Permission nor changes grants.
- **Runtime:** lookup between deletion and valid reprovisioning uses TASK-00064's unknown-Feature error, never ON or
  on-demand provisioning. Successful preparation validation of a fresh OFF record is not runtime availability.

## Guarantee and Consumer Boundary

This is a current-reference check plus atomic stored-record revision protection, not coordination with arbitrary
concurrent/future deployments. Scanner results cannot promise another version will not become active afterward.
Consumers must identify actual current code and report incomplete coverage honestly; the package cannot certify
undisclosed running code or privileged direct SQL. Preserve the accepted error behavior if overlap/drift leaves a
runtime reference without a record.

Do not introduce cross-deployment locks, historical release ledgers, name tombstones, future-name reservations,
interactive locks, cancellation, or a new approval protocol. Production discovery, UI/confirmation, caller protection,
persistence/schema, deployment wiring, and actual consumer qualification remain outside this library implementation.
Commands perform deletion; discovery/read operations do not mutate or publish domain events. No new HTTP/CLI surface.

## Acceptance Criteria

- [ ] Attribute-only references, registration-only references, both together, and references at every status reject
      deletion. Removing only one reference source is insufficient while the other remains.
- [ ] Failed/incomplete discovery and operational scanner failure leave the record intact with no removal success.
      A complete current-code inventory proving absence permits deletion; candidate-code absence alone does not.
      Controlled fixtures prove contract behavior, not completeness of any real application scan.
- [ ] Unknown IDs, invalid expected revisions, stale revisions, and a concurrent edit during discovery reject without
      removing newer state. Repository tests prove the final expected-state write, not just an earlier comparison.
      Old requests cannot delete a newly reintroduced same-name Feature with a different identity.
- [ ] Pre-commit failure preserves the record and emits no removal fact. Successful deletion publishes only after
      commit; publication failure afterward does not undo deletion. No Permission deletion, grant change, or default
      substitution occurs as a deletion side effect.

      reference allows Permission removal only when no other Feature/Role/Agent reference blocks it; exercise the
