Pi harness. A maintainer should be able to select work through `/skill:next`, invoke `/skill:build TASK-NNNNN`,
and have each delegated role consistently apply AccessControl's own planning, runtime, gates and evidence rules.

## Acceptance Criteria

- [ ] **C1 — Routing:** For unimplemented approved work or confirmed implementation defects, the documented default
  is `/skill:build TASK-NNNNN`; an explicit implementation-only request may use `/skill:work TASK-NNNNN`.
  Review, QA, delivery and unresolved-evidence routes remain specific to actual state. Navigation recommends and
  stops, follows Board priority unless the user selects narrower work, and never launches another workflow.
- [ ] **C2 — Intake versus authority:** Guidance distinguishes a Build recommendation from invocation. Explicit
  invocation delegates the provider's defined work, independent review, QA and land sequence, including owned
  commits, non-force push and open-PR publication, without repeated approval for already delegated effects.
  It does not authorize merge, release, deployment, unrelated work or restricted disclosure. Actual missing
  prerequisites still hold the affected action; they are not automatically replaced by a generic approval loop.
- [ ] **C3 — Checkout and security:** Reuse an existing TASK checkout choice; otherwise resolve it before
  implementation. Preserve correction-batch maintainer-brief requirements. Do not infer a brief is available
  or unavailable from its absence in public records, and do not copy restricted criteria into public guidance.
- [ ] **C4 — Target binding:** Document how delegated roles find this target's instructions, planning records,
  `develop`-based feature branch policy, Docker wrappers, canonical gates, completion semantics and evidence
  locations. Provider links resolve from the owning provider; target facts remain local. Preserve canonical
  Review/QA subject identity and independence, Build's shared revision allowance, and existing evidence on resume.
- [ ] **C5 — Contributor consistency:** README, CONTRIBUTING, AGENTS, the project profile and affected standards
  agree about the workflow and its authority. A single invocation can explicitly delegate multiple distinct
  effects; ordinary edits and planning approval alone do not authorize publication. Record the adopted changes
  and retained deviations without a wholesale standards replacement or private filesystem identities.
- [ ] **C6 — Preserved package contracts:** Keep the Domain/Application-only boundary, exact statement coverage,
  existing canonical build and hosted-check policies, OpenAPI testing exception, local run-layout deviation,
  automatic parent completion and signed-library-release controls. No dependency, package API, runtime or
  application-infrastructure migration is introduced.
- [ ] **C7 — Capability truthfulness:** Verify the supplied provider's explicit Build/Next entrypoints and relevant
  harness discovery behavior rather than treating omission from automatic model-selection metadata as absence.
  Document any actual missing setup separately. Do not claim end-to-end Build qualification from documentation,
  enrollment status or source inspection alone; no installation, enrollment or global-setting changes are needed
  without a separately evidenced and authorized setup decision.
- [ ] **C8 — One delivery:** Keep this record, its implementation and generated planning updates on
  `feature/task-00081-agent-os-workflow-alignment` for one PR. Preserve unrelated work and all existing TASK
  priorities/dependencies. Record independent review and applicable QA through normal workflow evidence.
