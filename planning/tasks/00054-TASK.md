## Scenarios and Acceptance Criteria

- [ ] Publish reusable suite contracts and binding instructions in the checkout for consumer persistence/transaction,
      authorization, cipher and sink implementations. "Publish" does not authorize push, tag or package release.
      Use public capability seams; no production Adapter layer or consumer lifecycle replica is introduced.
- [ ] Map all TICKET-00013 D1–D7 items to predecessor focused tests and integrated conformance. Update actual evidence
      references in [TICKET-00014's scenario map](../tickets/00014-TICKET.md#scenario-ownership-and-evidence-traceability),
      retaining outstanding real-consumer proof and migration/cohort/restore ownership there. A named test is not a pass.
- [ ] Every retained public/direct rotation/revocation path atomically cancels/fences delivery without key/sink access.
      Race these actual paths against admission and in-flight invocation, then query original operation status: retired
      credentials never become successor secrets or valid old acknowledgements. Preserve terminal revocation,
      authentication fencing and revocation's existing publication behavior.
- [ ] Interleave caller revocation, Permission removal, delegation expiry, destination reassignment and credential
      retirement before claim, between claim/admission, before materialization, during invocation and before outcome.
      Test final trusted-time checks, earliest deadlines, late admission commit returns, revoke/regrant ABA and shared
      writer participation. Unconfirmed admission never materializes; already admitted late effects stay fixed-sink inert.
- [ ] Delay predecessor before and after sink acceptance of successor; rotate across slots and reassign slots across
      Agents/caller scopes. Equal opaque operation IDs have distinct delivery IDs. Swap each receipt/idempotency binding
      field and bytes; mismatches reject. Identical retries preserve receipt and selection. Sink arrival/pointer never
      selects usable credentials; exact current package/destination authority governs selection even before the sink
      learns the new package revision.
- [ ] Exercise lost sink response, committed/rolled-back admission/outcome uncertainty, restarted discovery and expired
      claim takeover with real package paths. Preserve original bytes/ID and reject stale completion. TASK-00049 owns
      the combined provision/rotation publisher-failure scenario; neither conformance TASK depends on the other or
      substitutes for the delivery recovery tests in TASK-00052.
- [ ] Rewrap and retire pending copies through actual maintenance paths, then inject restored/missing/corrupt key
      access, expiry, delivered-secret loss and replay after cleanup. No envelope fallback, secret reread, automatic
      issuance, revival, deduplication reset or lowered high-water mark. Safe original correlation persists.
- [ ] Test default-only and valid/invalid overrides across discovery, claim/admission, retry, retention and cleanup.
      Bounded existing recovery/status remains available under the new-work capacity policy without mandatory manual
      setup or extra human approval. Storage outage remains explicitly unavailable/indeterminate, not an inferred success.
- [ ] Assert external sink invocation outside every transaction, exact receipt binding, typed sanitized outcomes and
      secret-safe results/events/audit/serialization/debug/failures. Issuance, receipt and old admission grant no current
      enrollment activation, launch or signing authority. Document consumer-bindable fresh activation/use authorization
      proof; do not implement consumer enrollment/broker code or claim package doubles certify it.
- [ ] Run reusable suites against package-controlled behavioral adapters and report exactly which interleavings they
      prove. Document required real database/sink/authority-writer binding, fault injection and consumer execution
      evidence. In-memory success does not prove PostgreSQL atomicity/concurrency, real sink behavior or consumer use
      safety. Real integrations must qualify separately before support/adoption claims; gaps remain explicit.
