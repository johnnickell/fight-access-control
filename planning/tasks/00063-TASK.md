# Validate Feature preparation before activation

## What to Build

Deliver read-only preparation validation for [TICKET-00015](../tickets/00015-TICKET.md), plus reusable contract
scenarios and guidance that let consumers compose declaration, provisioning, and validation without copying the
package's policy into deployment scripts. This is a query/use-case slice, not a standalone testing or docs-only PR.

A complete candidate reference inventory must resolve to valid stored Features and their bound Permission identities
before a consumer activates that code. Validation of a healthy OFF Feature passes preparation: this result says that
required configuration exists, not that anyone may use the Feature or that deployment is authorized.

## Use Case and Contract

- **Actor/trigger:** an authorized consumer deployment checks the intended candidate inventory against the target
  environment's catalog after provisioning, including after retry or recovery from a failed/lost provisioning call.
- **Input:** the complete validated inventory established by TASK-00061 and the consumer-composed authoritative
  Feature/Permission repositories. Validate every unique referenced name; do not silently skip missing members,
  truncate to a default page, or use a stale provisioning result as proof of current stored definitions.
- **Reads:** resolve each referenced Feature and its stored Permission ID. A valid stored OFF, PREVIEW, or ON record
  satisfies preparation regardless of the requesting caller's preview membership. No default Permission is needed
  for this read, and a same-name replacement Permission must not repair a missing bound ID.
- **Output:** a clear successful preparation result or distinguishable invalid/incomplete/error outcome, with safe
  diagnostics identifying unusable references where appropriate. Specify public query/result/error types and any
  affected schema metadata with the implementation. Do not return an HTTP response or an authorization decision.
- **Failures:** missing Feature, broken Permission reference, failed/incomplete discovery, invalid persisted definition,
  and operational repository failure cannot produce a successful preparation result. Distinguish configuration
  failures from infrastructure faults; neither is permission to activate referencing code.
- **Effects/messages:** validation is a query/read-only operation. No Command, aggregate mutation, grant, repair,
  provisioning, commit, domain-event dispatch, or deletion is performed, including on invalid data. Consumers can
  record internal diagnostics without turning validation into a state-changing audit workflow.
- **Consumer action/security:** the deployment owner blocks activation on an unsuccessful result and authorizes its
  setup/read entry points. The package neither activates code nor authenticates the caller. Successful preparation
  does not grant runtime availability, business/action authority, management rights, or release/deployment permission.
- **Guarantee limit:** validation concerns the complete inventory and catalog observed through the supplied contracts.
  It is not an atomic fence against later arbitrary deployments, privileged SQL, or undisclosed running code.
  Reference guards and runtime fail-closed checks remain necessary; no distributed deployment coordinator is added.

## Acceptance Criteria

- [x] A complete candidate inventory with valid OFF/PREVIEW/ON records and existing bound Permission IDs passes
      preparation. A complete empty inventory also passes without default configuration or catalog mutation.
      Test more than one reference so partial validation cannot accidentally pass.
- [x] Any missing Feature, broken binding (including an ON record), invalid definition, failed/incomplete discovery,
      or repository failure prevents success. A resolvable default or same-name/different-ID Permission does not mask
      the broken binding. Diagnostics distinguish unusable configuration from operational failures.
- [x] Validation rereads authoritative catalog state rather than trusting a saved provisioning outcome, and validates
      the complete inventory without pagination loss. Queries never create/repair records, grant authority, commit,

## Implementation and builder verification (revision awaiting independent re-review)

The new `ValidateFeaturePreparation` Query and `ValidateFeaturePreparationHandler` request complete CANDIDATE
references, then read each distinct Feature and its bound Permission ID. The safe `FeaturePreparationResult` reports
`prepared` or ordered name/problem diagnostics (`missing_feature`, `broken_binding`, `invalid_definition`). Incomplete
or wrong-scope discovery and operational storage faults throw, never return success. The query mutates nothing and
performs no transaction/event dispatch; an OFF Feature passes configuration preparation, not availability. The
FeatureRepository read contract calls for malformed persisted definitions to surface `FeatureStateException` rather
than null. These additive PHP types and three opt-in OpenAPI components introduce no endpoint, migration or release
choice. See [integration guidance](../../docs/feature-preparation.md) for consumer obligations and exact limits.
