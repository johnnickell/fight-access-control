# Audit synchronous User security and session operations

## What to Build

Deliver optional explicit atomic audit for RevokeSession and all seven synchronous User operations owned by
[TICKET-00044](../tickets/00044-TICKET.md): activate, login, refresh, logout, changePassword, resetPassword and
confirmEmail. Own synchronous audit constructor wiring and outcome paths together, avoiding duplicated optionality
changes across password/email handler tasks. Use TASK-00122's shared contract, not another model/service redesign.

### Complete Use Cases

| Actor and trigger | Existing operation | Meaningful committed outcome / no-change distinction |
| --- | --- | --- |
| Invited User supplies activation proof and chooses credentials | activate | User activation, grant consumption and authoritative session issuance form one owned outcome, not a record per helper write. |
| User supplies valid login credentials | login | Authoritative authentication/session issuance, retaining throttle/dummy-hash/rehash and coupled User/session authority. |
| Credential holder refreshes an authoritative session | refresh | Successful rotation is meaningful; a benign bounded conflict is no-change. Terminal replay may commit revocation before outward refusal. |
| User logs out with the current refresh credential | logout | Actual session revocation, preserving current credential and no-change/authority rules. |
| User changes a password or completes reset proof | changePassword, resetPassword | Secret-free evidence of committed password/authority/grant/session effects with existing admission and single-use safeguards. |
| User supplies email-change confirmation proof | confirmEmail | Matching User/grant/reservation confirmation and associated authority/session effects commit atomically with enabled evidence. |
| User/admin revokes a non-current managed session | RevokeSession | Self-service and authorized administrative revocation both receive meaningful enabled evidence, with retained target/reason/current-session rules. |

For planning inventory, the seven synchronous method names identify the current AuthenticationService seams;
RevokeSession identifies the corresponding CommandHandler. Follow direct narrower capability owners if TASK-00112
has already replaced that service. Do not retain/recreate a broad facade, pull unrelated dependencies together or
split a new class per helper merely to preserve these current names.

### Behavior and Validation

- Own optional last nullable AuditEvidenceRepository wiring across the actual synchronous owner(s) and the session
  handler, including currently mandatory password/email audit. Omitted/null intentionally disables durable audit;
  configured failure must not silently turn it off. Update directly necessary constructors/named callers, fixtures,
  current message/port contracts and public composition examples coherently.
- Preserve direct trusted actor provenance. Use authoritative authenticated/admitted identity or explicitly
  declared system/anonymous origin appropriate to the actual outcome; never identify a request as authenticated
  solely from a target UserId, worker execution, label or unvalidated credential. No transport/ambient resolver,
  actor wrapper, new account or authorization grant is introduced.
- Preserve business-required actor/target checks. Where attribution is genuinely absent, supply optional typed
  use-case provenance under the accepted policy; with auditing enabled validate it before the first mutation
  requiring evidence, not necessarily before proof/discovery. Disabled/pure no-change execution gains no new
  audit-only input obligation. Actor identity cannot replace actual credential, ownership or administration checks.
- Explicitly add evidence to the actual transaction/connection committing the meaningful User/grant/session state.
  Use typed subject/relationships, trusted actual occurrence time, applicable authoritative revisions and real
  correlation where available. Do not invent a CommandMessage for synchronous calls or serialize raw input/results.
- Retain actual activation/recovery/email grant single-use and reservation checks, current User/session identity,
  authentication-authority versus persistence revisions, expected-state/CAS, refresh rotation/conflict/replay and
  token lifetime/remember semantics. Keep state-based invariants Domain-owned and repository-backed coordination
  with its Application owner, following implemented User transition encapsulation rather than duplicating policy.
- Preserve current-session management prohibition, cross-user administration policy, required administrative reason,
  target/reference/authority checks and self-service behavior for RevokeSession. Audit reasons need explicit safe
  admission; supplying actorId confers no right to revoke someone else's session.
- A benign refresh conflict, missing/invalid/rejected work with no committed change, or helper no-op gets no new
  mutation record. Terminal replay's actually committed session revocation DOES get evidence even if refresh returns
  an outward refusal after commit. Record the committed security transition, not a successful refresh or a durable
  rejected-attempt log. Preserve commit-before-outward-rejection ordering; do not roll back revocation just to throw.
- Concurrent helper resolution that observes a winner's already completed revocation must not manufacture another
  change record. Audit the owning use-case outcome, not every retry/session helper call, bulk row update or claim.
  Shared SessionRevocationService helpers must not independently add records and duplicate lifecycle/password/email
  outcomes. Make actual committed changes observable through cohesive existing boundaries where necessary.
- Enabled audit failure before commit or concurrent losing mutation rolls back required staged work/evidence.
  Preserve uncertain-commit truth, primary failures and ordinary post-commit event/subscriber propagation. Do not
  extend Agent provision/rotation's confirmed-result warning exception to these User operations; committed evidence
  survives later publication failure and does not claim the caller received tokens or notifications.
- Keep raw passwords, activation/reset/email/refresh credentials and returned token material sensitive and
  non-serializable. Exclude secrets, hashes, ciphertext, raw messages/entities, exception diagnostics and unnecessary
  personal data from evidence/context/public responses/logs. Bounded context is not automatically public disclosure.
