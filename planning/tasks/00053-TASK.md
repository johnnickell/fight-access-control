# Maintain and retire protected delivery material safely

## What to Build

Deliver authorized pending-copy rewrapping, key-retirement accounting, retention expiry and bounded cleanup while
preserving original delivery identity and replay/order defenses. This is slice D approved on 2026-09-27 under
[TICKET-00013](../tickets/00013-TICKET.md), targeting `v0.5.0`.

Implement maintenance transitions, Domain repository selection/write obligations and Application cipher/cleanup
coordination with public consumer capability contracts and tests. Key management and sink implementations remain
consumer-owned; this is not a general key-vault or secret retrieval framework.

## Use Case and Contract

- **Actor/trigger:** a currently authorized maintenance worker rotates wrapping keys, assesses pending-copy references,
  expires retained delivery or performs bounded cleanup. Consumer policy participates in the relevant package-owned
  transaction/fences; possession of a key version, operation ID or maintenance command is not authority.
- **Queries:** bounded secret-free selection/accounting of applicable pending copies and terminal cleanup work.
  Reads do not mutate, commit or emit Domain events. Do not confuse a snapshot count with permission to retire a key
  while another writer can add references; document the shared key-reference/write fence and consumer retirement obligation.
- **Effects:** rewrap preserves plaintext, integrity binding, delivery ID, destination order and lifecycle outcome.
  Expected-state writes cannot resurrect material after concurrent completion/retirement. Expiry/cleanup removes
  recoverable delivery material while retaining safe correlation/tombstones and required deduplication/high-water evidence.
- **Results/events:** sanitized maintenance outcome/accounting, not secret output or a delivery receipt. No new business
  event is required solely for maintenance; any supported fact follows its durable transition. Authentication envelope
  lifetime is independent and cannot supply missing delivery material.

## Acceptance Criteria

- [x] Document cipher representations, typed sanitized transient/permanent/corrupt outcomes, maintenance authorization,
      expected-state writes and key-reference/retirement obligations. Rewrapping exposes no general plaintext handle
      or ordinary serializable secret. Consumers implement key access and actual retirement, not the package.
- [x] Rewrapping pending material preserves original bytes/identity/binding across restart and key version changes.
      Temporary key access failure retains discoverable material/version; restored access permits original delivery.
      Race rewrap against delivery completion, cancellation and expiry: a stale write cannot restore a removed copy.
- [x] Pending-copy accounting includes every retained copy and fences retirement against relevant writers. No key is
      declared safely retired from a stale read or incomplete batch; independent authentication-envelope dependencies
      remain the consumer's responsibility. No production key-vault or physical key-destruction implementation is added.
- [x] Permanent key loss, corrupt/swapped ciphertext and exhausted retention give safe terminal outcomes with no
      raw fallback, authentication-envelope decryption, automatic generation/rotation or revived credential. Revoked
      Agents remain terminal; known-active rotation or ambiguous historical provision requires explicit reconciliation.
- [x] Completion/retirement already removes material through TASK-00050/00051; this maintenance path handles expiry,
      retained copies and cleanup without duplicating those policies. After acknowledged delivery, only safe receipt/
      status lookup is supported. Later sink material loss cannot produce another secret-read facility or enrollment readiness.
- [x] Cleanup preserves scoped operation/canonical version/tombstone evidence and protected-sink deduplication/order
      guarantees. Old operation keys never become new issuance. Delay external calls through cleanup and replay them:
      no retired material recreation, lower high-water mark, stale selection or activation is allowed. Publish consumer
      cleanup capability/conformance obligations; an unsupported sink must fail closed, not silently forget history.
- [x] Document/test finite retention, maintenance batch/work and inert-entry cleanup defaults and optional valid/invalid
      overrides, including recovery windows, key references and TASK-00046/00051 bounds. Cleanup cannot evict required
      safety evidence to meet capacity. Preserve existing recovery/status under new-work capacity rejection; routine
      recovery needs no mandatory configuration or additional human approval.
- [x] Safe output, audit/events, serialization/debug and failures expose no secret/ciphertext/key path/provider detail.
      Sensitive sink effects remain outside every database transaction. Physical sink/key actions cannot be claimed
      atomic with package state; document fail-closed restart/uncertainty handling and prove durable outcomes.
- [x] Focused tests and public maintenance/cleanup contracts cover TICKET-00013 D6/D7 and replay aspects of D4/D5.
      TASK-00054 integrates these with real package rotation/delivery paths; basic maintenance failure/race proof stays
      here. Update consumer guidance and requirement evidence references without claiming real adapter qualification.
