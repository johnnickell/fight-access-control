## Scenarios and Acceptance Criteria

- [ ] Expose reusable observable conformance for scoped uniqueness, request/version binding, same-key resolution,
      transactional issuance/authority participation, destination reservation and safe status/results. Consumers bind
      their repositories/transaction and authorization adapters through public seams; no production Adapter namespace
      or consumer-specific SQL/Permission names are introduced. Generate fixture IDs with the owning factories.
- [ ] For **both provision and rotation**, commit issuance while success and failure publishers fail, terminate the
      initiating caller and do not retry it. Restart the actual package discovery/claim/admission/delivery path with
      an authorized worker; pending work and abandoned expired claims reach a receipt-confirmed delivery outcome.
      No event or initiating-process memory is required. Exactly one issuance/audit fact remains; external retry stays
      at-least-once with the same delivery ID/bytes and notification retries retain fact identity.
- [ ] Exercise real provision/rotation-to-status transitions and preserve the original credential tuple across
      delivery, retirement and terminal outcomes. Confirmed issuance metadata/warning alone cannot mean confirmed
      delivery, enrollment activation or permission to launch. Document/run the consumer-bindable obligation for
      fresh activation/use authority without implementing consumer enrollment or claiming a receipt grants permission.
- [ ] Reuse and extend TASK-00046/00048's committed-versus-rolled-back uncertain-commit fixtures and response-loss
      restart tests through public paths; retain distinct pre-commit failure, indeterminate and confirmed-warning
      outcomes. Same-key recovery must not use events, a fresh key or a consumer copy of lifecycle policy.
- [ ] Conformance covers current authority on retries/status/discovery, explicit worker delegation to original scope,
      cross-scope equal operation IDs and shared-slot reservation order. Interleave issuance with authority/lifecycle
      writers and prove one fenced winner. Capability failure rolls back; no nested transaction or cached external
      allow decision can pass. TICKET-00013 owns sink/admission race policy and its focused suite.
- [ ] Run default-only and valid/invalid-override scenarios across provision and rotation. New-work capacity
      rejection/deferral remains clearly retryable while authorized existing status, same-key resolution and worker
      recovery function under the capacity policy. Recovery stays bounded without extra human approval or required
      manual configuration. This does not claim reads succeed during an unavailable database outage.
- [ ] Retained/tombstoned operation keys do not become fresh issuance after expiry/cleanup. Unknown canonical versions
      deny; existing-version equality/conflict stays stable. TICKET-00014 retains ownership of cross-version rollout,
      incompatible-writer and restoration qualification rather than treating this current-contract proof as migration proof.
- [ ] Reusable assertions reject secret/ciphertext/key-path/provider-error exposure in safe results, events, audit,
      serialization, warnings, debug and failures. Sensitive invocation reaches only the bound protected destination;
      no raw-return or authentication-envelope recovery fallback is exercised as a compatibility path.
- [ ] Map each TICKET-00012 I1–I7 item to focused predecessor tests and these integration/conformance scenarios; update
      [TICKET-00014's scenario map](../tickets/00014-TICKET.md#scenario-ownership-and-evidence-traceability) with actual
      test/receipt references and outstanding consumer evidence. Do not mark a requirement proven solely because the
      test name exists or the harness is wired.
- [ ] Run the suites against package-controlled behavioral adapters as appropriate and document real consumer binding
      instructions, fault injection and required authority-writer participation. Clearly label package evidence versus
      real adapter/database/sink evidence. In-memory success is not PostgreSQL atomicity, uniqueness or concurrency
      qualification, nor a consumer activation/launch qualification. Preserve failures and gaps honestly.
