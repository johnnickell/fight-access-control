# Save the reason for administrative session revocation

## What to Build

When an authorized administrator successfully revokes another user's session with audit enabled, retain the exact trimmed explanation in the audit record. Keep the existing 1–500 character limit. Administrators are expected not to enter secrets; do not scan, classify, truncate, or replace the explanation. The maintainer approved this scope for repair. Normal priority; no known blockers.

## Reproduction and ownership

On v0.10.1 (`57a693e3`) and clean `develop` (`917e13ae`), `RevokeSessionHandler` requires a reason for cross-user revocation, but `AuditSessionRevocation` stores only the session ID and before/after revisions. The existing in-memory handler test supplies `Compromised device`, verifies revocation and the administrative audit write, and explicitly asserts that the explanation is absent from the serialized record. The expected result is one committed record that reads back that exact explanation. Source and test inspection establish the omission; the focused test run timed out in Docker setup, so no fresh runtime result is claimed.

[TASK-00006](00006-TASK.md) originally required durable reasons. [TASK-00122](00122-TASK.md) (PR #198) introduced the typed audit contract that dropped the explanation; [TASK-00127](00127-TASK.md) (PR #231) owns the completed optional session audit work. This TASK owns the repair and supersedes the free-text exclusion only for administrative session revocation.

## Scope and effects

- Existing `RevokeSession` command only. Preserve target, current-session, ownership and cross-user authorization checks. No new query, permission, event or event payload field.
- Write the reason with existing administrative audit facts in the same transaction as the session mutation. Update typed audit readback and its affected documentation. Do not add reasons to self-service, logout or replay audit facts.
- No backfill, compatibility reader, consumer storage changes, release or deployment.

## Acceptance Criteria

- [ ] An authorized cross-user revocation with audit enabled commits the session change and exactly one administrative audit record. Serializing and reading back the evidence preserves the exact trimmed reason, including a valid 500-character Unicode reason. The success event contains no reason.
- [ ] Missing, blank or over-limit reasons, an unauthorized actor, current-session rejection and a lost concurrent write leave no new revocation audit record. Audit write failure rolls back the revocation. Audit-disabled and self-service behavior remain unchanged.

## Verification

- Add and observe one failing regression in `RevokeSessionHandlerTest`: submit `  Compromised device  ` in the existing in-memory scenario and assert `Compromised device` on readback of the committed evidence. Confirm the failure is the missing reason before changing production code.
- Run focused handler and audit contract tests with `./bin/phpunit`, then `./bin/planning-check`, `./bin/documentation-check`, `git diff --check` and `./bin/build`. Hand verified implementation to independent Review and QA.

Tests cover exact trimmed readback, the 500-character Unicode boundary, no reason in the success event or other session audit actions, and rejection and rollback paths.
