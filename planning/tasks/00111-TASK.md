# Make User transitions own authentication-authority revisions

## What to Build

Deliver the aggregate-encapsulation slice of [TICKET-00035](../tickets/00035-TICKET.md). Remove the caller protocol
of changing User business state and separately incrementing authentication-authority revision. Keep every current
security/atomicity guarantee. Normally one Domain/Application/test/docs PR; AuthenticationService decomposition
is explicitly separate in TASK-00112.

### Actors, Messages and Effects

Existing synchronous activation/login/password/email-confirmation callers obtain a complete User successor from
meaningful Domain operations. Existing safe token/results and UserActivated/UserLoggedIn/password/email facts are
unchanged. Grant consumption, session cancellation/revocation, audit and token issuance retain their existing
transaction and post-commit owners; revision encapsulation creates no additional event or authority grant.

### Concrete Caller Contract

Before: clone User, call changePassword(hash, time), then advanceAuthenticationAuthorityRevision().
After: clone User and call changePassword(hash, time); the related version/revision changes are internal.
Successful login still needs a meaningful authentication transition even without rehash. Preserve its required
serialization instead of deleting the revision write or adding a generic touch/flags API.

## Acceptance Criteria

- [ ] Activation, password change/reset and email confirmation internally advance their authentication-authority
  revision exactly once, with authenticationVersion changes kept distinct and correct for each operation.
- [ ] Successful login advances required authority once whether or not password rehash is needed; stale/throttled/
  invalid/nonactive cases retain current rejection and no-authority-mutation behavior. Design a cohesive Domain
  transition and keep credential verification/orchestration with its actual owner.
- [ ] No owned production caller needs a separate public increment or bookkeeping sequence. Remove the obsolete
  increment API and update callers/fixtures/current examples directly; no compatibility method or automatic double bump.
- [ ] Complete expected-state CAS, coupled User/session insertion, recovery fences, grant single use and actual
  audit/rollback/commit outcomes remain unchanged. Repository enforcement is not replaced by aggregate methods.
- [ ] Tests prove exact counters, rejected-state immutability, login/reset winners, lifecycle changes, stale rehash,
  no-rehash login and late audit/revocation failures through observable persisted results rather than the old call graph.
- [ ] Sensitive synchronous inputs, redacted failure evidence and post-commit publication outcomes remain intact;
  no secret-bearing message, generic persistence facade, new grant or exactly-once promise is introduced.
- [ ] Current composition/docs/Unreleased notes, focused domain/use-case/race checks, complete full gate/exact
  coverage/local receipt and independent Review/applicable QA cover the implemented contract.
