# Reject expired invitation delivery retries before mutation

## What to Build

Repair package-owned `RetryInvitationDelivery` admission so an authorized consumer can retry failed delivery only
while the current activation grant is usable. Read an injected clock inside the existing transaction, before the
retry transition, complete-state CAS and audit write. At `now >= expiresAt`, reject without changing persisted
state or publishing a retry-request fact. An expired invitation needs explicit **resend**, which creates fresh
activation authority and a fresh delivery generation; retry must never issue or extend a credential.

This is one regression-first standalone bug PR, not a delivery redesign. John approved H1–H3 and selected the main
checkout in the Build invocation (`1. approved 2. main`). The task became ready-for-agent with no local blockers and
was then in-progress for the authorized Work implementation and commit. Independent Review ACCEPT and behavioral
QA PASS now complete package acceptance; see the closeout below. Publication is separately authorized through Land;
no merge, release, Agent OS edit or dependency adoption is authorized.

**Priority/dependencies:** consumer-blocking repair, ordered before optional v1 self-registration TASK-00073–00075
without changing those records. No unfinished local prerequisite. Agent OS **TASK-00042** is an external consumer
reference, not AccessControl TASK-00042 or a `blocked_by` edge. Local live/archive search found no existing open

## Diagnosis and Reproduction

- Reported consumer baseline: `johnnickell/fight-access-control` **v0.5.0**, source
  `46ffcf75f1e14dbc5b58a5049e05a600ce5cf8a0`. The local tag resolves to that commit.
- Inspected checkout: clean `develop` at `7357662e0429e61c1f751c003550511dfd1d0106`. `git diff` from the reported
  source through this head is empty for `src/` and `tests/`; the defect remains in current implementation.
- `RetryInvitationDeliveryHandler::handle()` loads latest-by-User inside `commitTransactional()`, calls
  `ActivationGrant::requestDeliveryRetry()`, persists through `replace()`, and adds
  `user.invitation_delivery.retry_requested`. It has no clock dependency or time check.
- `CredentialDelivery::requestRetry()` requires `RETRY_PENDING` and recoverable material only. It changes status to
  `PENDING`, resets due time to the previous attempt time, and preserves delivery identity/history. The aggregate
  advances revision. `ActivationGrant::isUsableAt()` already expresses issued authority and strict `at < expiresAt`.
- `InvitationDeliveryRetryRequested` publishes after commit. The optional `InvitationDeliverySubscriber` dispatches
  `DeliverUserInvitation`; that handler's clock-aware claim rejects expired work. Common's synchronous dispatcher
  can therefore throw `EventDispatchFailed` **after retry state and audit have committed**.

### Messages, queries and effects

- **Actor/trigger:** consumer-authorized inviter/administrator explicitly requests recovery of a failed invitation.
- **Command:** unchanged `RetryInvitationDelivery(actorId, userId)`, void handler. No caller-supplied timestamp,
  delivery ID or expected revision is added; the command targets the current generation at execution.
- **Queries:** existing `FindInvitationDeliveryStatus` / `FindCredentialDeliveryStatus` remain advisory, secret-free
  reads. No new query, status value, endpoint or OpenAPI payload change.
- **Success:** same grant/credential hash/expiry and same delivery ID (provider idempotency identity); retry-pending
  becomes pending, revision advances once, existing due-time/history rules remain, one retry-request audit commits,
  then `InvitationDeliveryRetryRequested` publishes. A return does not establish delivery or account activation.
- **Expected rejection:** reuse public
  `Fight\AccessControl\Domain\AccessControl\ActivationGrant\Exception\ActivationDeliveryNotRetryableException`.
  Accepted expiry text: `The activation delivery work is no longer retryable.` Consumers map the class, not parse
  messages. No new expiry-only subtype/reason code; missing and unusable work share a coarse safe category.
  Existing concurrent-change rejection stays the same type with its existing constant message.
- **Failure evidence:** normal `CommandFailedEvent` remains allowed (it is not the retry-request audit/fact).
  Expected rejection contains only the safe command and constant text, never credentials, hashes, ciphertext,
  claim tokens, destination or provider/storage diagnostics. Failure notification must not replace the original
  expected rejection if it throws; see H1. Arbitrary infrastructure-error redaction outside this narrow rejection
  is not redesigned; consumers still sanitize response/log boundaries.
- **No retry-side cleanup:** rejected expired work remains unchanged, potentially still `retry_pending` until
  existing `ExpireInvitationDelivery` cleanup or authorized resend. Retry is not implicit cleanup or resend.
- **Recovery:** unchanged `ResendInvitationDelivery` accepts still-issued expired authority, revokes the predecessor,
  generates a fresh credential/grant/delivery ID and expiry, and atomically audits before publication. It does not
  make consumed/revoked grants resendable. Keep separate cleanup and resend eligibility intact.

## Human Decisions — Ratified

John explicitly approved all three recommendations before implementation on 2026-10-19. The following accepted
semantics supersede the original proposed/pending wording in the diagnostic planning checkpoint:

- **H1 — Failure surface:** accept reuse of the coarse existing not-retryable exception and constant message, rather
  than a new expiry reason/code. Recommend keeping that original throwable primary even when `CommandFailedEvent`
  notification fails (the current catch can mask it). Limit the correction to this handler; do not convert unrelated
  post-commit delivery failures into success, warnings or rollback claims.
- **H2 — Time boundary:** accept admission at one fresh clock sample **after transactional latest-state retrieval**
  and before mutation/CAS, not at request receipt or before entering/waiting for the transaction. A request sampled
  before expiry can cross expiry before commit/subscriber invocation; the existing worker must still reject expired
  claims and preserve committed retry state/audit. This TASK does not guarantee completion before expiry or impose
  a wall-clock-at-commit fence. If stricter commit-time semantics are required, resolve the repository contract
  implications before marking ready, rather than silently widening this repair.
- **H3 — Compatibility:** accept required clock wiring and the resulting breaking-minor classification. Exact tag
  selection/signing/publication remains a later explicit decision; do not silently call this a compatible patch.
