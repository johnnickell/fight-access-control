# Cancel only the identified email-change request

## What to Build

Require `CancelEmailChange` to identify the email-change request being cancelled, using its existing typed
`EmailChangeGrantId` as the request identity. Cancel only that request while it is current and cancellable.
If a newer request exists, reject the old cancellation and leave the newer one untouched.

John approved this exact-ID contract after the pre-v0.9.0 audit. It applies to both self-service and authorized
administrative cancellation. This standalone bug owns the command, owning handler and directly affected
safe-read/caller/schema/docs changes, not a new email-change workflow. Record creation starts no implementation,
publication, release or consumer adoption.

## Traced Reproduction and Evidence Limit

At inspected revision `c2971971c271ecf7020bb9025b3a7e470d75b9a4`,
[CancelEmailChange](../../src/Domain/AccessControl/EmailChangeGrant/Command/CancelEmailChange.php) carries only
actor and target User IDs. Its [handler](../../src/Application/AccessControl/EmailChangeGrant/CommandHandler/CancelEmailChangeHandler.php)
loads the latest grant and checks that grant against the current reservation. Those checks protect state read
at execution, not the request the caller previously reviewed.

Reproduce through public operations during implementation:

1. Create email-change request A for an active User. Capture its request ID and the cancellation intent.
2. End A through a supported terminal transition, then create request B for the same User, including a case
   reusing the same destination address.
3. Submit the delayed cancellation for A.
4. Expected: reject stale A and preserve B's pending reservation, usable grant and delivery state. Current
   actor/target-only dispatch instead selects B, because it cannot carry A's identity.

This is a source-traced scenario, not an executed reproduction. Before repair, add one failing regression that
shows the existing path selecting B, then update it to prove the approved exact-ID rejection. Do not claim a
historical API already promised an ID input it did not have, or report a deployed exploit without evidence.

## Use Cases and Contracts

| Actor and trigger | Commands / Queries / Events | Outcome and expected side effects |
| --- | --- | --- |
| Owner reviews and cancels a current pending change | Current authorized safe status/read; `CancelEmailChange` with exact request ID | Clear only its matching reservation and revoke its grant/delivery; canonical email is unchanged. |
| Admitted administrator cancels the identified target request | Same Command plus existing cross-User admission | Same exact-request behavior and enabled attributable audit; IDs confer no permission. |
| Delayed cancellation names an obsolete or foreign request | Same Command; deliberate safe conflict/refusal | No successor, other User, reservation, grant, delivery or audit mutation. |
| Confirmation, expiry, replacement or another cancellation competes | Existing transition owners and cancellation fact | Preserve the supported serialized/CAS winner; no partial User/grant/audit changes. |
| Commit acknowledgement or publication fails | Existing safe authorized observations, not an invented result journal | Retain uncertainty or committed cancellation truthfully; never retarget/replay against a successor. |

## Scope, Validation and Permissions

- Add the required typed request ID to the public Command, getter and canonical `fromArray()`/`toArray()` contract.
  Validate missing/malformed IDs and update shipped OpenAPI metadata, fixtures, callers and examples directly.
- Compare the supplied ID with the authoritative current grant inside the handler-owned transaction, before any
  cancellation mutation. Preserve existing User/destination/reservation matching and complete-state comparisons.
  A newer request for the same address is still a different request; comparing address alone is insufficient.
- Ensure an authorized caller can obtain the non-secret request identity needed to name the reviewed change
  through an appropriate current safe package read contract. Reuse an existing qualifying read or extend it
  narrowly; do not expose raw grants, secret material or add consumer endpoints.
- Retain current entry authentication/operation/target admission and package self/admin ownership rules. Supplied
  actor, User and request IDs are not authority. Wrong-target IDs must not disclose another User's state.
- Preserve the existing deliberate conflict/refusal semantics for stale, absent and non-cancellable work;
  unknown repository/audit/clock faults remain internal faults. Missing or stale intent must not fall back to
  cancelling the latest generation. Do not add a caller-wide revision requirement or a generic replay engine.
- Keep reservation clear, exact grant revocation and enabled self/admin audit in one transaction. Optional audit
  remains optional; configured audit failure rolls back cancellation. Success facts follow confirmed commit.
- Do not promote an address, revoke unrelated sessions, recall external mail, erase accepted notification history
  or require a functioning provider. This TASK is independent of TASK-00185's notification participation.
- Preserve pre-v1 current-contract-only policy: update consumers' documented obligations without compatibility
  defaults, aliases, old actor/target-only overloads or migration/backfill machinery.
