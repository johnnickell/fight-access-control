## Use Cases and Contract

| Actor/trigger | Operation | Observable outcome and effects |
| --- | --- | --- |
| An authorized operator prepares a Feature ahead of code | Create with validated name and existing Permission ID | Persist a unique new identity OFF at revision 1; publish its creation fact after commit. Reuse provisioning's model/reference rules; no code registration, grant, or Permission creation is required or implied. |
| An authorized operator opens or refreshes management | Read by Feature ID or list a page of Features; reuse existing Permission-choice reads | Return identity/name, status, stored Permission ID, available display information, explicit binding validity, and revision. Reads neither mutate nor commit nor emit domain events. |
| An authorized operator selects a status | Change status with expected revision | Atomically check current revision and persist a real change with revision +1, publishing its fact after commit. Name and binding are unchanged. |
| An authorized operator selects a Permission | Change binding with expected revision and selected existing ID | Atomically preserve reference integrity, update the binding with revision +1, and publish its fact after commit. Do not change shared Permission definitions or principal grants. |
| An operator encounters stale data or broken binding | Refresh; retry an authorized edit using current revision and a valid selection | Stale attempts do not overwrite newer state; a valid rebinding repairs the stored reference through the ordinary operation without default substitution. |

Operation labels identify intent rather than finalized PHP names. Follow existing immutable message/handler contracts,
round-trip validation, Domain repository ownership, Unit of Work, and post-commit event/failure-rethrow conventions.
No credential-operation-specific publication exception applies. A thrown publication fault after commit is not rollback.

## Validation, Revision, and Read Semantics

- Creation uses the shared immutable unique FeatureName and an existing Permission ID; starts OFF at revision 1.
  No rename, aliases, direct PREVIEW/ON creation, grant side effect, or required prior registry entry. Extend all
  creation/reconstruction paths, including provisioning, consistently for the revision contract. Existing records'
  settings and revisions survive repeat provisioning; no default-based reset or hidden repair.
- Read by ID and list using the existing Pagination/ResultSet conventions. Preserve the requested page and expose
  enough state for an edit without requiring the caller to infer revisions or Permission identity from labels.
  Unknown Feature reads fail under normal lookup conventions rather than constructing an empty editable record.
- If a binding is broken, retain its stored ID, expose an explicit missing-binding indicator and no fabricated
  Permission label/identity. Management reads must remain useful for authorized recovery without reusing the runtime
  evaluator's throwing contract as the read model. No default substitution, automatic grants, or runtime access verdict.
- One shared positive revision governs status and Permission edits. Real changes advance it by one; idempotent valid
  updates do not. Require current expected revision even for a would-be no-op, so a stale edit cannot claim success.
  The final write/no-op validation boundary must preserve expected state, not merely compare in an earlier read.
- Reject unknown targets, invalid names/statuses/revisions, duplicate creation, stale state, and unresolved selected
  Permissions without partial change or success facts. Check authoritative Permission validity and the reference
  fence; a no-op cannot bypass required checks. Broken-binding recovery validates the new selected ID, not a default.
- Any currently defined Permission, including protected ones, can be selected. Binding is not membership and adds no
  tier/assignment bypass or promotion restriction. Coordinate creation/rebinding with TASK-00065's removal guard so
  conflicting writes cannot leave an invalid reference.
- All status selections remain supported. ON-to-PREVIEW/OFF requires warning and confirmation in the consumer UI.
  Cancellation invokes no mutation; stale rejection requires refresh and renewed confirmation if the transition still
  leaves ON. This is consumer interaction guidance, not a package confirmation token or extra approval service.
- Consumers protect every read/write entry point and select their management policy. The testing Permission itself
  grants no management authority; no hard-coded SUPER_ADMIN_ONLY requirement or single-administrator invariant.
