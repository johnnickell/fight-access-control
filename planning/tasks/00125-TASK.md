# Audit password-reset requests, delivery and expiry

## What to Build

Deliver optional explicit atomic audit for RequestPasswordReset, DeliverPasswordReset and ExpirePasswordResetDelivery
and their corresponding handlers under [TICKET-00044](../tickets/00044-TICKET.md). Preserve public concealment and
current credential delivery/recovery while recording meaningful committed outcomes with TASK-00122's typed contract.

### Actors, Messages and Effects

- Deliberately anonymous public reset requests may explicitly establish AnonymousId, never an authenticated target
  User or a fallback for absent provenance. Trusted delivery callers retain original admitted attribution; genuinely
  autonomous expiry may use explicit SystemId. An actor ID grants no policy or target authority.
- Own the three handlers' optional constructors, necessary typed Command/provenance/current round-trip changes,
  caller/worker composition, fixtures/assertions and directly affected docs/examples. Synchronous changePassword
  and resetPassword belong exclusively to TASK-00127; this task does not duplicate their constructor wiring/audit.
- Existing password-reset success/failure facts and read-only discovery/status remain. No secret-bearing Command,
  new audit Query, permission grant, transport route or scheduler is introduced.

### Behavior and Validation

- Make audit an optional last nullable repository argument, including formerly mandatory request/delivery writers.
  Omitted/null intentionally disables durable audit; configured evidence failure cannot silently downgrade to no-op.
  Enabled auditing needs attribution before the first mutation requiring evidence, not before a pure eligibility/
  no-change pass. Disabled/no-change execution gains no new audit-only actor requirement; existing required inputs remain.
- Preserve generic public outcome/concealment for unknown, inactive or otherwise ineligible accounts. Do not create
  an outcome record, new lookup failure or account-disclosure channel for a request that intentionally does no work.
- Preserve authoritative User recovery checks, grant replacement/single-use, latest delivery identity, expected-state/
  CAS, due-time/expiry and stale-worker defenses. Add evidence explicitly to the actual transaction that commits the
  eligible request or meaningful delivery/failure/expiry state, not every helper, claim or repository operation.
- Evidence carries typed User/grant/delivery relationships, trusted actual occurrence time, applicable authoritative
  revisions and real message/delivery correlation. Audit only newly committed outcomes; stale, terminal, not-due,
  failed-CAS or other validated no-change branches create no mutation record while retaining validation/fences.
- Keep claim/provider-call/outcome boundaries and current recovery intact. Audit failure aborts required staged
  state/evidence, not an already performed external send. Preserve uncertain commits, primary faults and ordinary
  post-commit propagation; committed evidence remains durable if later notifications fail. No universal replay or
  durable rejected-attempt store follows from correlation or failure evidence.
- Exclude reset credentials, tokens, hashes, ciphertext, email/provider/raw message/entity payloads, diagnostic
  exceptions and unnecessary personal data. Apply bounded action-specific safe context/reason admission, not a
  string/regex presumed secret-free. Evidence is not automatically public/log response data.
