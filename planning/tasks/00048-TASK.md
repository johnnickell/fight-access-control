# Rotate an Agent through a recoverable operation

## What to Build

Replace raw-return rotation with one authorized, operation-correlated credential successor and atomically cancelled/
fenced predecessor delivery. Retrying the original request/key resolves that successor even though its predecessor
is no longer current. This is slice C approved on 2026-09-27 under [TICKET-00012](../tickets/00012-TICKET.md), targeting
[EPIC-00009](../epics/00009-EPIC.md)'s `v0.5.0` replacement. John approved the concrete TICKET-00013 dependencies
on 2026-09-27; the former missing-information hold is now an ordinary dependency wait.

## Use Case and Contract

- **Actor/trigger:** an authenticated maintainer requests a new rotation with a fresh scoped operation key, target
  Agent and expected credential ID/revision, or retries that same original request after response loss.
- **Validation/authority:** use TASK-00046's trusted caller scope, package canonical request, current authorization,
  original-scope delegation and destination reservation fences. New rotation checks current predecessor inside the
  mutation transaction; authorized same-key resolution reads its recorded outcome instead of repeating that check.
- **Mutation:** one package Unit of Work commits successor Agent authority, new credential/authentication envelope,
  operation binding, separately protected delivery material/ID, destination write version, safe audit and predecessor
  delivery cancellation/fence. Every collaborator shares the transactional connection; no outer/nested transaction.
- **Results/events:** safe confirmed metadata with a typed sanitized publication warning when post-commit publication
  fails. Pre-commit failure and indeterminate commit remain distinct. Rotation fact follows confirmed commit only;
  retry does not issue/generate/audit again. Issuance grants neither delivery confirmation nor activation/launch authority.
- **Reads:** TASK-00047 owns public status Queries. Rotation/service resolution must work independently of a caller
  performing an extra query. Original operations continue identifying their own retired credential, not a newer secret.

## Acceptance Criteria

- [x] Replace/remove or explicitly reject the old raw-return rotation signature without inventing operation identity,
      expected predecessor, destination or authority. The new path retains one active credential, immediate retirement,
      terminal Agent revocation and the existing authentication nonce/current-authority race guarantees.
- [x] A normal authorized rotation commits one successor revision and one audit fact, pending delivery with its own
      immutable delivery ID and reserved destination order, and exact predecessor cancellation atomically. No live
      effect depends on successful event delivery, sink access or decrypting retired delivery material.
- [x] Original response loss plus service/caller restart resolves the original successor using the unchanged
      predecessor request. Different requests under that key conflict; new keys with stale predecessor reject. Races
      between identical keys, conflicting keys and different keys against one predecessor have one authoritative winner.
- [x] Wrong caller/scope, revoked authorization, expired delegation and denied/reassigned destination reject both new
      rotation and retries without leaking other-scope existence. New rotation reserves slot order across operations,
      Agents/scopes and slot reassignment; same-key resolution retains the original reservation and delivery identity.
- [x] Capability, cancellation, audit, encryption and persistence failures leave no partial successor, operation,
      delivery, reservation or audit. Inject both committed and rolled-back uncertain commits; report indeterminate,
      then reconcile authoritative storage with the original key rather than assume rollback or automatically reissue.
- [x] Confirmed commit plus publisher failure returns typed sanitized metadata/warning for rotation, even if failure
      publication also faults. No success publication before commit and no duplicate mutation/audit/fact on retry.
      Revocation/AuthenticationService/unrelated handlers retain their own publication behavior.
- [x] Exercise the real package cancellation seam against pending and admitted predecessor delivery, including races
      before admission and during an admitted call. Retired work cannot newly admit or stale-acknowledge/activate;
      already-admitted fixed-sink effects obey TICKET-00013's inert-staging rules, not a cross-system rollback claim.
      TICKET-00013 retains ownership of all other lifecycle entry-point implementation and its conformance coverage.
- [x] Apply finite documented defaults and optional valid overrides from TASK-00046. New-work capacity exhaustion
      gives a clear retryable rejection/deferral without blocking same-key resolution; tombstones and unknown canonical
      versions cannot become new rotation. No manual configuration/extra human approval is added for routine recovery.
- [x] No raw/ciphertext credential or unsafe exception/provider/key detail in results, serialization, debug, audit,
      events or warnings. Original issuance and current retirement/delivery state remain separate; metadata/receipt
      never implies delivery, enrollment activation or launch permission.
- [x] Focused Domain/Application tests prove TICKET-00012 I1–I7 for rotation and integration with atomic cancellation.
      Keep these tests with the slice. TASK-00049 owns reusable cross-path and no-caller scheduler proof, not deferred
      basic rotation failure tests. Update public API/composition documentation and owning acceptance references.
