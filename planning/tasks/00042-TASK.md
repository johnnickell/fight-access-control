# Reserve Super Admin Role identity and preserve User Role changes

## What to Build

Reserve the exact `ROLE_SUPER_ADMIN` name for the authoritative managed Role across custom creation, rename,
reconstruction, assignment, and effective-principal resolution. Remove actor-only authorization dependencies from
custom-Role lifecycle and User Role-assignment handlers while preserving ordinary User Role behavior. The
custom-Role membership handlers still use `RoleAdministrationAuthorization` until [TASK-00043](00043-TASK.md)
removes their final dependency.

## Use Case and Effects

| Actor and trigger | Commands / queries | Events | Effect and result |
| --- | --- | --- | --- |
| A consumer creates, renames, or removes a custom Role | `CreateCustomRole`, `RenameCustomRole`, `RemoveCustomRole`; existing Role reads | Existing custom-Role Events on real changes | Exact reserved-name creation/rename fails; ordinary custom-Role lifecycle continues and managed Roles stay runtime-immutable. |
| A consumer assigns or removes a User Role | `AssignRoleToUser`, `RemoveRoleFromUser`; existing User/Role reads | `RoleAssignedToUser`, `RoleRemovedFromUser` after real commits | The managed Super Admin Role follows ordinary association, revision, reference, and no-op behavior, including assignment to a pending User for bootstrap. |
| A User authenticates and receives effective authority | Existing principal resolution | N/A | A custom or inconsistent Role cannot appear as managed `ROLE_SUPER_ADMIN`; only active Users authenticate under existing lifecycle policy. |

## Permissions, Validation, and Compatibility

- The managed flag and exact name together identify the designated Role; no Role ID, duplicate name, stale managed
  definition, or adapter-supplied custom Role qualifies by itself. Invalid reconstruction or assignment fails closed
  without persistence change or success Event.
- The application builder owns caller checks for all Role lifecycle and User Role command entry points, including
  no-ops, and decides assignment/removal authority separately, confirmation, audit, last-admin protection, and
  recovery. Actor IDs in existing Commands remain provenance only. The package adds no named Permission check.
- Remove `RoleAdministrationAuthorization` from create/rename/remove handlers and
  `UserRoleAssignmentAdministrationAuthorization` from assign/remove handlers. Retain the Role administration
  interface only while membership handlers still consume it; [TASK-00043](00043-TASK.md) owns its final removal.
  Ownership-sensitive session, email-change, and invitation checks stay in place.
- Preserve User Role expected revisions, authoritative Role references, transaction rollback, safe failure evidence,
  post-commit success Events, and storage on pending, active, disabled, or deleted Users. This is a breaking pre-1.0
  constructor/composition change, so update maintained consumer guidance and changelog without claiming adoption.

## Acceptance Criteria

- [ ] Custom Role creation, rename, and reconstruction reject exact `ROLE_SUPER_ADMIN` impersonation; inconsistent
      stored Role identity cannot elevate a User through assignment or principal reconstruction.
- [ ] Ordinary User Role assign/remove, pending-User Super Admin bootstrap, revisions, no-ops, rollback, and event
      ordering retain their existing behavior; active-only authentication remains intact.
- [ ] Custom-Role lifecycle and User Role handlers no longer invoke actor-only authorization ports. Narrow
      ownership-sensitive ports remain, and the still-needed custom-Role membership port is left for TASK-00043.
- [ ] Focused package tests cover both accepted and rejected Role/User paths, including stale Role references and
      safe failure outcomes.
