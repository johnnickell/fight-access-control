# Declare and register Feature references

## What to Build

Deliver the complete portable declaration path for [TICKET-00015](../tickets/00015-TICKET.md): a developer can attach
one Feature name to a method or register a programmatic reference, and a consumer can supply a validated combined
inventory without depending on a framework, database, or filesystem scanner.

John approved this slice and the initial **method-only, nonrepeatable Attribute**. One method declaration names one
Feature. This is independently reviewable metadata/registration behavior, not a layer-only aggregate foundation.
The stored Feature model and provisioning operation belong to [TASK-00062](00062-TASK.md).

## Use Case and Contract

- **Actor/trigger:** a developer declares a gated method or a supported programmatic check; consumer build/deployment
  composition gathers references for the intended code.
- **Input:** Attribute names and explicit programmatic names use one dedicated FeatureName value. Validate 1–128 ASCII
  characters, lowercase letters/digits separated by single hyphens, starting with a letter. Reject rather than trim,
  lowercase, or otherwise normalize. Accept single-letter names and the parent TICKET's examples.
- **Attribute:** native PHP method target only, without repeatability. It carries only the Feature name, never status,
  Permission, defaults, or authorization policy. Do not introduce class-wide gates or multi-name any/all composition.
- **Inventory:** a small immutable reference collection merges discovered names and explicit registrations. Repeated
  references identify one Feature. Validate all supplied names; do not silently discard malformed declarations.
- **Discovery boundary:** represent successful complete discovery distinctly from failure/incompleteness. A complete
  empty inventory is valid; a failed or incomplete scan must not be converted into it. Define the narrow consumer
  discovery/result contract so TASK-00062/00063 and later current-reference deletion can reject an untrusted inventory.
  Candidate-code and current-code inventories must not be treated as interchangeable evidence.
- **Output/effects:** validated name-only metadata and reference inventory, with explicit validation/discovery failure.
  No catalog mutation, Permission lookup/grant, environment access, transaction, domain event, or access decision.
  Commands are N/A: declaration is metadata, not a persistent business mutation. Inventory reads are pure operations,
  not a management query surface.
- **Security:** metadata declares a reference, not enforcement or authority. Consumers supply scanning/composition;
  the package cannot certify an undisclosed codebase or discover a check the developer omitted. All supported checks
  use Attributes or explicit registration; unregistered dynamic checks remain unsupported.

## Acceptance Criteria

- [x] FeatureName accepts the approved examples and boundaries, including lengths 1 and 128; rejects length 0/129,
      leading digits, uppercase, non-ASCII, whitespace, underscores, repeated/trailing hyphens, and normalization traps.
- [x] Executable PHP reflection fixtures instantiate a valid method Attribute and reject wrong targets and repeated
      applications. The public declaration exposes only the validated name. Tests exercise native behavior rather
      than merely matching source text.
- [x] Combined discovered/explicit references deduplicate by validated name, preserve distinct names, and reject
      invalid input rather than dropping it. Neither the Attribute nor inventory embeds operational Feature settings.
- [x] Contract tests distinguish complete empty/nonempty discovery from failed/incomplete discovery and prevent those
      failures being represented as a successful empty inventory. Document the consumer's completeness obligation;
      controlled fixtures do not prove a real scanner found every running-code reference.
- [x] Public contract guidance demonstrates both declaration paths and inventory composition, the method-only scope,
      validation failures, candidate/current discovery distinction, and the absence of runtime enforcement.
- [x] Domain/Application placement satisfies the package boundary. Namespaces, accessors, and result/error types are
      recorded with the implemented contract; no production Adapter layer, scanner, persistence, or framework import.
- [x] Focused behavior tests and the complete package gate pass with exact production statement coverage. Record
      local evidence and independent review before marking done; this planning approval is not executed evidence.

## Implemented contract and evidence

- Domain `Feature/FeatureName` extends the public Common ValueObject and rejects invalid raw input without
  normalization; `FeatureNameException` and `FeatureDiscoveryException` live under the Domain Feature exception
  namespace. No stored Feature model is introduced.
- Application `Feature/Attribute/RequiresFeature` is native method-only, nonrepeatable metadata with only
  `getName(): FeatureName`. Native reflection fixtures prove target and multiplicity validation; direct method
  invocation proves that metadata does not enforce access.
- Application `FeatureReferences` accepts typed names, validates raw registrations through `fromStrings()`,
  deduplicates, and merges without mutating inputs. `getNames()` exposes validated names only.
- Application `FeatureReferenceScope` separates `CANDIDATE` and `CURRENT`. The consumer-owned
  `Feature/Service/FeatureReferenceDiscovery::discover()` returns `FeatureDiscoveryResult`: only

  partial data. `getReferences(requiredScope)` rejects both unavailable results and wrong-scope use. Completeness,
