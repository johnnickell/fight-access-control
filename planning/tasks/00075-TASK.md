# Recover pending registrations with authorized correction and reissue

## What to Build

Deliver both administrator recovery variants in [TICKET-00023](../tickets/00023-TICKET.md) as one complete,
independently reviewable package slice. When a User is still pending from a registration, an authorized
administrator may correct a wrong email or reissue fresh one-time activation after expiry at the **same** email.
Both variants retain the same User ID and exact assigned Role set, invalidate predecessor activation authority,
commit new registration-origin encrypted recoverable delivery and audit atomically, and publish a safe recovery
fact only after commit. Wrong-address correction must respect canonical-email claims and live reservations;
same-email reissue must not become an anonymous retry or a duplicate registration.

Use a distinct registration-recovery operation and an explicit package authorization boundary for the
administrator/target, in addition to consumer-protected dispatch. The existing `CorrectPendingInvitation` path
remains invitation-specific and must reject registration-origin work. Reuse the immutable origin/provider
contract from [TASK-00073](00073-TASK.md) and the pending User created by
[TASK-00074](00074-TASK.md); do not reassign newly configured default Roles or create a second User. Exact command
shape, administrator authorization port and any justified protected query are design choices inside this TASK.

## Execution Order

These assignments remain inside **one** TASK/PR; any SUBTASK coordination belongs under this TASK's ignored
`.runs/` space only after separate implementation authorization.

1. Design the distinct command/authorization seam and transaction-validated eligibility for the two variants.
   Check current pending registration origin, actor authority, destination claims, grant generation and expiry;
   existing protected `GetUserById`/delivery-status reads can support operator inspection unless another
   secret-free, read-only query is justified.
2. Implement an all-or-nothing replacement of current User email **only when corrected**, predecessor authority,
   fresh registration-origin grant/delivery and audit. Fence against competing activation, delivery, resend,
   recovery, lifecycle and address-reservation writers. Keep private-invitation correction and deleted-to-pending
   restoration separate.
3. Prove both variants with package-port end-to-end tests through delivery and eventual one-time activation,
   including controlled competing writes/failure/restart paths. Align public contracts, consumer obligations and
   final EPIC behavior evidence without claiming real consumer qualification.

## Acceptance Criteria

The complete [TICKET-00023 use cases, safety requirements and acceptance evidence](../tickets/00023-TICKET.md)
and [WF-027 recovery decisions](../wayfinder/tickets/WF-027-registration-delivery-origin.md) apply. Record
executable evidence for each criterion before checking it off.

- [ ] C1 — A distinct registered command/handler checks administrator authorization for the exact target inside
      the trusted operation, separately from supplied actor identity/provenance. Consumers must also protect every
      exposed dispatch/query path; no caller possessing an address or delivery identity gains recovery authority.
      Validate identity/destination/required command data and safe serialization. A query, if added, is protected,
      read-only and secret-free; no public address-availability probe or anonymous recovery.
- [ ] C2 — Wrong-address correction changes only the pending User's canonical destination/normal revision data,
      not ID, Roles, account state or unrelated authority. It validates an authoritative *registration-origin*
      predecessor and target destination, rejecting claimed canonical email/live reservation. In the same
      transaction revoke/replace predecessor activation, stage encrypted registration-origin successor delivery
      and audit the action. Successful provider invocation targets the corrected address after commit.
- [ ] C3 — At exact expiry or later, an eligible pending registration can receive fresh activation at its **same**
      email with the same User and Role set, without a canonical-email rewrite, second User or invalid retry of an
      expired token. A same-email request before expiry rejects. The old token/grant/delivery cannot activate or
      send as current work after replacement; resend/retry/restart retain registration origin and stable delivery
      idempotency per generation. An old delivered/terminal delivery does not itself imply activation.
- [ ] C4 — Reject absent, active, disabled or deleted Users, private-invitation origin, unauthorized actor,
      stale/mismatched generation, inconsistent User/grant/destination and colliding destinations without partial
      writes or success fact. `CorrectPendingInvitation` stays invitation-specific; deleted-to-pending restoration
      is a new private-invitation journey even if the old User was registered. Recovery never reapplies configured
      default Roles or allows a duplicate public registration to reclaim an existing identity.
- [ ] C5 — Prove both winner orders in deterministic competing schedules: recovery versus activation, resend,
      wrong-address correction, another recovery, delete/restore and address-reservation writer; include delayed
      provider delivered/retry/permanent outcomes. Use complete-state expected writes and authoritative
      revalidation through transaction completion; stale losers cannot override a successor, clear an unrelated
      reservation, revive a token or lose any original Role. All failed writes/commit roll back User,
      predecessor/successor and audit together.
- [ ] C6 — Resolve response loss and both uncertain-commit outcomes from persisted current state, never inferred
      rollback or a second success fact. Safe recovery event follows confirmed commit, failure notification
      retains normal original-throwable rethrow semantics, and post-commit publication/provider failure neither
      undoes committed recovery nor guarantees exactly-once delivery. No credential, ciphertext or sensitive
      provider error leaks into command/event/query/audit/failure evidence.
- [ ] C7 — Verify public message/query/event round trips, handler registration, generated OpenAPI integration,
      focused/full behavior tests, affected README/CONTEXT/consumer recovery and mail composition guidance,
      Unreleased changelog and repository/authorization contract changes. Explicitly distinguish package
      modeled concurrency/protected provider proof from unexecuted real consumer DB/authorization, template
      configuration, restart and public-abuse qualification. Apply current-contract-only
      [ADR 0011](../adr/0011-pre-v1-current-contract-only.md), without old-reader or migration routes.
- [ ] C8 — Run focused checks and the complete `./bin/build` with exact owned production statement coverage,
