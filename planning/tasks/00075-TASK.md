# Recover pending registrations with authorized correction and reissue

## What to Build

Deliver both administrator recovery variants in [TICKET-00023](../tickets/00023-TICKET.md) as one complete,
independently reviewable package slice. When a User is still pending from a registration, an authorized
administrator may correct a wrong email or reissue fresh one-time activation after expiry at the **same** email.
Both variants retain the same User ID and exact assigned Role set, invalidate predecessor activation authority,
commit new registration-origin encrypted recoverable delivery and audit atomically, and publish a safe recovery
fact only after commit. Wrong-address correction must respect canonical-email claims and live reservations;
same-email reissue must not become an anonymous retry or a duplicate registration.

Use a distinct registration-recovery operation and an explicit package authorization boundary for the
administrator/target, in addition to consumer-protected dispatch. The existing `CorrectPendingInvitation` path
remains invitation-specific and must reject registration-origin work. Reuse the immutable origin/provider
contract from [TASK-00073](00073-TASK.md) and the pending User created by
[TASK-00074](00074-TASK.md); do not reassign newly configured default Roles or create a second User. Exact command
shape, administrator authorization port and any justified protected query are design choices inside this TASK.

## Execution Order

These assignments remain inside **one** TASK/PR; any SUBTASK coordination belongs under this TASK's ignored
`.runs/` space only after separate implementation authorization.

1. Design the distinct command/authorization seam and transaction-validated eligibility for the two variants.
   Check current pending registration origin, actor authority, destination claims, grant generation and expiry;
   existing protected `GetUserById`/delivery-status reads can support operator inspection unless another
   secret-free, read-only query is justified.
2. Implement an all-or-nothing replacement of current User email **only when corrected**, predecessor authority,
   fresh registration-origin grant/delivery and audit. Fence against competing activation, delivery, resend,
   recovery, lifecycle and address-reservation writers. Keep private-invitation correction and deleted-to-pending
   restoration separate.
3. Prove both variants with package-port end-to-end tests through delivery and eventual one-time activation,
   including controlled competing writes/failure/restart paths. Align public contracts, consumer obligations and
   final EPIC behavior evidence without claiming real consumer qualification.
