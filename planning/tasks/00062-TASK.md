# Provision registered Features without resetting choices

## What to Build

Deliver the Domain/Application provisioning path for [TICKET-00015](../tickets/00015-TICKET.md): consume a complete
reference inventory, resolve a supplied default Permission when needed, and create only missing Features OFF without
resetting any existing record. Include the Feature model, Domain repository contracts, Application operation,
messages/results/events as applicable, tests, and consumer integration guidance needed for this complete path.

John approved **one atomic database transaction per provisioning pass**. All new records from a pass commit together;
a failure before commit rolls back that pass. Retry rechecks authoritative stored state, including after a
post-commit publication failure. This is not a partial-batch recovery protocol, durable outbox, or activation receipt.

## Use Case and Contract

- **Actor/trigger:** an authorized consumer deployment/setup invokes provisioning before referencing code becomes
  active, or repeats a prior pass after a failure/lost outcome.
- **Input:** TASK-00061's validated, complete inventory and optional consumer-supplied default Permission name.
  `DEFAULT_FEATURE_PERMISSION` is consumer configuration; package code reads no environment variables. Validate and
  resolve the default only if a missing Feature needs creation. An unused default is not required.
- **Model:** Feature identity extends the package's shared identity primitive; name is unique among current records
  and immutable. Every new Feature starts `OFF = 'off'` with exactly one existing Permission ID. Also define stable
  enum cases `PREVIEW = 'preview'` and `ON = 'on'` without implementing management or runtime availability here.
  Support faithful reconstruction of stored status/binding so provisioning cannot reset existing records.
- **Persistence:** Domain-owned repository lookup and atomic creation obligations enforce name uniqueness and valid
  Permission references, using the existing transactional boundary. Keep repositories beside the aggregate; do not
  introduce an Application Store/save port. A stale preflight existence check is not a uniqueness guarantee.
- **Default resolution:** when any name is missing, resolve the configured canonical Permission name to its current
  ID. Any defined tier is eligible, including SUPER_ADMIN_ONLY; referencing it creates no grant, Role membership,
  Agent assignment, or new tier-promotion restriction. Missing/invalid/unresolved required configuration rejects
  creation without an incomplete record.
- **Transaction:** the package operation owns one Unit of Work for the pass's catalog writes. Validate discovery
  completeness before accepting the inventory. Required configuration, persistence, and reference failures before
  commit leave none of this pass's new records committed. Existing records and other writers' commits are not undone.
- **Preservation/concurrency:** never replace an existing same-name record to make provisioning succeed. Changed
  defaults, repeated references, and concurrent creation must preserve the winning identity/status/binding. A
  uniqueness conflict can reject the entire pass for a fresh caller retry; no unbounded internal retry is required.
  Recheck state on retry rather than replaying a cached list of missing names.
- **Existing invalid data:** provisioning does not repair, rebind, or reset existing definitions. TASK-00063 validates
  their suitability before activation; completion of this creation operation alone must not imply activation-ready.
- **Result/events:** distinguish provisioning completion/failure from readiness. Publish creation facts only after
  the entire pass commits, one per new record; unchanged records produce no creation success event. Use normal
  package CommandFailedEvent/failure-rethrow behavior, not EPIC-00009's credential-only warning exception. If
  publication fails after commit, persisted records remain committed; retry treats them as existing and does not
  recreate records or replay creation facts for unchanged records. Do not promise reliable event delivery.
- **Retry/uncertainty:** a thrown call or missing event is not proof of rollback. A fresh pass consults storage;
  previously committed records remain intact, and a rolled-back pass can create its missing records later. No
  operation-key ledger, tombstone, or distributed coordination system is needed for create-if-absent provisioning.
- **Security:** consumers authorize deployment/setup entry points. The testing Permission confers neither setup nor
  management authority; no package-mandated administrator Permission is introduced.

## Acceptance Criteria

Checked items began as builder evidence; independent technical review and behavioral QA now accept the implementation snapshot recorded below.

- [x] Model tests prove OFF creation, stable identity, required Permission-ID binding, immutable validated name, exact
      status serialization, and faithful reconstruction without introducing a runtime evaluator or management API.
- [x] Real package provisioning against controlled repositories creates exactly the missing registered names using
      existing Permission IDs; duplicates resolve to one record. No Permission, grant, or unregistered Feature is
      created. Existing OFF/PREVIEW/ON records retain their identities and settings.
- [x] Required absent/malformed/unresolvable defaults reject creation; the no-creation case succeeds without an unused
      default. ADMIN_SAFE and protected defaults both work without changing assignment/tier policy.
- [x] Invalid/incomplete discovery rejects rather than appearing as an empty successful pass. A genuinely complete
      empty inventory produces no new records or creation events and needs no default.
- [x] Failure on a later insertion rolls back every new record from the pass, including earlier successful insertions.
      Configuration/reference/persistence failures before commit publish no creation facts. Assert stored outcomes,
      not only collaborator calls; no-op passes write no records and publish no creation facts.
- [x] Duplicate-name conflict and concurrent-winner scenarios preserve the winner's identity/status/Permission and
      roll back the losing pass's other inserts. A fresh retry rereads and creates only remaining missing records.
      Repository contracts specify the shared Permission reference fence needed with TICKET-00017 removal paths.
- [x] Success facts occur only after the single confirmed commit. Publication failure after commit leaves all records
      intact; retry does not duplicate them or emit new creation facts for existing records. Distinguish confirmed
      rollback from outcome uncertainty; missing notifications do not establish either rollback or activation readiness.
- [x] Changing the default or rebuilding the service before retry does not overwrite existing choices. A name absent
      after prior deletion can receive a new identity OFF with the current default; the real guarded-deletion sequence
      remains composed evidence under TICKET-00017, not proven by a seeded absent-record fixture.
- [x] Document the public invocation/results/errors, atomic pass boundary, caller retry on conflict, event failure
      limits, repository uniqueness/reference obligations, and preparation-validation step. Assess affected public
      schema/compatibility contracts without adding endpoints or choosing a release version.
- [x] Focused unit/behavior tests cover the complete path now, not deferred to TASK-00063. Full package verification
      and independent review are recorded before completion, including exact production statement coverage.
