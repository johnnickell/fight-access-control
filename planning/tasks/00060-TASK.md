# Align OpenAPI credential-delivery components with released contracts

## Outcome

Correct the package-owned reusable delivery schemas so consumers can describe released credential-delivery
messages and safe results without contradicting their canonical serialization. One bounded repair PR owns this
outcome; runtime delivery behavior does not change.

John approved the proposed scope and standalone record creation on 2026-09-28, then authorized an isolated planning
worktree, commit, push, and planning-only PR to `develop`. Implementation and its checkout selection, implementation
publication, and release execution remain separately authorized. Recommended priority is before the next release;
the required portfolio order is 60, without reprioritizing existing work. No implementation blockers are assigned.

## Scope

In scope:

- Correct `Fight.AccessControl.InvitationDeliveryStatus.status` and preserve its existing success-envelope reference.
- Add reusable components for `DeliverPasswordReset`, `FindCredentialDeliveryStatus`, `FindDueCredentialDeliveries`,
  `CredentialDeliveryStatusView`, and `DueCredentialDelivery`.
- Describe the actual due-work list shape and applicable optional typed success envelopes under existing catalog
  conventions. The due-work handler returns `list<DueCredentialDelivery>`, not a paginated Fight Common ResultSet.
- Add generated OpenAPI contract integration tests to the main PHPUnit suite and normal build/CI pipeline, including
  the necessary test-discovery and quality configuration. These validate shipped library contracts, not tooling text.
- Update [composition guidance](../../docs/openapi-composition.md), changelog, and release/composition qualification
  to use the contract checks without making release certification their only execution path. Align CONTEXT if
  clarification is needed; retain the package-owned values/consumer-owned transport boundary.

Out of scope: endpoints, security schemes, package-owned complete OpenAPI documents, runtime authorization or
delivery changes, production dependencies on OpenAPI, unrelated catalog cleanup, unreleased Agent work, generated
clients, and publication.

[ADR 0008](../adr/0008-openapi-payload-contract.md) already requires components for every public Domain Command and
Query and every safe query result. This repair follows that decision, including worker-facing contracts; no
worker-only exclusion is adopted. Consumers choose whether and where to expose those values over HTTP.

## Validation and permissions

Match canonical serialization, required fields, nullability, formats, supported purposes, positive discovery
limits, and safe failure classifications. Reject obsolete and unknown statuses. Missing required fields and
invalid typed values must not be described as valid inputs. Do not add constraints merely by analogy with other
schemas; inspect the owning contract and accepted package format conventions.

`DeliverPasswordReset` exports `actor_id`, `user_id`, and `password_reset_delivery_id`.
`FindCredentialDeliveryStatus` exports `purpose` and `delivery_id`; `FindDueCredentialDeliveries` exports `at` and
`limit`. The operational view exports `purpose`, `delivery_id`, `user_id`, `revision`, `status`, `due_at`,
`expires_at`, `attempt_count`, `last_attempt_at`, `last_outcome_at`, and `last_failure`; its last three values can
be null. Due-work items export `purpose`, `delivery_id`, `user_id`, `due_at`, `revision`, and `status`.

Safe-result schemas must expose no credential material. Consumer entry-point authorization remains unchanged;
reusable schemas grant no access and introduce no permission names or HTTP policy.
