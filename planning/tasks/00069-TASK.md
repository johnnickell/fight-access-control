# Rename an Agent atomically with typed provenance

## What to Build

Deliver one complete framework-neutral name-only update path for
[TICKET-00018](../tickets/00018-TICKET.md): an Agent-owned rename transition, a Domain repository write contract
that cannot replace unrelated authority, an immutable generic `UpdateAgent` command with typed initiating User-or-Agent
identity, its Application handler and safe committed-name result, and a name-changed fact containing target and typed
initiator. The initiating identity is provenance, **not authorization**. An authenticated Agent's self-service tool
and a separately authorized administrative consumer entry point will reuse this command later; neither is built here.

The handler validates the name through `AgentName::fromString()` (trim, nonempty, at most 120 characters), requires
the current target to remain `ACTIVE` at the write, and commits a real name change atomically before publishing its
fact. No expected old name, name revision or uniqueness rule: the last committed name wins. An unchanged normalized
name returns successfully without persistence write, timestamp change or success fact. Return only `{agent_id, name,
changed}` from the committed normalized outcome, without a compensating read; do not expose credentials or assigned
Permissions. Command/event messages follow the existing immutable serialization and failure-event/rethrow contract.

Coordinate name-only writes with existing Agent lifecycle, Permission-assignment and current operation/correlation
fences. A stale aggregate or direct repository call must not overwrite credentials/Permissions, revive a revoked
Agent, bypass current required repository admission or claim a successful no-op on a no-longer-`ACTIVE` target. Do
not misuse `AgentRepository::replace()`'s credential-retirement semantics or create a generic whole-Agent update.
Design a minimal safe repository method and aggregate transition consistent with the existing Agent boundary;
consumer production persistence remains outside this TASK.

## Acceptance Criteria

- [ ] A consumer-authorized User or Agent can supply a typed initiating identity and a chosen Agent target through
      the generic command. A real rename changes only the normalized name and `updatedAt`, commits atomically, then
      publishes a name-changed fact with the same target and initiator. Actor identity alone grants no authority;
      document protection of **all** consumer command-dispatch entry points, including direct bus calls.
- [ ] An unchanged normalized name yields `{agent_id, name, changed: false}` with no write, timestamp change or
      success fact. A committed change yields the normalized name and `changed: true` without a compensating read.
      Invalid name and missing/revoked or changed-to-inactive target reject with no write or success fact.
- [ ] Controlled competing writes show last committed rename wins without a new name revision or lost credential/
      Permission updates. Revocation wins over a stale rename; the repository's direct name-write contract also
      rejects unsafe successors or stale authority without resurrecting an Agent. Preserve existing operation
      correlation and shared fences rather than bypassing them in the name path.
- [ ] Pre-commit persistence failure rolls back. Post-commit event-publication failure is reported as failure,
      without pretending the rename rolled back or promising event delivery. Ordinary command failure-event/rethrow
      semantics apply; the credential-provision/rotation warning exception does **not** extend to this handler.
- [ ] Meaningful unit coverage for every new/modified class plus only a few focused transaction/interleaving
      composition checks prove these effects and the event ordering. Do not add a duplicate exhaustive suite or
      treat in-memory interleavings as real consumer database concurrency qualification.
- [ ] Update the affected current-contract and consumer-integration guidance (including entry-point authorization
      and name-only persistence obligations). Record focused checks, `./bin/planning-check`, and the canonical
      `./bin/build` with exact production-statement coverage and a durable local gate receipt for independent review.
