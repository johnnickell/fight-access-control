# Carry activation-delivery origin through provider recovery

## What to Build

Deliver the entire [TICKET-00021](../tickets/00021-TICKET.md) current-contract origin path as one independently
reviewable package slice. A non-sensitive, immutable registration-versus-private-invitation origin must survive the
activation grant's recoverable delivery lifecycle and reach the consumer-owned `CredentialDeliveryProvider` on
immediate delivery, claim/retry, restart discovery, resend and replacement. Keep `activation` as the credential
purpose; do not select copy from an event, route or historical User identity. Make existing private invitation,
correction and deleted-to-pending restore explicitly private; a resend preserves its current generation's origin.
Registration-origin issuance is exercised through the package grant/provider contract in this TASK; the actual
consumer-admitted registration command and full journey belong to [TICKET-00022](../tickets/00022-TICKET.md).

Carry the origin through Domain aggregate creation/hydration, authoritative repository state/expected-state writes,
Application provider invocation and affected public contracts without adding a production Adapter, package template,
HTTP response or new public registration command here. Existing `FindInvitationDeliveryStatus` and due discovery may
be reused; no new public identity query is required. This is a feature: implement testable code and then meaningful
behavioral tests, with no speculative bug/regression-first claim.

## Execution Order

These are dependency-ordered assignments inside **one** TASK/PR, not layer-only TASKs or separate authorization.
Coordination belongs in this TASK's ignored `.runs/` directory during authorized execution.

1. Specify the current origin/value and immutable provider contract at the activation delivery boundary. Trace
   creation and restoration of every current activation issuer and provider invoker; keep reset/email-change
   delivery behavior unchanged. Update in-memory persistence doubles to model current validation/CAS faithfully.
2. Wire both origins through issuance, claim, provider invocation, retry, due discovery after restart, resend and
   replacement. Make private-invitation correction reject registration-origin work; restore-to-pending creates a
   new private-invitation generation even for a previously registered User. Preserve current grant ownership,
   revisions, expiry and post-commit behavior.
3. Prove the complete path with controlled package-port tests, align public schema/docs/consumer composition and
   verify the full gate. Keep actual consumer template/SQL qualification explicit and unclaimed.
