# Consistent Authorization Modification

## Problem Statement

Fight applications need Agent Permission, User Role, and custom-Role Permission changes to have one predictable
retry and failure model. The package currently implements those changes through purpose-specific commands, but
their handlers repeat authorization, target and reference lookup, transaction ownership, optimistic-concurrency
checks, persistence replacement, success-event ordering, failure publication, and unchanged exception rethrow.
That repetition makes security rules harder to review and creates several places where equivalent behavior can
drift.

The observable command behavior is already inconsistent. Replacing an Agent's complete Permission set with the
same set is a successful no-op, while granting an already-present Permission, assigning an already-present Role,
revoking an absent Permission, or removing an absent Role fails even though the requested final authority state
has already been reached. A consumer retry can therefore produce a different result based only on which public
command expressed the same desired state.

The package must remove that inconsistency without weakening security. Idempotency cannot bypass actor
authorization, accept missing Users, Agents, Roles, or Permissions, ignore stale expected revisions, hide a
concurrency conflict, publish false success evidence, or introduce a generalized policy engine. Public commands
and events must continue to describe the exact security operation while shared coordination remains internal.

## Solution

Treat every authorization-assignment command as a request for a desired final state. Granting or assigning an
existing membership, revoking or removing an absent membership, and replacing a complete set with the same
identities complete as no-ops. A no-op performs no repository write, advances no authority revision, and publishes
no success event. Complete-set input is normalized as a mathematical set, so order and repeated IDs do not change
the desired result.

Retain the distinct public commands, package-specific authorization ports, aggregate invariants, optimistic-
concurrency boundaries, and purpose-specific success events. Move only repeated Application coordination into
final package-internal modules. Missing identities or definitions, denied actors, stale expected revisions,
persistence conflicts, and invalid Domain state remain hard failures that dispatch `CommandFailedEvent` and
rethrow the original exception unchanged.

The highest verification seam invokes each public command handler with deterministic repositories,
authorization ports, Unit of Work, clock, and event dispatcher, then observes committed authority state,
revision movement, persistence writes, commit and event ordering, no-op retries, success events, failure events,
and exception identity. One shared behavioral matrix applies those outcomes to Agent Permission, User Role, and
custom-Role Permission changes without requiring the three aggregates to use identical mutation mechanics.

## User Stories

1. As an API consumer, I want authorization updates to be safe to retry, so that a lost response does not force me
   to discover whether the first request already succeeded.
2. As an Agent administrator, I want granting an already-assigned Permission to complete as a no-op, so that a retry
   does not turn an already-correct Agent into an error response.
3. As an Agent administrator, I want revoking an already-absent Permission to complete as a no-op, so that repeated
   cleanup remains safe.
4. As an Agent administrator, I want replacing Permissions with the current set to complete as a no-op, so that
   declarative synchronization does not create artificial authority changes.
5. As a User administrator, I want assigning an already-assigned Role to complete as a no-op, so that repeated
   desired-state updates remain safe.
6. As a User administrator, I want removing an already-absent Role to complete as a no-op, so that cleanup does not
   depend on a prior read.
7. As a Role administrator, I want granting an already-contained Permission to a custom Role to complete as a no-op,
   so that retries do not fail after the first change commits.
8. As a Role administrator, I want revoking an already-absent Permission from a custom Role to complete as a no-op,
   so that declarative Role correction remains safe.
9. As a synchronization author, I want duplicate and reordered IDs normalized as one set, so that representation
   details do not manufacture an authority change.
10. As an operator, I want no-op retries to avoid persistence writes, so that storage activity represents real
    authority changes.
11. As a security reviewer, I want no-op retries to leave assignment revisions unchanged, so that every revision
    increase proves an actual authority transition.
12. As an event consumer, I want no success event for a no-op, so that downstream audit and projection work does not
    record a change that never happened.
13. As an event consumer, I want each real change to keep its purpose-specific success event, so that Agent grants,
    User assignments, and Role membership changes remain distinguishable.
14. As a security reviewer, I want actor authorization checked before accepting a no-op, so that idempotency cannot
    reveal or manipulate authority without permission.
15. As a security reviewer, I want target and referenced definitions validated before accepting a no-op, so that an
    already-absent relationship cannot hide a deleted or unknown User, Agent, Role, or Permission.
16. As a concurrent administrator, I want stale expected revisions rejected even when my submitted set matches the
    latest state, so that an explicit concurrency fence is never bypassed accidentally.
17. As a concurrent administrator, I want compare-and-replace loss to fail without partial change, so that one
    operation cannot overwrite another administrator's authority update.
18. As a package maintainer, I want all three mutation families to use the same transaction and failure rules, so
    that those security guarantees are reviewed and tested from one behavioral contract.
19. As a package maintainer, I want aggregate roots to retain their own state transitions, so that shared
    coordination does not reconstruct Agent, User, or Role internals.
20. As a package consumer, I want purpose-specific public commands retained, so that application intent remains
    explicit and serializable.
21. As a package consumer, I want shared mutation coordinators closed as internal implementation details, so that I
    do not build integrations against unstable orchestration classes.
22. As an Application author, I want dependency failures to dispatch `CommandFailedEvent` and rethrow the identical
    exception, so that outer error handling receives the original failure.
23. As a Domain author, I want missing identities, invalid definitions, stale authority, and violated invariants to
    continue failing hard, so that retry safety does not become silent error recovery.
24. As a User, I want effective Permissions to continue coming from assigned Roles, so that mutation consistency
    does not introduce a second direct-Permission model for people.
25. As a release owner, I want these semantics settled before `1.0.0`, so that consuming APIs can rely on one
    idempotent authorization-modification contract from the first stable release.

## Implementation Decisions

- Retain distinct public commands for granting, revoking, and replacing Agent Permissions; assigning and removing
  User Roles; and granting and revoking custom-Role Permissions.
- Interpret each command as desired state. Granting or assigning an existing membership and revoking or removing an
  absent membership completes normally as a no-op. Replacing a complete set with the same identities is also a no-op.
- Normalize every complete-set input as a set. Repeated value-equal IDs and input order do not alter the desired
  state or cause a failure, and stored authority remains duplicate-free.
- Perform actor authorization before target resolution or mutation for both real changes and no-ops. Preserve the
  existing Agent Permission, User Role-assignment, and Role-administration authorization ports.
- Resolve the target aggregate and validate every referenced Role or Permission before deciding that the requested
  state is already satisfied. Missing targets and definitions continue to fail hard.
- Check an operation's required expected revision before accepting an exact-set no-op. A stale expected revision
  fails closed even when the submitted set happens to equal the current authoritative set.
- A no-op performs no repository add or replacement, advances no credential, assignment, or other authority
  revision, changes no timestamp, and publishes no purpose-specific success event. The handler completes normally.
- A real change runs inside one `commitTransactional()` boundary, performs one aggregate-owned state transition,
  persists through the applicable Domain repository compare-and-replace operation, and creates one purpose-specific
  success event for post-commit dispatch.
- Dispatch a real change's success event only after the transaction commits. A transaction, persistence,
  concurrency, validation, or authorization failure publishes no success event and retains no partial change.
- Keep the distinct success events for Agent Permission grant, revoke, and replacement; User Role assignment and
  removal; and custom-Role Permission grant and revoke. Do not add one generic authorization-change event or a
  synthetic no-op event.
- Every public handler retains an outer `try`/`catch (Throwable)`, dispatches `CommandFailedEvent` with the original
  command and failure message, and rethrows the same `Throwable` instance unchanged.
- Consolidate repeated Application execution behavior in small final `@internal` concrete coordinators. Do not add
  public coordinator interfaces, a generic aggregate mutation framework, or compatibility promises for internal
  constructors and methods.
- Keep aggregate roots responsible for membership behavior. Shared coordinators may ask an aggregate for the
  desired successor or whether state changed, but they do not manipulate internal collections or reconstruct
  aggregate state.
- Allow Agent, User, and Role aggregates to preserve their established mutable or immutable transition style.
  Behavioral consistency does not require byte-identical implementation or one generic aggregate interface.
- Reuse an internal exact Permission resolver where mutation and principal-resolution flows need the same
  authoritative reference validation. That resolver is shared with PRD-00003 and remains a final `@internal`
  implementation component.
- Preserve the final Permission-reference fence used by Agent and Role changes. A Permission removed after initial
  lookup but before persistence causes the transaction to fail with no partial authority change.
- Preserve User Role-reference validation at the final persistence boundary. A Role that loses authority after
  initial lookup causes assignment or replacement to fail without partial change.
- Users continue to receive effective Permissions through assigned Roles. Changing a User's effective Permissions
  means changing User Role membership or Permission membership on a Role; this PRD does not add direct User
  Permission assignment.
- Keep framework adapters, endpoint policy, transport responses, retries, and error translation consumer-owned.
  Shared command behavior remains independent of synchronous or asynchronous invocation.

## Testing Decisions

- The primary behavioral seam invokes every public authorization-modification handler with deterministic
  repositories, authorization ports, Unit of Work, clock, and event dispatcher, then observes committed state,
  revisions, persistence writes, event ordering, failure evidence, and exception identity.
- Express the primary outcomes as one shared behavioral matrix applied to Agent Permission grant, revoke, and
  replacement; User Role assignment and removal; and custom-Role Permission grant and revoke.
- For every one-item command, prove a real change and an already-satisfied retry. The retry completes normally with
  no persistence write, revision or timestamp movement, or success event.
- For every complete-set operation, prove order independence, duplicate normalization, equal-set no-op behavior,
  empty-set behavior, real replacement, and stale expected-revision failure.
- Prove authorization, target existence, and referenced-definition validation still occur for an apparent no-op.
  A no-op assertion is incomplete if it bypasses those security checks.
- Prove each real change orders work as authorization and authoritative reads, transactional aggregate mutation,
  compare-and-replace persistence, commit, then exact purpose-specific success event.
- Prove final reference-fence loss, compare-and-replace loss, Unit-of-Work failure, repository failure, and event
  dependency failure have the exact specified rollback, publication, and rethrow behavior.
- Prove every failure dispatches `CommandFailedEvent` for the original command and rethrows the identical
  `Throwable` without publishing a purpose-specific success event.
- Domain desired-state tests prove Agent, User, and Role behavior for already-present membership, already-absent
  membership, equal sets, duplicate and reordered input, real changes, revision movement, and preserved unrelated
  state.
- Command and event contract tests retain canonical serialization round trips, named accessors, registration, and
  rejection of every missing required value.
- Public-boundary tests prove the purpose-specific commands, authorization ports, and success events remain
  supported while shared coordinators are final, marked `@internal`, and absent from the consumer extension surface.
- Focused coordinator tests cover only branches that cannot be observed precisely through the public behavioral
  matrix. They do not assert private call graphs or require one shared aggregate implementation.
- Package architecture tests continue to enforce Domain and Application direction, Domain repository ownership,
  absence of a production Adapter layer, and prohibition of public coordinator contracts.
- Every production statement remains executable under exact coverage, and completion requires
  `./bin/planning-check` plus the canonical `./bin/build` gate.

## Out of Scope

- Direct Permission assignment to Users, Agent Roles, a generalized policy engine, or changes to Permission-removal
  reference-integrity ownership.
- Combining purpose-specific commands, authorization ports, or success events into generic authorization messages.
- A generic aggregate mutation interface or public workflow-coordinator extension point.
- Consumer persistence adapters, framework endpoint policy, controllers, voters, middleware, filters, response
  handling, queue routing, retry configuration, or worker operation.
- Replacing the current `UnitOfWork` constructor type before Fight Common `1.2.0` is tagged. Production behavior
  already uses `commitTransactional()`; the type-reference refactor may follow that release and is not a prerequisite.
- Refactoring unrelated command handlers merely because they also use transactions and failure events.
- A version tag, release, package publication, compatibility layer, or implementation work in consuming repositories.
