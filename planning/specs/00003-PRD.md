# Unified Authenticated Authority

## Problem Statement

Fight applications need one clear way to inspect the authority selected for the current request whether that
authority belongs to a User authenticated through a session or an Agent authenticated through a signed request.
The package currently exposes the necessary behavior through overlapping User and Agent Permission snapshots,
an intermediate Agent authentication result, and a current-security facade that accepts invalid empty or
ambiguous construction before rejecting it at runtime. That makes the public API harder to explain and gives
consumers more package structure to understand than the authorization problem requires.

The framework boundary also needs to remain explicit. Symfony, Laravel, Yii, CodeIgniter, and Slim do not use the
same authentication integration mechanisms, and a package principal must not implement one framework's identity
interface. At the same time, a framework adapter needs a supported way to distinguish a User from an Agent, expose
the appropriate framework Roles, and delegate Permission checks without reconstructing package authority.

This is pre-`1.0.0` public-API work. No release has been tagged, so preserving the current class layout is less
important than establishing a small framework-neutral contract that consuming projects can depend on before the
first stability promise.

## Solution

Provide one final request-scoped `SecurityContext` containing exactly one immutable authenticated User or Agent.
It exposes the selected authority and delegates common Role and Permission-presence checks without authenticating
a request or deciding whether an endpoint should be allowed. A package-owned principal type identifies the selected
authority as a User or Agent while the concrete principal retains its own identity and authentication data.

Use one narrow `PrincipalPermission` snapshot for both principal types. Keep the authoritative `Permission`
definition and the richer administrative `PermissionView` separate because they answer different questions.
Simplify Agent authentication and current-principal resolution into one request-cached flow that returns the
complete `AuthenticatedAgentPrincipal`, preserves generic caller-facing denial, and retains secret-free diagnostics.

Consumer projects continue to own framework identity wrappers, authentication-path selection, endpoint policy,
transport mapping, persistence, cryptographic services, logging, metrics, and runtime composition. The package owns
portable authority behavior and conformance only. The highest verification seam begins with a consumer-supplied
signed Agent request, resolves the complete request-cached principal through `CurrentAgentPrincipalProvider`, places
that principal in `SecurityContext`, and observes only the resulting principal type, Roles, Permissions, caching,
nonce behavior, and safe failure outcome.

## User Stories

1. As an application author, I want one security context for User and Agent requests, so that authorization checks
   do not depend on which authentication mechanism produced the current identity.
2. As a controller author, I want to inject one `SecurityContext`, so that in-method Permission and Role checks use
   the same selected authority as endpoint authorization.
3. As an Application-service author, I want to inject `SecurityContext` only when authorization belongs inside the
   use case, so that ordinary Application behavior remains independent of request security.
4. As a framework adapter author, I want to supply exactly one authenticated authority, so that empty or ambiguous
   request identity cannot enter the package facade.
5. As a framework adapter author, I want an explicit User-or-Agent principal type, so that I can construct the
   correct framework-owned identity without guessing from available methods.
6. As an authenticated User, I want my actual package Roles preserved, so that framework Role integration does not
   replace or flatten User authority.
7. As an authenticated User, I want effective Permissions resolved into one immutable snapshot, so that every check
   in the request observes the same Role-derived authority.
8. As an authenticated Agent, I want direct Permissions without User Roles or refresh-session behavior, so that a
   machine identity cannot be mistaken for a person.
9. As a Symfony adapter author, I want an Agent identity to expose `ROLE_AI_AGENT`, so that framework identity
   requirements can be met without inventing package-level Agent Roles.
10. As a Symfony adapter author, I want Agents to avoid receiving `ROLE_USER` by default, so that framework
    compatibility does not silently broaden machine authority.
11. As a Symfony endpoint author, I want Permission-voter checks to delegate to the selected package authority, so
    that `IsGranted` compatibility and recommended endpoint authorization use the same Permission decision.
12. As a Laravel, Yii, CodeIgniter, or Slim adapter author, I want to use my framework's native authentication and
    authorization mechanisms, so that portability does not require a lowest-common-denominator framework layer.
13. As an application author, I want User and Agent principals to expose the same Permission snapshot shape, so that
    audit and authorization code does not translate equivalent DTOs.
14. As an audit author, I want each principal Permission to retain its stable ID and canonical name, so that evidence
    can identify the definition without receiving aggregate or persistence authority.
15. As an administrative client author, I want `PermissionView` to retain management and tier details, so that
    simplifying authenticated authority does not remove information needed by Permission-management screens.
16. As an Agent client, I want authentication and authority resolution to produce one complete result, so that I do
    not need an intermediate authentication object or a follow-up Permission query.
17. As an Agent client, I want repeated access during one request to return the same principal object, so that
    authorization cannot drift midway through the request.
18. As a security reviewer, I want credential and Permission-assignment authority revalidated before a principal is
    returned, so that rotation, revocation, and concurrent assignment changes fail closed.
19. As a security reviewer, I want a nonce consumed after a valid signature to remain consumed when later authority
    resolution fails, so that a signed request cannot be replayed after crossing the replay boundary.
20. As an untrusted caller, I want every Agent authentication or authority failure to have one generic denial, so
    that responses do not reveal credentials, replay state, or Permission membership.
21. As an operator, I want a safe diagnostic classification and correlation identity for an Agent denial, so that I
    can investigate failures without logging signatures, nonces, secrets, or raw request material.
22. As a package consumer, I want HMAC verification, secret deciphering, nonce storage, clocks, persistence, and
    diagnostics represented by framework-neutral ports, so that the package does not select my infrastructure.
23. As a package consumer, I want public principals, services, and commands separated from internal coordinators, so
    that I do not accidentally implement or call unstable package machinery.
24. As a package maintainer, I want exact Permission resolution shared internally, so that User resolution, Agent
    resolution, and authority replacement cannot disagree about missing or renamed definitions.
25. As a release owner, I want obsolete pre-release classes removed without compatibility aliases, so that the first
    stable API does not preserve avoidable duplication.

## Implementation Decisions

- Rename `CurrentSecurityContext` to `SecurityContext` without a compatibility alias. It is a final class whose
  constructor requires exactly one `AuthenticatedAuthority`; the consumer adapter selects that authority first.
- `SecurityContext` returns the selected immutable authority and delegates `hasPermission()` and `hasRole()` checks.
  It does not authenticate, inspect transport state, select between authentication paths, or decide endpoint policy.
- The package-owned `AuthenticatedAuthority` contract exposes Permission presence, Role presence, and
  `getType(): AuthenticatedPrincipalType`. The backed principal-type enum has `USER` and `AGENT` cases.
- `AuthenticatedAuthority` is public for consumers to type against but package-implemented by the supported User and
  Agent principals. Consumers do not provide additional authority implementations.
- Keep `AuthenticatedUserPrincipal` and `AuthenticatedAgentPrincipal` distinct. The User principal retains its
  stable User and refresh-session identity, authentication version, Roles, and effective Permissions. The Agent
  principal retains its Agent and credential identity, credential revision, Permission-assignment revision, and
  direct Permissions.
- User authority reports its actual package Roles. Agent authority reports no package Roles. Framework-only markers
  such as `ROLE_AI_AGENT` belong to a consumer-owned identity wrapper and do not enter the package authority model.
- Use one final immutable `PrincipalPermission` for both principal types. It exposes `getPermissionId()`, `getName()`,
  and the exact safe `permission_id` and `name` array representation. Permission entries are value-deduplicated.
- Remove `AgentPrincipalPermission` and any narrow Agent Permission view that carries no meaning beyond the shared
  principal snapshot. Administrative reads reuse the shared safe identity/name representation where appropriate.
- Keep `Permission` as the authoritative Domain definition and `PermissionView` as the administrative query result
  containing Permission tier and managed status. Neither is interchangeable with `PrincipalPermission`.
- Keep `CurrentAgentPrincipalProvider` as the public name for the consumer-composed Agent flow. It validates one
  signed request, authenticates the credential, consumes the nonce after signature acceptance, revalidates current
  credential and Permission-assignment authority, resolves the exact Permission snapshots, and caches the completed
  `AuthenticatedAgentPrincipal` for that request.
- Remove the intermediate `AgentAuthenticationResult`. Agent authentication details needed for final resolution stay
  inside the one provider flow rather than becoming a second public result.
- A failure before signature acceptance does not consume a nonce. A failure after valid signature and nonce
  consumption does not restore that nonce, even when credential or Permission authority later fails revalidation.
- Preserve one generic caller-facing Agent denial. Preserve a secret-free server-side diagnostic classification and
  consumer correlation identity without signatures, nonces, shared secrets, or raw request material.
- Retain consumer-owned ports for HMAC verification, secret deciphering, nonce consumption, clocks, persistence,
  diagnostics, and runtime composition. Do not add a production Adapter layer or third-party framework dependency.
- Implement exact Permission resolution and other reusable package-owned service collaborators as final `@internal`
  concrete classes. Do not expose collaborator interfaces or promise compatibility for their constructors and methods;
  message handlers remain supported public application entry points.
- A Symfony adapter may wrap either concrete principal in a framework-owned User identity, return actual User Roles
  for a User, return `ROLE_AI_AGENT` for an Agent, and delegate `PERMISSION_TO:*` through a Permission voter. It does
  not make a package principal implement Symfony interfaces or grant an Agent `ROLE_USER` by default.
- Other framework adapters use native guards, providers, middleware, filters, policies, voters, and current-identity
  facilities while preserving the same package-observable authority behavior.
- Outer adapters normally own authentication, validation, authorization, synchronous or asynchronous invocation,
  and failure translation. Application services use `SecurityContext` only when authorization intentionally belongs
  inside the package or consuming use case.
- Consumer repositories are compatibility feedback, not prerequisites owned by this PRD. An integration failure may
  cause a later package refactor without requiring this repository to dictate another project's tickets.

## Testing Decisions

- The primary behavioral seam starts with a consumer-supplied signed Agent request, exercises the complete
  `CurrentAgentPrincipalProvider` flow, places its result in `SecurityContext`, and observes the selected principal
  type, Permission and Role checks, request caching, nonce outcome, generic denial, and safe diagnostics.
- The primary seam uses deterministic in-memory repositories and security ports. It does not require HTTP,
  persistence technology, a framework container, or a third-party security library.
- Principal contract tests prove `USER` and `AGENT` type results, actual User Role behavior, always-false Agent Role
  behavior, shared value-deduplicated `PrincipalPermission` entries, stable IDs and names, and safe serialization.
- `SecurityContext` contract tests prove construction with one authority and exact delegation to that immutable
  authority. Empty and multiple-authority constructor branches disappear rather than remaining runtime failures.
- Agent behavioral conformance proves one authentication and resolution per request and object-identical principal
  reuse for every later access during that request.
- Authentication-order tests prove malformed or invalid signatures do not consume a nonce, valid signatures consume
  it exactly once, and later authority-resolution failures leave it consumed while returning only the generic denial.
- Authority-fence tests prove removed or rotated credentials, stale credential or Permission-assignment revisions,
  missing Permissions, stale references, and concurrent assignment replacement fail closed without a principal.
- Diagnostic tests prove every failure classification and correlation identity remains secret-free and never enters
  the untrusted caller result.
- Public-boundary tests prove production consumers can autoload and use `SecurityContext`, both concrete principals,
  the authenticated-authority contract, principal-type enum, and shared Permission snapshot through supported public
  constructors and methods.
- Public-boundary tests also prove removed intermediate or duplicate snapshot types are absent from the supported API
  and package-internal coordinators are marked `@internal` rather than presented as consumer extension seams.
- Focused unit tests cover only Domain validation and failure branches that cannot be observed precisely through the
  higher behavioral and public-contract seams. Tests do not assert internal coordinator call graphs.
- Package architecture tests continue to reject framework imports, production Adapter code, and outward dependency
  direction. Consumer conformance asserts outcomes rather than identical wrappers, containers, routes, or schemas.
- Every production statement remains executable under exact coverage, and completion requires
  `./bin/planning-check` plus the canonical `./bin/build` gate.

## Out of Scope

- Production adapters or implementation tickets in Symfony, Laravel, Yii, CodeIgniter, Slim, Fight CMS, or another
  consuming project.
- A shared HTTP abstraction, framework User implementation, controller attribute, middleware, voter, guard, filter,
  response type, or denial format.
- Agent Roles, an Agent `ROLE_USER` default, policy evaluation beyond Role and Permission presence, or a generalized
  authorization engine.
- Direct User Permission assignment. Users continue to receive effective Permissions through assigned Roles.
- Replacing Agent HMAC with JWT authentication. A later consumer transition may reuse the same principal boundary.
- Authorization-assignment retry semantics and mutation coordinator consolidation, which belong to PRD-00004.
- Fight Common `UnitOfWork` type migration, a `1.0.0` tag, package publication, compatibility aliases, or consumer
  application delivery.
