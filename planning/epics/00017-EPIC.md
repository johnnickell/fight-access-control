# Explicit Optional Atomic Audit Recording

## Destination

Make AccessControl audit behavior explicit, cohesive and reusable within its CommandHandlers and related
synchronous use-case owners. Consumers opting into audit must not need business-aware TransactionalUnitOfWork
decorators, repository interception or post-commit subscribers to manufacture atomic evidence. Consumers may
also intentionally disable audit, with no durable-audit guarantee in that composition.

John approved the interview decisions and final shared understanding, the complete six-TICKET requirement split
and the two/five/five/four/four/four-TASK plans for all six TICKETs recorded below: 24 chores in total.
No implementation is started or authorized by writing these planning records. This is a pre-v1 contract change, not a v1 stability claim or a selected release version.

## Current Code, Released Baseline and Consumer Problem

- Current AuditEvidence carries an actor string, action string, UserId-or-AgentId subject and a string context
  map. It cannot directly identify a Role subject and has no explicit evidence identity, occurrence time,
  revisions or correlation fields. AuditEvidenceRepository already provides add(AuditEvidence): void.
- The current 37 CommandHandlers include 17 with a direct audit repository dependency and 20 without. Several
  existing writes cover only administrative paths, not every meaningful outcome. Dependency presence is not
  complete behavior or transaction qualification.
- CreateCustomRoleHandler, RenameCustomRoleHandler and RemoveCustomRoleHandler already mutate in the package
  transaction and publish success afterward, but do not insert package audit evidence. The inspected Audit and
  custom Role handler files match the local v0.8.0 tag; the current published release is v0.8.0 per project context.
- Agent OS's RoleMutationUnitOfWork inspects the transaction callback's returned CustomRoleCreated/Renamed/Removed
  event and calls RoleMutationAudit before commit. PostgresRoleMutationAudit writes a Role audit row. This is the
  concrete consumer workaround to remove after qualification, not a pattern the package should preserve.
- Existing password/email sensitive operations and Agent provision/rotation/revocation demonstrate explicit audit
  writes in their own transactions. Human delivery handlers also audit committed failed-delivery state, which
  differs from recording a command rejection in a transaction that rolls back.
- Installed Common supplies the existing TransactionalUnitOfWork callback contract, UniqueId and Uuid::NIL.
  Inspection identified no new Common mechanism needed for this audit destination. Actual supported-minimum
  evidence still belongs to implementation; local inspection is not full-gate or consumer qualification.

The consumer sources inspected were Agent OS's src/Application/Authorization/RoleMutationUnitOfWork.php,
src/Domain/Authorization/RoleMutationAudit.php, src/Adapter/Persistence/Repository/PostgresRoleMutationAudit.php,
its PostgresAuditEvidenceRepository and config/application/custom_roles.php. No sibling source was changed.

## Accepted Decisions

### D1 — Durable outcome evidence, not logs or post-commit events

An audit record is secret-free durable evidence of a semantically meaningful use-case outcome. Diagnostic logging
helps investigate execution/faults but is not an atomic business record. Domain events communicate facts after
commit; publication or subscription cannot substitute for required evidence when audit is enabled.

Record meaningful committed account, credential, session, membership, Permission, Role, Feature and managed-policy
outcomes, including explicitly recorded delivery failures and automated expiry/maintenance outcomes. Do not record
every repository call, worker poll, temporary internal claim or helper step merely because it executed.

### D2 — Auditing is optional everywhere, including existing mandatory writers

Every covered CommandHandler and related synchronous use-case owner supports an optional last audit repository
constructor argument, using the evolved AuditEvidenceRepository contract. Omitted/null means intentionally disabled;
configured storage failure never means disabled. Prefer explicit nullable injection over a no-op repository that
appears to promise durable persistence. No separate enable flag, lifecycle service or null implementation is needed.

John explicitly chose this policy for existing required-audit writers too. This deliberately weakens the old
guarantee when a consumer opts out; it is not a claim that unaudited execution remains durably audited. With a
repository supplied, audit remains part of the required atomic outcome. Mixed per-handler composition is explicit;
merely binding a repository somewhere does not enable audit for every use case. Enabling audit later does not
backfill previously unaudited outcomes; resolving an existing operation must not fabricate historical evidence or
change its retained key merely to manufacture an audit record.

This visibly amends conflicting mandatory-audit target guidance, including audit-preservation language in
EPIC-00015/00016, the project profile and existing operation/recovery plans, only within this approved audit policy.
It does not weaken aggregate invariants, authorization, shared writer/transaction fences or recovery safety.
Existing source and released guides remain the implemented/released baseline until this change is implemented.
Implementation must reconcile current guidance, constructors, callers, tests and release notes without rewriting
historical acceptance or pretending the new optional contract already ships.

### D3 — Evolve the existing cohesive evidence and persistence contracts

Improve AuditEvidence and AuditEvidenceRepository rather than create a parallel generic audit service. The
repository remains collection-like: explicitly add evidence inside the owning transaction. Do not infer evidence
by inspecting arbitrary returned events, intercepting aggregate repositories or wrapping a generic Unit of Work.

Evidence identifies supported package subjects through precise typed identities/references, preserving subject
kind as well as identifier. Support demonstrated User, Agent, Role, Permission and Feature subjects, and session,
grant, delivery or operation references where their actual outcomes require them. Preserve scoped operation-key
identity where a bare UUID would lose scope. Do not accept arbitrary objects, serialized entities, unrestricted
subject type/ID strings or untyped bags. Exact factories and ownership of concrete subject values are requirement/
design work within this boundary, not permission for a generic identity framework.

Application handlers own orchestration and transaction/audit coordination. Domain aggregates keep business
invariants/transitions. Reuse cohesive collaborators where useful, but reconcile existing helper-owned transactions
so audit is inserted explicitly within the actual owning transaction, not appended after it. In particular, the
Agent Permission-assignment coordinator must not force audit outside the mutation boundary. Do not introduce
forwarding handlers, nested transactions or generic lifecycle layers to avoid that responsibility.

### D4 — Direct typed actor IDs, including fixed system and anonymous identities

Use actorId values directly rather than an AuditActor wrapper or service-name string convention:

- UserId identifies an attributed User; AgentId identifies an attributed Agent.
- SystemId is a special UniqueId representing the system. Only Uuid::NIL is valid; generate() returns that fixed
  nil identity, fromString(Uuid::NIL) succeeds and non-nil construction/hydration rejects.
- AnonymousId follows the same fixed-nil rule but remains a different type. It identifies a deliberately anonymous
  initiating actor, not the system or a fabricated User. No system/anonymous account row or singleton machinery
  is required. Persist actor type alongside ID so equal UUID text cannot collapse different actor kinds.

System applies to deliberate application-originated provisioning, scheduled expiry and autonomous maintenance.
Anonymous applies to intentionally unauthenticated public requests, such as password-reset requests or public
registration. Actor means the originating identity for the audited operation: a worker executing an admitted User
command must not overwrite that User's attribution merely because execution is automated. The action and real
correlation describe the operation; this does not require a separate identity for every worker/service.

Entry adapters/trusted callers establish provenance and entry-point authorization. An actor ID grants no permission,
and the handler must not inspect HTTP, Console, MCP, HMAC or an ambient principal resolver. Preserve current
Application/Domain target/scope authorization contracts; audit does not remove them or authorize new actor classes
to perform operations previously restricted by policy.

Where a Command lacks actor information, add explicit optional typed actorId input to its transport-neutral use-case
contract. Reuse existing actor data where adequate. With auditing enabled, validate required attribution before
the first mutation that requires evidence; never silently substitute system/anonymous for missing input. A pure
no-change pass needs no audit-only attribution. Auditing disabled requires no newly introduced audit-only actor
input, but existing business-required actor fields remain required. Declared anonymous use cases may explicitly
establish their AnonymousId rather than mistake a target UserId for an authenticated initiator.

John's approved Feature-provisioning target shape is illustrative until implemented:

```php
$commandBus->execute(new ProvisionFeatures(
    defaultPermissionName: $defaultPermissionName,
    actorId: SystemId::fromString(Uuid::NIL),
));
```

Supply this once per provisioning command, not on every code-defined Feature. No login, special account or extra
human approval is introduced. Existing code discovery and creation/availability/authorization distinctions remain.

### D5 — Precise evidence contents without payload capture

| Fact | Accepted contract |
| --- | --- |
| Evidence identity | Unique record ID; unlike SystemId/AnonymousId, it is not the fixed nil identity and is not a generic command-idempotency token. |
| Actor | Direct typed actor ID under D4, with its kind preserved. |
| Subject/action | Typed primary subject and package-defined action, not arbitrary caller text or inferred event class. |
| Occurrence time | Trusted use-case outcome time, not message creation or database insertion time. Reuse the authoritative operation time where already captured. |
| Related subjects | Typed references needed to explain a relationship, such as the Permission granted to a Role. |
| Revisions | Authoritative before/after values where meaningful, preserving actual revision semantics and Role incarnation. Creation/removal do not fabricate nonexistent predecessor/successor state. |
| Correlation | Actual message/operation identifiers where available; not authority or proof of deduplication. |
| Safe context | Bounded, action-specific typed/validated facts, not an unrestricted context map. |

Exclude credentials, tokens, password hashes, ciphertext, raw messages, serialized entities, exception diagnostics
and unnecessary personal data. Free-text reasons are not automatically safe because their PHP type is string;
apply explicit field-specific admission/redaction policy rather than claiming secret freedom from a type or regex.
Evidence and identifiers are not automatically authorized public HTTP/log response data.

A Role rename can establish who changed which Role, when and between which revisions without a complete entity
snapshot. No event-sourcing, tamper-proof ledger, generic logging, retention or reporting subsystem is introduced.
Consumers remain responsible for appropriate durable storage, access and retention policy.

### D6 — Atomicity, failures and truthful outcome handling

When enabled, aggregate changes and their evidence participate in the same actual transaction/connection. Persist
evidence before commit; publish success only after confirmed commit. Audit-write failure before commit fails the
operation and rolls back staged transactional work. Never catch it merely to continue successfully without audit.

Concurrent losing writes roll back their staged evidence. Evidence describes authoritative committed outcomes,
not proposed stale successors. Lost commit acknowledgement remains uncertainty under the existing operation
contract, not proof of rollback and not a reason to manufacture a failure record or blindly repeat mutation.

Post-commit event/subscriber failure leaves mutation and audit committed. Preserve existing failure propagation
and the scoped Agent provisioning/rotation confirmed-result/publication-warning exception. Database rollback cannot
undo an external send, delivery or cleanup already performed; preserve the existing separately committed claims,
receipts, fences and recovery. Audit failure cannot imply that such an external effect never happened.

The repository checking that some transaction is active is insufficient proof of composition: it must join the
handler's actual connection and enclosing transaction. No business-aware Unit-of-Work decorator, repository
interception, nested independent commit or post-commit subscriber may be required to obtain this guarantee.

### D7 — No-change, rejection and existing retry behavior remain simple

- A meaningful new committed outcome gets evidence when enabled.
- Existing validated no-change branches get no new mutation record. Keep their authorization, revision/reference
  validation and fences; do not weaken admission just because no write follows. Examples include renaming a Role
  to its current name, assigning an already held Role or granting an already held Permission.
- A rejected/rolled-back attempt gets no committed-outcome record. Guaranteed durable rejected-attempt evidence
  is excluded; optional consumer diagnostic/security telemetry is separate and cannot survive by being written
  into the transaction that rolls back.
- Preserve Agent provisioning/rotation's existing retained-key resolution: resolving the original issuance creates
  neither new issuance nor duplicate mutation evidence. This is existing synchronous behavior, not a new generic
  command replay feature. A message/correlation/evidence ID alone is not universal command idempotency.
- A genuinely new operation gets its own evidence even if it resembles a prior action. Committed delivery-failure
  state is an auditable outcome, not the same thing as a rejected command.

For ProvisionFeatures and ReconcileManagedPolicy, record evidence per meaningfully changed Feature/Role/Permission,
sharing command correlation. Unchanged subjects get none. Ordinary coupled operations record their meaningful
use-case outcome and relevant relationships, not every incidental repository write.

## Concrete Custom Role Handler and Consumer Adoption

The following sketches illustrate the approved ownership; proposed evidence factories/signatures are not existing
APIs or independently accepted implementation. The handler gains an optional last constructor argument:

```php
private ?AuditEvidenceRepository $auditEvidenceRepository = null
```

Inside CreateCustomRoleHandler's existing transaction callback, after its existing validation and Role insertion:

```php
$this->roleRepository->add($role);

if ($this->auditEvidenceRepository !== null) {
    $this->auditEvidenceRepository->add(
        AuditEvidence::customRoleCreated(
            actorId: $command->getActorId(),
            roleId: $role->getId(),
            occurredAt: $createdAt,
            revision: $role->getRevision(),
            messageId: $messageId,
        )
    );
}

// Return the existing CustomRoleCreated event; publish it only after commit.
```

The evidence factory supplies a unique record identity; messageId is captured from the incoming message, not by
retaining/serializing it. Rename records actual before/after revisions only on change. Remove records the prior
authoritative revision and removed identity, not a fabricated successor. Existing exception handling must preserve
its primary failure and post-commit semantics.

Agent OS's current composition wraps its ordinary transactions in RoleMutationUnitOfWork with
PostgresRoleMutationAudit before injecting the Role handler. The target instead uses the ordinary shared Unit of
Work and the evolved audit adapter directly:

```php
$auditEvidenceRepository = new PostgresAuditEvidenceRepository($connection);

$handler = new CreateCustomRoleHandler(
    $roleRepository,
    $clock,
    $transactions,
    $events,
    $auditEvidenceRepository,
);
```

The Role repository, audit adapter and transactions must share connection and transaction identity; removal also
retains its User/reference-fence composition. The current PostgresAuditEvidenceRepository cannot automatically
handle the new Role/actor/evidence model: consumers update their persistence mapping/schema and qualify it first.
Then Agent OS can remove RoleMutationUnitOfWork, RoleMutationAudit and PostgresRoleMutationAudit without losing
atomicity. No sibling repair, schema operation or deletion is authorized by this EPIC's planning approval.

Consumers must explicitly choose audit injection, preserve actor/subject kinds and applicable complete revision/
correlation data, provide safe field admission and protect evidence access. Verify audit failure rollback,
concurrent loss, committed evidence despite publisher failure, no-change behavior and existing recovery against
the real shared connection. An enabled adapter must not silently discard unsupported evidence or fall back to
no-op behavior. Package fixtures do not qualify consumer storage, bootstrap, sinks or deployment.

Apply ADR 0011: update current constructors/messages/callers/tests/docs directly. No legacy actor-string reader,
old mandatory-constructor compatibility facade, overload mode or package migration/backfill machinery is added.
Document pre-v1 breaking public/persisted contracts and consumer schema/composition obligations; actual consumer
data operations, release/version selection, signing and deployment remain separately authorized.
