# Enforce Permission Grant Tiers

## Destination

Publish a framework-neutral AccessControl package contract for the proposed `v0.4.0` release in which every
Permission has a tier and a managed `SUPER_ADMIN_ONLY` Permission can belong only to the managed
`ROLE_SUPER_ADMIN`. Only human Users may receive that authority, through assignment of that Role. Custom Roles,
other managed Roles, and Agents cannot acquire it through any package command. The package enforces its own
membership and managed-policy invariants; consuming applications protect command entry points and decide caller,
target, scope, confirmation, and audit policy.

## Decisions so far

- [Define protected Permission membership and designated Role identity](../wayfinder/tickets/WF-011-protected-permission-membership.md):
  the exact `ROLE_SUPER_ADMIN` name identifies the designated Role only when it is managed and authoritative.
  Consumers define managed Permission names and tiers; AccessControl enforces the declared tier without an actor
  exception or a protected-name list.
- [Classify custom Permissions for delegation](../wayfinder/tickets/WF-012-custom-permission-delegation.md): every
  Permission has a non-null tier. Custom Permissions start `ADMIN_SAFE` and cannot become protected.
  `ADMIN_SAFE` permits controlled custom-Role and direct Agent delegation, including Agent complete-set replacement;
  it does not authorize a caller or target.
- [Separate Permission eligibility from caller authorization](../wayfinder/tickets/WF-013-target-aware-role-administration.md):
  package Role and Agent Permission commands reject protected grants and invalid definitions, including complete-set
  requests and idempotent paths. Application builders protect API, CLI, worker, and direct command-bus entry points.
  Remove actor-only checks from Role administration, Agent Permission, and User Role-assignment handlers; retain the
  ownership-sensitive checks for cross-user sessions, email changes, and pending-invitation correction.
- [Set Super Admin assignment and removal guarantees](../wayfinder/tickets/WF-014-super-admin-role-elevation.md):
  reserve `ROLE_SUPER_ADMIN` for the managed Role across creation, rename, and reconstruction. User Role assignment
  and removal otherwise retain ordinary package semantics, including pending User assignment for bootstrap. The
  consumer owns elevation and removal authorization, confirmation, audit, last-admin protection, and recovery.
- [Guard managed Permission reclassification](../wayfinder/tickets/WF-015-forbidden-authority-remediation.md):
  reject promotion to `SUPER_ADMIN_ONLY` while an ordinary managed Role, custom Role, or Agent holds the Permission;
  do not partially reconcile policy or remove memberships automatically.
- [Set atomic tier enforcement proof](../wayfinder/tickets/WF-016-atomic-enforcement-and-proof.md): a concurrent grant
  and promotion cannot both succeed. Repository contracts preserve tier authority through the command transaction;
  adapters choose their locking method. Focused package unit tests prove the behavior, and implementation runs the
  normal package build.

## Acceptance boundary

- Managed-policy definitions cannot place a protected Permission outside the designated managed Role, and
  reconciliation rejects an unsafe tier promotion before changing authority.
- Custom-Role grants and direct Agent grants or complete-set replacements reject protected Permissions without a
  partial write or success event. Eligible `ADMIN_SAFE` changes retain their existing desired-state behavior.
- A custom Role cannot impersonate `ROLE_SUPER_ADMIN`; User Role commands keep their ordinary package behavior.
- Package tests cover allowed and rejected commands, no-op and conflicting-state paths, and failure outcomes. The
  complete `./bin/build` gate passes for implementation changes.

## Boundaries and handoff

- This EPIC owns the AccessControl package contract and its tests. Fight Agent OS currently has no stored
  Permissions; its schema, adapters, command-entry protection, PostgreSQL/HTTP tests, dependency update, and full
  consumer build belong to separate adoption planning. No historical Agent OS Permission cleanup is planned here.
- Scoped Workspace/Repository administration, consumer Permission-name classification, caller audit, last-admin
  safeguards, package tagging/release, and consumer deployment remain outside this EPIC's implementation scope.
- The [Wayfinder map](../wayfinder/permission-grant-tiers-v0-4-0-map.md) is decision-complete. Decompose this EPIC
  into TICKETs and TASKs before implementation; this record does not authorize code changes or a release.
