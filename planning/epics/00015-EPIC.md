# Pre-v1 Architecture and Supported Common Integration

## Destination

Give maintainers cohesive Domain aggregates, use-case-owned Application capabilities and thin protocol adapters
before extending the remaining permission integrations. Adopt supported canonical Fight Common contracts without
building on deprecated names, provisional Stores or broad lifecycle forwarding services. Preserve existing security,
transaction, recovery and public wire guarantees while intentionally replacing pre-v1 PHP interfaces.

conversation. This is an accepted planning destination, not implementation acceptance or a workflow invocation.
The inspected AccessControl baseline is clean `ea1e2268f4fe748101987ba614b1676459c4d6c1`.

## Accepted Decisions and Policy Amendments

1. **Layer and namespace ownership:** retain `Adapter → Application → Domain`. Domain uses
   `Domain/{BoundedContext}/{Aggregate}` with roots, identities, repository interfaces and owned entities/values;
   Commands/Queries express intent and Events past facts. Application mirrors aggregate ownership with handlers,
   policy-named subscribers and cohesive semantic capabilities; Service is a fallback, not a miscellaneous home.
   Adapter alone references frameworks/infrastructure. Application may use PSR and supported upstream Application/
   Domain contracts; Domain may use pure PHP and supported upstream Domain contracts. Keep justified package exceptions.
2. **MCP ownership:** concrete profile Tools, schemas, protocol failure mappings, Common descriptor/registry bindings
   and availability implementations move to `Adapter/Mcp/{Tool,Resource,Skill}/Agent`. Genuine authentication,
   Permission decisions and synchronized continuation remain Application-owned. Use the transport-neutral Mcp
   capability, not speculative Http/V1 folders. Common owns protocol engines and use cases; no wrappers around its
   Commands/Queries, copied schemas, new endpoint or generic permission facade.
3. **Visible replacement of old guidance:** this target specializes the capability/framework-only Adapter layout
   in WF-035, EPIC-00014 and the profile where aggregate-oriented protocol presentation is involved. It does not
   authorize production persistence adapters here or remove optional-framework isolation. TASK-00107 owns normative
   guidance/ADR reconciliation; old code remains the implemented baseline until its refactoring TASK is accepted.
4. **Cohesion and naming:** organize Agent authentication, provisioning, credential rotation/revocation, delivery,
   maintenance, continuation and Permission-assignment collaborators by their actual capabilities. Group Feature
   discovery and authorization admission similarly. Use `$agentRepository`, `$queryBus`, `$synchronousCommandBus`
   and `$eventDispatcher`, not collection-like collaborator names. Actual collections keep natural plural names.
5. **Aggregate encapsulation:** User business transitions own their related authentication-authority revision changes.
   Callers must not separately increment bookkeeping. Preserve the distinct authentication version and successful-login
   serialization requirement. Repository CAS and coupled session insertion remain mandatory atomic capabilities.
6. **Synchronous use cases, not one broad service:** replace the profile/ADR 0003 requirement that all secret-bearing
   operations live on AuthenticationService with cohesive synchronous authentication, session, password and email-
   confirmation capabilities. Keep raw secrets sensitive and non-serializable, normal bus dispatch for existing
   messages, audit/transaction ownership and current post-commit failure semantics. No forwarding facade or options bag.
7. **Agent domain clarity:** AgentName owns one name rule, using the existing fixed Unicode-edge provisioning semantics
   so canonical request bytes/marker 2 remain unchanged. Rename adopts that rule as an intentional pre-v1 behavior
   change. Treat AgentCredentialOperation as a separate aggregate in AccessControl, not a new bounded context; expose
   a narrow secret-free read repository and preserve atomic Agent/operation retirement and shared writer fences.
8. **Compatibility:** apply ADR 0011. Update AccessControl consumers/tests/docs directly without old-name aliases,
   deprecated facades, historical readers or migrations. Common's released 1.x compatibility policy remains Common's
   obligation; AccessControl uses its qualified canonical APIs, not their deprecated bridges. Current-contract
   hydration, generations, receipts, tombstones, ordering and restoration safety are not compatibility debris.

## Approved Follow-up — Result-Preserving Agent Commands

During the explicit-audit Grill, John requested preserving the eventual command conversion of
`AgentProvisioningService::provision()` and `AgentCredentialRotationService::rotate()` in EPIC-00015/00016.
This EPIC owns their future command/handler coordination and public use-case conversion;
[EPIC-00016](00016-EPIC.md#agent-command-result-coordination-follow-up) owns coordinated result typing and
qualification, without a duplicate conversion implementation. The separate audit destination does not depend on it.

The inspected current services take secret-free intent: retained operation key, name/Agent/predecessor metadata
and destination binding. Secrets are generated internally and returned results contain safe issuance metadata,
not credentials. Internal secret generation alone is not a reason to exempt these operations from Commands.
This does not relax the rule against serializing raw authentication/password/credential inputs.

- Introduce transport-neutral provisioning/rotation intent and let their Application CommandHandlers own the
  existing synchronous coordination through actual configured buses. This does not require a queue or job system.
- Preserve retained key/request identity and canonical binding, same-key resolution, scope/target/destination
  authorization, shared fences/atomicity, delivery separation and current post-commit outcomes. Keep confirmed
  issuance, indeterminate commit and typed sanitized publication-warning results visible to the caller. A later
  status Query is not assumed to reproduce an invocation-specific publication warning.
- The installed Common CommandHandler and CommandBus return void. Result-preserving conversion therefore needs
  actual supported result-capable synchronous command contracts upstream, or a separately approved caller-contract
  change. No such alternative contract change is approved here. Verify implemented/independently accepted/qualified
  tagged APIs and a sufficient minimum; do not infer availability from Common planning or local source.
- Do not emulate results through mutable messages, captured side channels, event inspection, direct-handler bypass
  or AccessControl-only bus shims. Move ownership rather than add forwarding handlers around retained services.
  Remove superseded direct service APIs/owned callers under ADR 0011 when the replacement is qualified.
- Coordinate existing canonical adoption with TASK-00110 and operation/read ownership with TASK-00114, without
  silently expanding either task. Existing TASK-00107–00114 scope, priority and blockers are unchanged.

This is an approved architectural follow-up, not implemented source, a qualified Common release or an accepted
conversion TICKET/TASK plan. Scope its requirements and integration acceptance during a later To Tickets continuation;
retain the original four-TICKET/eight-TASK plan as complete for its original scope. Under EPIC-00016/TICKET-00038,
[TASK-00130](../tasks/00130-TASK.md) now owns dispatch-specific result typing/qualification only. It consumes actual
converted production handlers; this EPIC's conversion retains its own business tests/gate/independent acceptance.
The qualifier remains needs-info for qualified Common result APIs and the real conversion supplier. Add the actual
local supplier edge(s) once those TASKs exist, before clearing readiness; do not invent IDs or expand earlier tasks.

TASK-00130 neither decomposes nor implements this EPIC's missing conversion requirements. Missing result-contract
proof holds affected conversion/qualification only, not current services, the existing 37 void handlers, independent
Query adoption, audit work or unrelated ready capabilities.
