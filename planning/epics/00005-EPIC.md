# Agent-Aware MCP Tool Authorization

## Destination

Publish a reusable AccessControl-owned contract that lets an Agent-protected MCP composition advertise and invoke
only the tools permitted by the current authenticated Agent. Once a request reaches this availability integration,
an unresolved Agent, missing required Permissions, and unknown tool names produce the same public unavailable
outcome. Fight Common remains policy-free, while consumers retain transport authentication and denial handling,
authentication selection, exposed-tool selection, and runtime wiring.

## Decisions so far

- `Fight\AccessControl\Application\AccessControl\Agent\Attribute\RequiresAgentPermission` declares one required
  direct Agent Permission at Common's public MCP tool declaration boundary. The attribute is repeatable and every
  declaration is required; future any-of policy needs a separate explicit construct. Its exact PHP target, tool class
  or `handle()` method, follows Common's published `McpTool` contract rather than being guessed in this epic.
- Every tool in an Agent-protected composition must declare its required Permission metadata. Missing metadata is a
  composition failure; malformed or absent metadata encountered at runtime still fails closed. Public tools belong
  in a separate unprotected composition rather than receiving an implicit missing-metadata exception.
- Fight Common owns MCP capability and tool registration, canonical tool names, discovery filtering, tool selection,
  and public unknown-tool behavior. AccessControl supplies one request-scoped implementation of Common's neutral
  tool-availability boundary and does not pass an Agent, principal, Permission, or policy object into Common.
- Composition builds an immutable canonical-tool-name-to-required-Permissions catalog from the same registered tools,
  Common's resolved canonical names, and AccessControl's attributes. Reflection does not repeat after that integration
  instance exists. A framework may construct the instance per request, and a consumer may add a compiled or
  release-scoped metadata cache, but AccessControl does not own a filesystem cache or duplicate Common's naming rules.
- One fresh `CurrentAgentPrincipalProvider` resolves the authoritative Agent and Permission snapshot once per MCP
  request. The snapshot may be reused within that request only. Every later request, including a protected-interaction
  retry, resolves current authority again from persistence.
- Tool discovery filters unavailable tools before deterministic ordering and pagination. Direct invocation checks the
  same availability before tool-specific validation, CQRS dispatch, progress, interaction-state disclosure, or resume.
  Unknown and unavailable tools are publicly indistinguishable and an authority failure performs no protected work.
- Only static tool metadata may be cached across requests. Agent principals and filtered availability remain
  request-local, and authorization-sensitive discovery uses `ttlMs: 0` with `cacheScope: private`.
- Request-local authorization is a snapshot boundary. Revocation after principal resolution does not cancel work
  already authorized within that same request; a later request observes the revocation.

## Acceptance boundary

- An authenticated Agent sees and invokes a protected tool only when its snapshot contains every declared Permission.
- Once a request reaches the availability integration, an unresolved Agent, an Agent missing any required Permission,
  and a caller naming an unknown tool receive the same public unavailable behavior, with no tool validation or
  protected command/query dispatch. Consumer transport authentication may reject a request before MCP dispatch.
- Missing metadata rejects an Agent-protected composition, while repeated attributes prove conjunctive authorization.
- Permission or Agent revocation between discovery and invocation, or between protected interaction rounds, is
  observed by the next request and denies before protected work.
- Conformance proves that Common receives only a neutral availability decision and that canonical tool names cannot
  drift between registration, discovery, invocation, and the Permission catalog.

## Dependencies and exclusions

- Fight Common must first publish the later tool contracts that own `tools/list`, `tools/call`, resolved canonical tool
  metadata, availability filtering, and protected-interaction retry. Its emerging `McpCapabilityRegistry` owns
  protocol-method registration and is not itself a per-tool metadata map.
- Exact Common interface names, PHP signatures, and the compatible attribute target are resolved against that
  published tool surface before TASK-00035 becomes ready for agent or implementation begins; this does not reopen
  the behavior fixed by this epic.
- Consumer routes, HTTP responses, authentication selection, OAuth claim or scope mapping, TLS, origins, limits,
  persistence adapters, framework composition, and exposed-tool selection remain consumer-owned.
- Self-service Agent profile reads and name updates, their schemas, Permission identities, idempotency, events, and
  failure classifications remain outside this epic and require their own Wayfinder resolution.
