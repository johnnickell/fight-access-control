# Optional User Self-Registration and Registration-Origin Delivery for v1.0.0

## Destination

Provide an optional, framework-neutral AccessControl registration use case before the v1.0.0 stability decision.
Consumers may expose it per installation; AccessControl supplies the registration operations and matching handlers,
not an enablement gate or a public page. A new registrant becomes a pending User with consumer-configured default
Roles and a recoverable one-time activation credential. Consumer-owned mail providers can distinguish registration
from private invitation and select their own templates, including after restart. Authorized administrators can
recover a pending registration without losing its User or Roles.

John approved this one destination after all decisions in the
[Wayfinder map](../wayfinder/self-registration-v1-map.md) closed. This additive planning track does not change the
v0.5.0 feature set or enable registration by default in fight-agent-os or any starter. Its target is planning before
v1.0.0, not a release, deployment or consumer-adoption commitment.

## Accepted behavior

- [WF-026](../wayfinder/tickets/WF-026-registration-admission-and-default-authority.md) owns admission. The
  registration handler receives a nonempty list of consumer-configured `RoleName` strings at construction and
  resolves current Roles by name. A public request cannot choose Role identities. Missing Roles or a
  `ROLE_SUPER_ADMIN` default reject the whole registration; there is no global assumption that `ROLE_USER` exists
  or blanket prohibition on other consumer-defined Roles. Canonical-email claims and live reservations retain
  authoritative atomic uniqueness. A successful registration commits the pending User, all default Role assignments,
  activation grant, encrypted recoverable delivery and audit together; pre-commit failure, including a concurrent
  Role-reference change, leaves none of these effects. Provider invocation occurs after commit, not as proof of
  delivery or activation.
- [WF-027](../wayfinder/tickets/WF-027-registration-delivery-origin.md) owns message identity. Reuse the existing
  one-time password-setting/activation journey, but durably record immutable registration-versus-private-invitation
  origin on recoverable activation delivery and pass it to the consumer provider. Immediate delivery, retry,
  scheduler restart, resend and replacement must preserve the appropriate origin; `activation` purpose or transient
  events alone cannot select the template. Existing private invitations stay private invitations. A deleted User
  restored to pending by an administrator starts a new private-invitation journey, even if previously registered.
- Administrator registration recovery is a distinct, authorized operation from private-invitation correction and
  from anonymous registration. For a pending registration it can correct a wrong address or issue new activation
  after expiry at the same email. Both retain the existing pending User and assigned Roles, invalidate prior
  activation authority, create a fresh registration-origin grant/delivery and audit the change. It never creates
  a second User or gives an anonymous caller recovery access. Existing private-invitation correction remains
  invitation-specific.
- [WF-028](../wayfinder/tickets/WF-028-public-registration-safety-boundary.md) owns the public boundary.
  Duplicate canonical emails remain rejected internally, including existing Users in all states and live
  reservations; they do not produce new activation work or package-level generic success. Consumers own public
  response mapping and evaluation of account enumeration, plus throttling, challenges and abuse logging for
  **every** entry point they expose. AccessControl has no HTTP registration response or new registration-specific
  anti-abuse/enabled-setting policy.

## Acceptance and integration boundary

- Downstream TICKETs must state the registration, administrator recovery and delivery use cases with their
  commands, necessary queries, events/audit, authorization, validation and rejection behavior. Design the exact
  API, administrator authorization contract, Role-reference fencing and concurrency/recovery proof there without
  reopening the decisions above. Preserve current package command failure/rethrow and post-commit publication
  semantics; never describe a post-commit notification fault as a rollback.
- Package evidence must prove all-or-nothing pending identity/default Roles/grant/delivery/audit, duplicate-email
  and invalid-Role rejection, safe concurrent Role changes, correct origin for both invitation and registration
  through retry, restart, resend and recovery, predecessor invalidation, and pending-User/Role retention. Include
  existing invitation behavior, deleted-to-pending private origin and failure/restart paths in the matrix. Verify
  with the project's focused tests and complete implementation gate when implementation is authorized.
- Document the consumer provider contract, wiring and persistence/worker implications, with consumer-bindable
  evidence where useful. Separately check in an actual consuming project that its existing private invitation
  templates are configurable and remain distinct from new registration templates; package provider-invocation
  tests do **not** establish consumer mail composition, real database concurrency or deployed public protections.
  Record unexecuted consumer qualification as a gap, not package acceptance evidence.

## Exclusions and planning handoff

Consumers own pages/routes, installation database settings, persistence/SQL, mail templates and rendering,
provider/transport adapters, scheduler composition, public abuse protections, response text/status and runtime
qualification. No package production Adapter layer, template service or requirement to turn on registration in
Agent OS or starters is included. A new public cancellation flow, general non-pending recovery, retroactive
reassignment of already-pending Users when configured defaults change, package generic acknowledgement for
existing emails, old-contract migration/compatibility paths and changes to unrelated private-invitation policy
are excluded.
