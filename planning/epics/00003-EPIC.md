# Pre-1.0 Authorization Boundary Simplification

## Destination

Make the package's authorization API small, explicit, and consistent before the first public release. A consuming
project receives one authenticated User or Agent through one `SecurityContext`, checks Roles and Permissions through
that context, and can retry authority-assignment commands without producing duplicate writes, revisions, or events.
Framework integration remains consumer-owned, while package-owned resolution and mutation coordination remain
closed implementation details.

## Decisions so far

- `SecurityContext` is the final public request-scoped facade over exactly one authenticated authority.
- Authenticated Users and Agents remain distinct, expose a package-owned principal type, and share one narrow
  `PrincipalPermission` snapshot without sharing User Roles or session behavior.
- Agent authentication and current-principal resolution form one request-cached flow with fail-closed authority
  revalidation and secret-free diagnostics.
- Agent Permission, User Role, and custom-Role Permission commands express desired state. Repeating an already
  satisfied change is a no-op with no persistence write, revision change, or success event.
- Package-owned workflow coordinators are final and `@internal`. Consumers depend only on the supported public API.
- `v0.1.0` establishes the first public package milestone. Later `0.x` releases may refine public contracts before
  the separately authorized `1.0.0` stability promise.

## Progress

normalized complete-set semantics; TASK-00030 delivered aggregate-owned idempotent User Role mutation with final
Role-reference fencing. Both passed canonical exact-coverage builds. TASK-00031 completed retry-safe custom-Role
Permission mutation with a final Permission-reference fence and exact coverage. All constituent Tasks and tasks
are terminal; a separate stability review remains before `1.0.0` release authorization.
