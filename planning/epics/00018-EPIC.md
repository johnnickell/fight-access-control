# Portable Feature and Permission Admission

## Destination

Provide two independently selectable HTTP admission capabilities across Slim, Yii 3, Symfony, Laravel and
CodeIgniter 4: Feature gating through FeatureFlag and portable Permission requirements through an AccessControl-owned
RequiresPermission. Consumers can select either capability or both without duplicating policy in each framework.
When both apply, both must pass; a Feature being available never authorizes the underlying action.

John approved the interview decisions and complete shared understanding, then the four-TICKET requirement split
recorded below. Grill created one EPIC; To Tickets subsequently created its four requirements. John then approved
TICKET-00049's two-TASK declaration plan, TICKET-00050's four-TASK Feature plan, TICKET-00051's four-TASK Permission
plan and TICKET-00052's reduced two-chore evidence/gap-closure plan below, not implementation. All five frameworks are in scope; no assigned release/version, consumer adoption,
relative framework priority or new combined release obligation with other EPICs is inferred.

## Inspected Baseline

- src/Application/AccessControl/Feature/Service/FeatureAvailability.php already evaluates fresh stored Feature state
  against an existing authenticated User/Agent snapshot or null. It validates the stored Permission binding at every
  status; ON can be available anonymously, PREVIEW needs the bound Permission ID, and OFF denies everyone.
- src/Application/AccessControl/Feature/Attribute/FeatureFlag.php currently permits methods only, is not repeatable,
  and declares a discovery reference rather than runtime enforcement. No production Feature middleware exists.
- AccessControl has no portable RequiresPermission Attribute. Agent OS has its own
  src/Adapter/Http/Attribute/RequiresPermission.php, which permits classes only and is repeatable. This consumer
  observation is not a portable package API or authorization to modify that repository.
- Current PermissionMiddleware and Symfony PermissionSubscriber use explicit trusted PermissionDeclaration bindings,
  inward admission/authority contracts and qualified safe-error composition. Attributes are not automatically consumed.
  Native Symfony IsGranted composition remains distinct from a portable package Attribute.
- [TASK-00103](../tasks/00103-TASK.md) (shared PSR-15 with separately qualified Slim/Yii 3 journeys) and
  [TASK-00104](../tasks/00104-TASK.md) (Symfony) are done. [TASK-00105](../tasks/00105-TASK.md) (Laravel) and
  [TASK-00106](../tasks/00106-TASK.md) (CodeIgniter 4) already plan native Permission integration, are ready-for-agent
  and name the completed TASK-00103 as their sole blocker. Neither pending adapter is implemented.

These are bounded source/planning observations, not an exhaustive audit, fresh product gate, supported-minimum
qualification or real consumer proof. Existing code and released guides remain the implemented/released baseline.

## Decisions so far

### D1 — Two independent capabilities, five supported framework families

Feature admission and Permission admission are separate opt-in capabilities. Enabling Feature checks must not
require enabling Permission middleware, and enabling Permission checks must not require Feature evaluation.
When both protect an action, both restrictions apply. An action with no effective Feature declaration is not
Feature-gated; this does not make it public or bypass the selected Permission capability's existing explicit
public/authenticated/protected-route rules.

| Framework | Integration direction |
| --- | --- |
| Slim | Shared PSR-15 admission with trusted native route/action/context composition. |
| Yii 3 | Reuse PSR-15 where honest; qualify actual Yii 3 composition independently of Slim. |
| Symfony | Native subscriber/listener at the qualified admission lifecycle. |
| Laravel | Native middleware with explicit application registration. |
| CodeIgniter 4 | Native before-filter with correct response short-circuit and error composition. |

Use thin optional adapters around shared framework-neutral declarations/evaluation/admission, not five implementations
of Feature or Permission policy. Keep capability-first placement, isolated optional dependencies and
Adapter → Application → Domain. Consumers still own installed routes, authentication, application policy/scope,
bootstrap and infrastructure; no unrelated service/framework activation or global handler takeover is implied.
This approved destination extends the existing optional HTTP Permission Adapter boundary only for the Feature
admission and portable declaration adaptations above, not production persistence or general framework infrastructure.

### D2 — Portable class and method declarations

Extend the existing FeatureFlag to classes and methods and make it repeatable. Introduce AccessControl-owned portable
RequiresPermission with the same class/method and repeatability support, rather than require Agent OS's Attribute.
Feature names and Permission requirements use the package's validated canonical concepts; exact public namespace/
factory/signature choices belong to requirement/design work within this boundary, not speculative compatibility APIs.

Adapters enforce effective declarations on the selected HTTP action. Explicit trusted route bindings cover closures
and other supported handlers and may supplement attributes. This does not intercept arbitrary direct PHP calls,
service methods, buses, workers or other transports. Keep existing native framework authorization checks separate;
a portable Attribute is not an automatic Symfony voter, role mapper or OAuth-scope conversion.

### D3 — Conjunctive accumulation and no weakening

Accumulate effective class, method, inherited and explicit route requirements. Every declared Feature and Permission
must pass; repeated identical requirements are deduplicated without changing meaning. Requirements on parent classes
and overridden parent methods remain effective. A child class/method can add gates but cannot silently remove an
inherited gate. Protect association with the actual selected action, including supported inherited/invokable forms;
unsupported, malformed or ambiguous protected metadata cannot turn into an unguarded action.

Validate and reject contradictory configuration rather than silently choose an override/winner. In particular,
explicit public/authenticated-only Permission policy cannot erase effective RequiresPermission requirements. A public
Permission route may legitimately have a Feature gate: the two capabilities remain independent. Do not infer public
Permission admission merely from an absent Attribute or treat untrusted request data as a route declaration.

Inheritance/merging must be implemented deliberately, not assumed from PHP Attribute target flags or reflection
alone. Cover class hierarchies, overridden methods, duplicate requirements, inherited action dispatch and explicit
route additions in executable tests. Current declaration/discovery/provisioning callers must recognize class-level
and repeated Feature references without silently omitting the effective gates.

### D4 — Reuse Feature evaluation without new authorization

Use existing FeatureAvailability semantics and authoritative fresh reads:

| Stored Feature state | Feature gate after valid binding checks |
| --- | --- |
| OFF | Deny, including privileged User/Agent callers. |
| PREVIEW | Pass only if the existing authenticated User/Agent snapshot has the bound Permission ID; anonymous denies. |
| ON | Pass the Feature restriction, including anonymous callers; separate action authorization still applies. |

No role/display-name bypass, identity substitution, implicit default binding, new grant, automatic provisioning or
mutation is introduced. A missing/broken binding is not repaired by evaluation, even at OFF/ON. Preserve typed
Feature/Permission identity matching and Domain-owned invariants. Availability remains a fresh restriction, not a
live authority lease or promise to cancel work already admitted without another check.

Reuse trusted User/Agent identity and appropriate existing authority contracts; Permission admission preserves User
Role-derived versus Agent direct Permission semantics. Null is deliberate anonymous Feature context, not fallback for
an invalid/conflicting authenticated context or failing provider. Avoid stale request/provider singletons, inherited
subrequest authority, double authentication or replayed Agent nonces. Fresh Feature settings do not refresh grants
inside a previously captured principal; keep the normal documented authority/request lifecycle.

### D5 — Safe Feature refusal distinct from faults

Return a generic HTTP 404 when OFF or an unmet PREVIEW requirement denies the Feature gate. Do not expose Feature
names, bound Permission IDs, status/configuration details or private diagnostics. Missing Feature definitions, broken
bindings, malformed declarations and storage/provider/native faults remain safely handled configuration/operational
errors, not ordinary disabled-Feature 404s, successful admission or implicit public access.

Permission refusals retain existing authentication/authorization behavior and qualified safe classification,
including consumer-selected valid authentication challenges where required. Compose known outcomes through Common's
actual safe error policy and selected native boundaries, preserving one redacted reporting owner and safe fallback.
Do not classify arbitrary messages/codes/causes, copy exception text into responses, add competing reporters/renderers
or claim delegated HTML/global handlers are automatically safe. Preserve MCP/OAuth native envelopes outside this scope.

### D6 — Admission ordering and supported native lifecycles

Enforce declarations before protected validation and action/use-case work. Derive requirements from trusted selected
route/action metadata, not client headers, request parameters, caller-controlled Attribute names or copied grants.
Preserve action/route association and actual framework-native response short-circuit and request/subrequest/reset
behavior, including exceptions and reused containers.

Qualify real lifecycle order instead of promising universal pre-construction denial. Symfony kernel.controller
follows controller resolution; some Laravel controller-middleware discovery can construct controllers before route
middleware. Preserve existing qualified early admission where applicable, explicitly document eager/bootstrap and
supported controller-form limits, and never describe discovery/construction as authorization proof. Do not bypass
framework safeguards or introduce a generic reflection/security framework to hide these limits.
