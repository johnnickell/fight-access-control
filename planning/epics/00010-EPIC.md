# Permission-Based Feature Flags

## Destination

Deliver a framework-neutral AccessControl capability for controlling feature availability, including production
preview access for selected Users and Agents through existing Permissions rather than Role checks. Applications
can discover code-declared Features, provision them safely, manage their availability, and retire them without
leaving known current references to deleted records.

**Approved by John; planning authority only.** The behavior and package-only integration boundary are accepted in
[WF-017 through WF-022](../wayfinder/permission-based-feature-flags-map.md). John subsequently approved the three-TICKET
decomposition: registration/provisioning, evaluation, and management/retirement. Those requirements are recorded;
All three TICKETs now have approved TASK plans: three registration/provisioning TASKs, one evaluator TASK, and three
management/retirement TASKs (TASK-00061–00067). Implementation remains separately authorized. No release version is
selected. Consumer adoption, including Fight CMS migration, is separate; approval does not authorize code changes,
publication, or deployment.

## Decisions so far

### D1 — Availability and authority

[WF-017 — Define feature availability and preview semantics](../wayfinder/tickets/WF-017-feature-availability-and-preview.md)
settles the string-backed enum:

```php
enum FeatureStatus: string
{
    case OFF = 'off';
    case PREVIEW = 'preview';
    case ON = 'on';
}
```

OFF denies everyone. PREVIEW requires the Feature's testing Permission. ON removes the feature restriction,
including for anonymous callers where the underlying use case permits anonymous access. Ordinary business/action
authorization always remains separate. Feature availability never grants management authority.

[WF-018 — Bind preview eligibility to configurable Permissions](../wayfinder/tickets/WF-018-feature-preview-permission-binding.md)
requires every Feature to be created with one existing Permission, persisted by stable Permission ID. Applications
may reuse one Permission or choose different ones for each Feature, and the management UI may change that binding.
Any existing Permission is eligible under existing tier/assignment rules: Users obtain authority through Roles,
Agents through direct Permissions, and protected Permissions remain human-only. No privileged name, Role bypass,
or new tier restriction is introduced.

Permission deletion is rejected while any Feature references it, including OFF/ON Features. If inconsistent stored
data nevertheless leaves a missing referenced Permission, deny availability without substituting the default or
mutating status. Consumers may present 404 like OFF while retaining an internal diagnostic. This does not equate
all infrastructure failures with 404.

### D2 — Registry, provisioning, and retirement

[WF-019 — Handle Attributes referencing missing Feature records](../wayfinder/tickets/WF-019-missing-feature-records.md)
requires a name-only Attribute or an explicitly registered programmatic reference for every supported feature check.
The registry describes code references; the database owns environment-specific status and Permission selection.
Unknown names error rather than imply ON. Attributes alone do not enforce access.

Before activating referencing code, automatic provisioning creates missing registered Features OFF. Consumer
configuration `DEFAULT_FEATURE_PERMISSION` names an existing Permission, resolved to its ID in the target environment.
If creation is needed but that default cannot resolve, fail provisioning instead of creating incomplete records.
Existing status and Permission choices survive redeployment and default changes. Provisioning creates neither
Permissions nor principal grants. Runtime checks never provision on demand.

Deletion checks current code references and registered pointers. Any reference, or inability to establish absence,
rejects deletion. Remove references, deploy, then retry. A later deployment reintroducing the same name creates a
fresh OFF record with the current default Permission, not the deleted record's settings. No historical name reservation
or cross-deployment fencing is required; the guarantee is current-reference checking, not atomic coordination with
arbitrary concurrent deployments. Unexpected missing runtime records still error, never fail open.

### D3 — Names and operator management

[WF-020 — Define Feature naming and management transitions](../wayfinder/tickets/WF-020-feature-naming-and-management.md)
requires a dedicated FeatureName value with 1–128 ASCII characters: lowercase letters/digits separated by single
hyphens, starting with a letter. Reject invalid input without normalization. Examples: `new-checkout`,
`agent-tools-v2`, and `dashboard`. Names are unique among existing records and immutable; no rename or alias facility.
A different name introduces a new Feature, and retirement uses the guarded workflow above.

Operators manage status, Permission selection, and deletion through consumer UI. The list exposes OFF/PREVIEW/ON;
ON-to-PREVIEW/OFF requires warning and confirmation in that workflow. Reject stale updates, refresh, and reconfirm
when appropriate using lightweight optimistic concurrency; a simple revision is acceptable. No edit-locking,
approval system, management CLI, or independent public management API is required. Automatic deployment provisioning
is separate and leaves existing records unchanged.

Each consumer authorizes its management entry points. A SUPER_ADMIN_ONLY management Permission is permitted but
not mandated; neither that policy nor a single-administrator assumption is hard-coded into this package.

### D4 — Freshness

[WF-021 — Define Feature evaluation freshness](../wayfinder/tickets/WF-021-feature-evaluation-freshness.md)
requires each explicit check to read current stored Feature status and testing-Permission binding, using the existing
authenticated User/Agent snapshot for authority. Do not add per-check reauthentication, shared Feature caching, or
retained Feature settings between worker jobs. Consumers must preserve fresh-read semantics in their adapters.

OFF affects subsequent checks; it does not automatically cancel work already admitted, undo prior effects, or schedule
additional checks. A job that checks again evaluates current Feature state; one with no further check can finish.
Fresh Feature reads do not promise immediate refresh of grants/revocations within an existing principal snapshot.

### D5 — Package and consumer boundary

[WF-022 — Confirm Feature package and consumer integration scope](../wayfinder/tickets/WF-022-feature-package-integration-scope.md)
approves the package-only deliverable:

- Domain model/values, repositories, Permission reference integrity, and accepted state invariants.
- Application evaluation, safe reads and management operations, automatic provisioning, and guarded deletion policy.
- A framework-neutral name-only PHP Attribute and small registry representation/contracts within the permitted
  Domain/Application production boundary; no framework listener or filesystem scanner is copied from CMS.
- Narrow consumer capabilities for persistence and current-reference discovery, package behavior tests,
  consumer-bindable contract scenarios where needed, and integration guidance.

Consumers separately own database adapters/migrations, actual code discovery, registry composition, deployment hooks,
framework/runtime enforcement, UI and its confirmation workflow, HTTP responses/diagnostics, authentication and
entry-point authorization, environment-specific configuration, and end-to-end qualification. Each environment uses
its configured repository/catalog; this EPIC adds no environment/tenant rollout dimension. The same package evaluator
serves consumer entry points without introducing a new transport or management surface.

## Acceptance boundary

Implementation requirements must make the following observable outcomes executable:

1. Valid names and unique immutable identities are enforced; every new Feature has a valid Permission and starts OFF.
2. OFF/PREVIEW/ON decisions work for authorized/unauthorized Users, Agents, and anonymous callers as applicable;
   protected tiers and ordinary action authorization remain intact. Missing Features and broken Permission references
   never grant availability, and default provisioning configuration is never used as an evaluation fallback.
3. Registry provisioning creates only missing registered Features, resolves the configured default to an existing ID,
   rejects unresolved required configuration, and preserves existing choices under repeat invocation. State and result
   contracts describe failures and retries without silently resetting another writer's data.
4. Feature references block Permission deletion. Current code/registry references and failed/incomplete discovery block
   Feature deletion. Removing references permits a later retry; reintroduction creates a new OFF record.
5. Management operations support the specified consumer UI and lightweight stale-update rejection without inventing
   a general CLI/API or a package-level human approval protocol. Consumer confirmation/authorization obligations are
   explicit and separate from library invariant tests.
6. Repeated explicit checks observe fresh Feature state, worker jobs do not retain old settings, and authenticated
   snapshots retain their existing lifecycle. No cache or automatic cancellation is required.
7. Package tests, targeted consumer-bindable contract evidence, and integration guidance distinguish package behavior
   from actual scanner/runtime/UI/persistence qualification. Implementation passes `./bin/planning-check` and the full
   `./bin/build`, including exact production statement coverage. Planning-only checks are not implementation evidence.

## Approved registration/provisioning design

During TICKET-00015 TASK decomposition, John approved a method-only, nonrepeatable name-only Attribute: one Feature
per method declaration, with other checks using explicit registration. He also approved one atomic database
transaction per provisioning pass. Pre-commit failure rolls back that pass; retry rereads stored state and preserves
existing choices, including after post-commit publication failure. This supplies neither guaranteed event delivery
nor an activation receipt. [TICKET-00015](../tickets/00015-TICKET.md) owns the detailed requirements.

## Approved evaluation interface

John approved [TASK-00064](../tasks/00064-TASK.md) as TICKET-00016's complete evaluator slice. It accepts a validated
FeatureName and an existing User or Agent principal snapshot, or null for anonymous input. Match stored Permission IDs
against captured snapshot IDs without changing AuthenticatedAuthority or the existing name-based helpers. Ordinary
availability returns a boolean; unknown Features and broken bindings produce distinguishable errors, with operational
failures kept separate and never converted into availability. Existing snapshot lifetimes and fresh Feature reads
remain unchanged. [TICKET-00016](../tickets/00016-TICKET.md) owns the detailed requirements.

## Approved management and retirement design

John approved [TASK-00065](../tasks/00065-TASK.md) for Permission reference protection,
[TASK-00066](../tasks/00066-TASK.md) for creation/read/update management, and
[TASK-00067](../tasks/00067-TASK.md) for guarded retirement and final lifecycle evidence. One shared Feature revision
starts at 1 and advances only on real status/Permission changes; updates and deletion require expected revision.
Valid no-ops perform no writes, revision advance, or success publication; stale attempts reject. Reads retain broken
Permission IDs with explicit missing-binding indication and reuse existing pagination conventions. Consumer warning/
confirmation, refresh/reconfirmation, and caller authorization do not become a package approval protocol.
[TICKET-00017](../tickets/00017-TICKET.md) owns the detailed requirements.
