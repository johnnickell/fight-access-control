# Permission-Aware MCP Integration and Framework Adapters

## Destination

Provide reusable permission-check tooling and optional framework-native integration for Common's MCP Tools,
Resources, whole Skills, Prompts, Subscriptions and durable Tasks. Consumers can bind their configured Agent
Permissions to these capabilities, enforce current authority at the appropriate request/disclosure/continuation
boundary, and compose application-specific target scope without duplicating protocol or permission mechanics.

Deliver this as **one combined future AccessControl release**, including Common-owned execution Tools and all five
framework families: **Slim, Yii 3, Symfony, Laravel and CodeIgniter 4**. Do not silently ship a reduced first release
that omits Subscriptions, durable Tasks or a selected framework. Exact release number remains **unassigned**.
Individual runtime capabilities remain explicitly opt-in; Task polling works without live Subscriptions. One EPIC
and one release outcome do not require one PR, five duplicate middleware implementations or simultaneous enablement.

The [Wayfinder map](../wayfinder/mcp-capability-permission-integration-map.md) has completed its decisions and this
is its single approved EPIC destination. John confirmed that destination and unassigned version, then explicitly
invoked Grill to write it. No further interview is needed to repeat those settled choices.

## Ownership and package boundary

| Owner | Responsibility |
| --- | --- |
| AccessControl | Existing authenticated authority/Permission contracts; reusable Agent Permission bindings; trusted current-authority check tooling; thin optional permission/framework adapters |
| Common | Neutral MCP protocol/discovery/invocation and access ports, shared execution/notice/Task use cases and storage mechanics, guarded HTTP, selected safe-error categories/presentation and native error integrations |
| Consumer | Authentication selection and trusted context; requirements/grants and stable seed identities; application relationships/project/session/document/Task scope; routes/bootstrap, keys, persistence, workers and runtime; disclosure/sharing and diagnostic-sink policy |

Preserve `Adapter → Application → Domain`. Domain/Application retain their current DDD paths. Adapters use
`Adapter/<Capability>/<Framework-or-Provider-or-Standard>/...`; container extension points use
`Adapter/ServiceContainer/<Framework>/...`, following Common's current ADR 0023 rather than deprecated aliases.
The [project profile](../agents/project-profile.md#package-boundary-and-contracts) owns this narrow structural
approval. Keep framework dependencies optional/isolated and registration deliberate. Later approved implementation
owns Composer mapping, dependency/architecture checks, mirrored Adapter suites and exact statement coverage; no
such executable configuration is supplied by this EPIC.

Do not add an AccessControl project/tenant/relationship store, persistence adapters, stream manager, Task executor,
job scheduler, token issuer, default route or automatic grants. Common must not depend on AccessControl or receive
Agent credentials/principal policy through protocol metadata. Human authority remains distinct from direct Agent
Permissions; OAuth scopes, role labels, recipient fields and supplied IDs are not grants.

## Required outcomes

### 1. Bind protected Tools without modifying Common

Consumers can register nonempty Permission requirements for Common-owned Tools explicitly, while attributes remain
available on AccessControl/consumer-owned Tools. Requirements stay conjunctive: all declared Permissions must hold.
Protected composition rejects missing, malformed or conflicting declarations; no permissive fallback or silent
attribute override. Preserve same-registry/exact immutable Tool-definition identity and unknown/foreign denial.
Do not subclass Common's final Tools or copy their schemas/CQRS implementations merely to attach attributes.

Cover `execution.summarize`, `execution.list`, `execution.get`, `execution.phases`, `execution.activity`,
`execution.messages` and `execution.detail`, together with existing attributed profile Tools. Coarse availability
precedes protected Tool validation/dispatch, but does not itself authorize the requested records or protected bodies.
Generic registry lookup, direct `handle()` and alternate bus paths must not become unguarded bypasses.

### 2. Bind independently protected Resources, Skills and Prompts

Supply reusable Agent Permission composition through the appropriate neutral family hooks, with validated identity
association and fail-closed unknown/unmapped requirements. Recheck discovery and direct retrieval independently;
prior listing is neither required for an admitted read nor continuing authority for a later one.

Whole-Skill admission and general Resource admission remain independent of Tool/Prompt availability. Skill member
reads, saved/historical URIs and returned Resource links receive their applicable current checks. A Prompt does not
authorize a linked Resource, Skill activation or Tool execution. Application-backed providers retain independent
business Query admission; static content does not need invented Commands/Queries. Keep metadata, visible catalogs,
counts, cursor context and protected bodies within their actual permitted scope.

### 3. Keep target scope and protected detail separate from capability access

Consumer relationship policy supplies Common's scoped access decisions. A broad Tool/family Permission must not
manufacture all-project, all-session, all-Task or body grants by copying request selectors into an access object.
Execution/timeline permission, protected reference/metadata permission and body permission remain distinct. Apply
current admission on every selected page/chunk and constrain totals as well as rows; a body grant alone cannot
bypass a required metadata grant. Consumers also protect direct Query/Command/worker entry points.

### 4. Integrate current authority with Subscriptions and durable Tasks

Reuse Common's actual implemented ports, not hypothetical signatures. Compose independent checks for supported
notice recording/removal/read/recovery, listening, notification disclosure, subscriber inspection and optional
publication. Topic matches, intended recipients, subscription IDs and heartbeats grant no continuing authority.
Protect queued notifications and catalog-change signals themselves from concealed-activity disclosure.

For durable Tasks, keep creation, trusted producer updates, read/result/input disclosure, answer admission,
cancellation, removal and worker continuation independently authorized as applicable. Prior successful creation,
handle possession and generic safe-notice access do not authorize full Task state. Task-specific live state must
not leak into the general safe-notice feed or indiscriminate Mercure output. Current-state recovery and polling
remain independent of live delivery; follow Common's actual completeness/retention and input/cancellation contracts.

Ordinary requests retain the accepted request-local principal snapshot. Before each new protected live disclosure
or background continuation, evaluate current Agent status, original credential binding, applicable Permissions
and consumer-owned scope through trusted check contracts. Revocation, credential change or verification failure
denies further protected disclosure/work; do not silently switch credentials or replay the original consumed
nonce. Callers/Common runtime invoke these checks; AccessControl does not manage the stream/job. Denial cannot
retract disclosed bytes, undo earlier effects, force cancellation or prove a durable job stopped.

### 5. Integrate all five native framework journeys

| Framework family | Integration direction |
| --- | --- |
| Slim | Shared PSR-15 permission middleware with consumer route/context composition |
| Yii 3 | Reuse the PSR-15 integration where its real route/context contract fits; no Yii 2 support inferred |
| Symfony | Native subscriber/listener at an appropriate post-routing admission point |
| Laravel | Native middleware and explicit consumer registration |
| CodeIgniter 4 | Native before-filter integration |

All adapters delegate inward to reusable checks, never duplicate application policy or trust caller-supplied
principal/Permission data. Protect declarations, request-local lifetimes and matched-target metadata; deny safely
before protected validation/dispatch. Qualify controller-construction promises against the native lifecycle:
Symfony `kernel.controller` runs after controller resolution and cannot by itself provide pre-construction denial.
Specify supported version ranges and actual ordering/subrequest/context behavior during downstream design and
qualification. No relative implementation priority among the frameworks was selected.

### 6. Compose safe errors without merging transport contracts

Remain compatible with, and reuse where appropriate, Common's safe Application failure categories and selected
HTTP error boundary. Permission adapters signal deliberate outcomes; they do not produce raw-message responses,
guess statuses from exception codes/causes, convert operational faults into denials or install competing loggers.
Retain one redaction-aware reporting owner and explicitly public-safe projection, including required challenges/
headers and safe fallback on failure. Unsafe legacy handlers are not a fallback.

MCP retains JSON-RPC, unavailable/unknown concealment and exact-class Tool failure mapping to authored constants;
it must not inherit HTTP/JSend envelopes or assume category inheritance is an automatic Tool mapping. OAuth keeps
its own protocol outcomes. Domain exceptions remain Domain-owned and do not depend on Application categories.
Agent OS's custom RuntimeException failures and response/reporting contracts require deliberate consumer migration
if later selected; this EPIC does not modify that application or promise drop-in replacement.

## Use-case and side-effect boundary

Actors are consumer integrators and currently authenticated callers, with separately trusted producers/workers
for Common operations. Triggers are protected discovery/read/invocation, native HTTP admission, repeated live
disclosure or durable-operation admission/continuation. Outcomes are an admitted operation within permitted scope
or safe denial/failure without unauthorized work or concealed metadata/body disclosure.

No new business Commands, Queries or Events are mandated solely for permission evaluation. Reuse the owning Common
use cases/buses and existing AccessControl authentication/authority contracts. Permission checks do not mutate a
business aggregate, commit another handler's work or create a grant. Existing authentication nonce consumption and
its transaction/freshness guarantees remain distinct from later authoritative revalidation. Any new public API,
Permission vocabulary/tier or persisted-shape consequence must be specified in downstream requirements/design;
this EPIC invents no schema/migration, compatibility shim or implicit transaction/outbox guarantee.

## Acceptance evidence

Later implementation must demonstrate:

- Real Common-owned and attributed Tool composition with complete requirements, missing/conflicting/foreign
  rejection and denial before protected validation, Query/provider work, content opening, progress or retry admission.
- Actual AccessControl authority/Permission resolution composed with neutral family and scoped Common admissions,
  not only Boolean stubs; independent protected metadata/body grants and cross-project/session/Task isolation.
- Fresh pages, direct reads, saved links/URIs/cursors, chunks and retries after authority changes; no caller `_meta`,
  IDs, cached catalog or prior success supplies authority. Protect totals, continuation/history-loss and signals too.
- Current authority checks before queued/live disclosure and protected continuation, with revocation/rotation/
  Permission/scope changes and resolver faults; no stale singleton principal, nonce replay or silent credential switch.
- Distinct Task/notice operation permissions, full-state isolation, polling/recovery without live delivery and honest
  failure/retention semantics against the actual qualified Common implementations.
- All five framework-native journeys with real applicable lifecycles: ordering, trusted context, request reset,
  optional dependency/registration isolation, safe failure/header/fallback and single-reporting behavior.
- Minimum-supported Common/framework verification, finite encoded response boundaries and safe diagnostics without
  private exception messages, credential data, raw protected content or accidental duplicate reporting.
- Mirrored owned-code tests, exact statement coverage including new adapters, architecture checks, documentation,
  canonical package gate and required independent Review/behavioral QA under the project profile.

These are future acceptance obligations, not checks already run. Package/controlled framework fixtures qualify the
promised library integration; actual consumer database/cryptography/bootstrap/lifetimes, deployed clients and
operations remain separate evidence. No Agent OS/starter adoption, deployment or universal redaction is claimed.

## Exclusions

- A Common protocol/storage fork, second MCP endpoint, generic CQRS bridge, framework policy engine, project/tenant
  relationship model, persistence adapter, scheduler/executor or automatic Permission grants.
- Changes to Common, Agent OS or starter repositories, their requirements, consumer Composer adoption or deployment.
- Unselected/deprecated MCP capabilities or unrelated framework infrastructure for adapter-count symmetry.
- Guarantees of in-flight interruption, rollback, exactly-once effects, retraction, complete capture, guaranteed
  notification recording/delivery, receipt/processing or authoritative Workflow/Review/QA state from MCP handles.
- Version selection, publication/merge, signed release and deployment; creation of TICKETs/TASKs from this Grill.
